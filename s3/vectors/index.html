S3 Vectors：让 S3 里的文件按意思搜得到

S3 里放着大量文档和图片，现在只能按文件名找。这篇讲清楚 Amazon S3 Vectors 是什么、怎么用、怎么收费，再用一个完整的场景 demo 串起来：S3 文件 → 向量 → 按权限检索 → 带出处的回答。

声明：本文配套的代码是讲解用的示例，不是 AWS 官方工具，不能直接用在生产环境。
上限、价格以 AWS 官方文档为准（本文查阅日期 2026-11-24，价格来自 AWS Price List，发布于 2026-11-21）。
先看这里：三句话
  1. S3 Vectors 是 S3 里专门放向量的桶。不用建集群，按存储量和查询量付费，适合"数据很多、查询不太频繁"的场景。
  2. 一定要用 ENHANCED 索引。它先按权限过滤，再找最相近的，一个人只能看 1% 的文件时也能召回得到；它还支持中文全文检索和混合检索。
  3. 费用的大头是"查询处理量"：索引越大，每次查询越贵。原文片段放进"不可过滤"的元数据，能按部门分开就分成多个索引。

标注说明：要点 每节开头的关键信息 · 高亮 核心结论 · 文档 · Limits 出处（AWS 官方文档的页面），可以点到文末参考里查原文。

1 · 它是什么

要点本节关键信息
  • 三层：向量桶 → 向量索引 → 向量（key + 浮点数 + 元数据）。文档 · What is
  • 冷查询亚秒级，热查询最快约 100 ms；写入强一致，写完马上能查。文档 · What is

"向量"就是把一段文字或一张图变成的一串数字。意思相近的内容，数字也相近。所以搜索"工资几号发"时，能找到写着"每月工资在次月 10 日发放"的那段话，哪怕两句话里没有一个相同的词。

向量桶一种新的 S3 桶；"阻止公有访问"永远打开，关不掉
→
向量索引桶里再分组；维度、距离算法在建索引时定死
→
向量key + 1024 个浮点数 + 元数据（部门、权限组、原文片段……）
图 1 · S3 Vectors 的三层结构
  • 不用管机器：没有集群、没有节点数，按用量付费。文档 · What is
  • 适合什么：官方说法是 "ideal for workloads where queries are less frequent"。比如企业文档检索、Agent 记忆、图片去重、视频片段检索。文档 · Use cases
  • 不适合什么：需要很高 QPS、很低延迟的在线推荐。这类场景可以把索引快照导出到 OpenSearch Serverless。文档 · Integrations
  • 权限：IAM 的命名空间是 s3vectors:，和 s3: 分开，可以精确授权到某一个索引。

2 · 怎么用：五个 API 就够

要点本节关键信息
  • 建索引时维度、距离算法、不可过滤的字段以后都不能改。文档 · Full-text config
  • 同一个 key 再写一次就是覆盖；每次 PUT 最少按 128 KB 计费，所以要批量写（每次最多 500 个）。定价页
  1. 建桶：CreateVectorBucket。
  2. 建索引：CreateIndex，定好维度（和 embedding 模型一致，例如 Titan Text V2 是 1024）、距离算法（cosine）、哪些元数据只返回不过滤。
  3. 写入：PutVectors，每次最多 500 个。
  4. 查询：QueryVectors，带上查询向量、topK、过滤条件；可以返回元数据和距离。
  5. 管理：GetVectors（每次最多 100 个 key）、ListVectors（可分 16 段并行）、DeleteVectors。
# boto3 1.44+（老版本没有 queryTexts / returnScores）
sv = boto3.client('s3vectors', region_name='eu-central-1')
sv.create_vector_bucket(vectorBucketName='my-vectors')
sv.create_index(vectorBucketName='my-vectors', indexName='docs',
    dataType='float32', dimension=1024, distanceMetric='cosine',
    metadataConfiguration={
        'nonFilterableMetadataKeys': ['chunk_text'],          # 原文：只返回，不过滤
        'textSearchConfigurations': [{'metadataKey': 'chunk_text', 'language': 'zh'}]})

sv.put_vectors(vectorBucketName='my-vectors', indexName='docs', vectors=[{
    'key': 'doc1#00000', 'data': {'float32': emb},
    'metadata': {'dept': 'HR', 'acl': ['all-staff'], 'chunk_text': '年假 12 天……'}}])

hits = sv.query_vectors(vectorBucketName='my-vectors', indexName='docs', topK=5,
    queryVector={'float32': q_emb},
    filter={'acl': {'$in': ['all-staff']}},                         # 按权限过滤
    returnMetadata=True, returnDistance=True)['vectors']

每一步都有能直接跑的脚本：examples/（01 建索引 · 02 写入和查询 · 03 过滤 · 04 混合检索 · 05 管理 · 06 Agent 记忆）。

过滤语法

写法意思
{"dept": "HR"}等于（不写操作符就是 $eq）
{"price": {"$gte": 10, "$lte": 50}}数值范围：$gt $gte $lt $lte
{"acl": {"$in": ["hr", "all-staff"]}}属于其中之一；acl 是列表字段时，和给定的值有交集就算匹配（实测）
{"path": {"$startsWith": "hr/"}}前缀匹配（只在 ENHANCED 上可用）
{"$and": [...]} / {"$or": [...]}组合；另有 $ne $nin $exists

注意过滤条件的个数：$in 里有 3 个值就算 3 个条件，ENHANCED 索引每次查询最多 100 个。文档 · Metadata filtering 一个用户属于很多权限组时，要先在业务侧合并。

3 · ENHANCED：先过滤，再检索

要点本节关键信息
  • ENHANCED 先算出过滤条件命中的向量，只在这些里面找最相近的（pre-filtering）。文档 · Metadata filtering
  • 2026-09-30 及以后新建的向量桶默认 ENHANCED；之前的桶默认 CLASSIC，可以原地升级，不额外收费。文档 · Index mode
CLASSIC：一边找一边过滤
先找"最相近的一批"，再检查权限一个人只能看 1% 的文件时，最相近的那批里可能没有他能看的 → 结果少于 topK，甚至为空
ENHANCED：先过滤
先圈出"他能看的"，再在里面找最相近的权限再窄也能召回；可过滤元数据最多 40 KB；支持全文检索、$startsWith
图 2 · 两种索引模式的区别：对"按权限过滤"影响很大

按权限检索时，过滤条件往往很窄，所以这一点比什么都重要。查看一个索引的模式用 GetIndex 看 indexMode；升级用 UpdateIndexMode，原地生效，不用重新导入。文档 · Index mode

4 · 混合检索：意思和关键词都要

要点本节关键信息
  • 向量检索懂意思，但对错误码、型号、人名这种"要一模一样"的词不敏感；BM25 全文检索正好补上。文档 · Hybrid search
  • 混合检索 = 向量 + BM25，用 RRF 合成一个排名；有 zh 中文分词器。文档 · Full-text config

→
向量检索：按距离排序
只传 queryTexts
→
全文检索：按 BM25 分数排序
两个都传
→
混合检索：两种排名用 RRF 合成一个

hits = sv.query_vectors(vectorBucketName='my-vectors', indexName='docs', topK=5,
    queryVector={'float32': embed('VPN 报错 E2071')},
    queryTexts=[{'text': 'VPN 报错 E2071', 'metadataKey': 'chunk_text'}],
    filter={'acl': {'$in': groups}}, returnMetadata=True, returnScores=True)
  • 怎么开：索引必须是 ENHANCED；在 textSearchConfigurations 里列出文本字段，可选 10 种语言：en、fr、es、pt、it、de、nl、zh、ja、ko。
  • 已有数据也能开：UpdateMetadataConfiguration 会在后台回填，字段状态从 BUILDING 变成 ACTIVE 之后才能查。回填按 PUT 的价格收费。定价页
  • 分词器以后不能改：要换只能删掉这个字段，再重新加一次。

6 · 怎么收费

要点本节关键信息
  • 五项：存储、写入、查询请求、查询处理量、返回数据；没有固定费用。定价页
  • 查询处理量 = 被查索引里的向量数 × 每个向量的"处理大小"，按索引大小分三档。定价页
  • 不可过滤、也不做全文检索的元数据不算进查询处理量。定价页
项目美东（弗吉尼亚北部）法兰克福怎么算
存储$0.06 / GB·月$0.064 / GB·月向量 + key + 全部元数据
写入（PUT）$0.20 / GB$0.214 / GB每次请求最少按 128 KB 算
查询请求$2.50 / 百万次$2.70 / 百万次每次 QueryVectors
查询处理量每个索引：前 10 万个向量 $0.004/TB · 10 万~1,000 万 $0.002/TB · 1,000 万以上 $0.0004/TB（法兰克福约高 7%）索引里的向量数 × 处理大小
全文检索文本$0.00012 / TB（单一价格）全文字段的大小 × 向量数
返回数据$0.01 / GB；每次查询前 512 KB 免费每条结果最少按 256 字节算

用 AWS 自己的例子对一下

  • 例 1：1,000 万个向量分在 40 个索引里（每个 25 万），每月 100 万次查询 → $11.38 / 月。定价页 · Example 1
  • 例 3：1,000 万个向量在 1 个索引里，每个带 3 KB 全文检索文本，每月 100 万次混合检索 → $107.79 / 月 + 一次性回填 $5.72。定价页 · Example 3

同样是 1,000 万个向量，差 10 倍：区别主要在每次查询要扫的索引有多大。如果业务本来就按部门、按租户查，分成多个小索引会便宜很多。repo 里的 tools/cost_estimate.py 用的就是定价页的算法，测试会用这两个例子核对。

不在 S3 Vectors 账单里的费用：embedding（Bedrock 按 token 收费）、OCR（Textract 按页收费）、Lambda、SQS、回答用的大模型。对于百 TB 级的存量回填，这几项通常比 S3 Vectors 本身贵得多，要单独估算。

8 · 场景：S3 文件语义检索（按权限过滤）

要点本节关键信息
  • 事件只是"提醒"，S3 的当前状态才是"事实"：重复、乱序的事件不会留下错误的向量；极少数丢失的事件由对账补上。
  • 权限组只从验证过的 JWT 里取，请求体里写的 groups 一律忽略；对象没有 acl 就谁都搜不到。
  • 处理一个对象不扫描整个索引：切片 key 连续编号，按 key 直接取。

需求：S3 桶里有百 TB 级的文档、图片、视频，要能用自然语言搜内容，结果只包含调用方有权看的文件，对象处理不出区域。完整需求和逐条对照见 repo 的 requirements.md 和 architecture.md。

图 5 · 场景 demo 的整体流程

indexer 每次怎么判断

  1. HEAD 对象：对象不在了 → 删掉它的全部向量。所以删除事件、过期事件、迟到的旧事件都按同一条规则处理。
  2. ETag、规则版本、模型都没变，上次也写完整了 → 什么都不做（重复事件）。如果只是权限变了 → 只重写元数据，不重新做 embedding。
  3. 否则 → 抽取、切分、embedding，覆盖第 0..m-1 片，再删掉第 m 片及之后的旧片。
  4. 写完再 HEAD 一次：对象在处理期间又被覆盖了 → 抛异常让队列重试，重试时处理新版本。
为什么 Lambda 角色要给 s3:ListBucket？没有这个权限时，HEAD 一个已删除的对象返回的是 403，不是 404。indexer 就分不清"被删了"还是"没权限"，删除事件会一直失败。ListBucket 只是读权限，不影响"只读源桶"的要求。

10 · 常见坑

  • CLASSIC 索引 + 很窄的过滤条件 → 结果偏少，甚至为空。换成 ENHANCED。
  • 大文本放进可过滤元数据 → 超过上限时写入报 400；而且每次查询都要为它付费。原文片段放进 nonFilterableMetadataKeys。
  • 频繁覆盖或删除同一批 key → 旧数据会暂时计入索引大小，查询费用暂时变高。定价页
  • 一次只写一个向量 → 每次 PUT 最少按 128 KB 计费。批量写，每次最多 500 个。
  • Lambda 自带的 boto3 太旧 → 没有 queryTexts、returnScores。部署包里要带上新版 boto3。
  • 处理每个对象都 ListVectors 一遍 → 索引一大就跑不动。用固定格式的 key（doc_id#序号），按 key 直接取。
  • 写到一半、删到一半 → 留下永远删不掉的旧切片，甚至旧权限。规则：第 0 片最后写，删除从高序号往下删，这样剩下的永远是连续的一段，重试时能补完。
  • 失败消息等 90 分钟才重试 → SQS 的可见性超时一般设为 Lambda 超时的 6 倍。失败时用 ChangeMessageVisibility 缩短等待时间。
  • 权限组由调用方自己填 → 谁都能冒充别的组。权限组只能从验证过的身份里取。

? · 术语表

术语大白话
向量 / embedding把一段文字或一张图变成一串数字；意思相近，数字就相近
距离（cosine）两个向量有多"不像"：0 是一样，越大越不像
topK返回最相近的前 K 条
元数据贴在向量上的标签：部门、权限组、路径、原文片段……
可过滤 / 不可过滤能不能在查询里按它筛选；不可过滤的只随结果返回，不算查询处理量
BM25经典的关键词打分方法：查询里的词出现得越多、越少见，分数越高
RRF把两个排名合成一个：每条结果按它在两个排名里的名次加分
ENHANCED / CLASSIC索引模式：先过滤再检索 / 一边找一边过滤
ETagS3 给每个对象版本的"指纹"；内容一变，ETag 就变
DLQ死信队列：失败太多次的消息放到这里，等人处理
JWT登录后拿到的"通行证"，里面写着你是谁、属于哪些组，带签名，改不了
