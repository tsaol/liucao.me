AgentCore Runtime：microVM 还是 Instances

Runtime 是 AgentCore 的核心：把 agent 放进容器，每个会话一个隔离环境。2026 年它多了第二种计算方式 Instances，跑在你自己账号的 EC2 上。这页讲两种怎么选、怎么收费、安全边界在哪，再加上我实测的数据和踩到的坑。

1 · 是什么 2 · 两种计算方式 3 · microVM V2 4 · Instances 5 · 怎么收费 6 · 评估 7 · 实测 8 · 怎么选 9 · 上手
查阅日期 2026-11-25。价格、上限以 AWS 官方文档为准。"实测"是我在东京区域（ap-northeast-1）用一个多 agent 编程任务测的：同一次任务里一半 agent 放 microVM、一半放 Instances，样本小（每边 3 个 agent），只说明量级。
先看这里：三句话
  1. Runtime 有两种计算方式：microVM（无服务器、按用量计费、秒级启动）和 Instances（跑在你自己账号的 EC2 上，按实例计费再加 12% 管理费）。
  2. 默认选 microVM。只有需要 x86 / GPU、超过 8 小时的会话、或者要 root 权限（装系统软件、跑容器、封网络）时才用 Instances。
  3. 用 Instances 一定要记住：停会话不等于关机器。要删掉会话，实例才会释放；而且这些实例默认不出现在 EC2 的实例列表里。

标注说明：要点 每节开头的关键信息 · 高亮 核心结论 · 文档 · Instances 出处（AWS 官方页面，文末参考里有链接）· 实测 我自己在东京区域测出来的结果。

1 · Runtime 是什么

要点本节关键信息
  • 你给一个容器镜像（或代码包），它负责运行、隔离、伸缩；一个会话 = 一个隔离环境，用你传的 runtimeSessionId 区分。文档 · Instances
  • 容器只要做到两件事：GET /ping 返回健康状态，POST /invocations 处理请求，都在 8080 端口。文档 · Instances 入门

调用方式很简单：InvokeAgentRuntime 带上 runtime 的 ARN、会话 ID 和请求内容。第一次用一个新的会话 ID 时，Runtime 给它准备一个新环境；之后同一个会话 ID 的请求都进同一个环境，会话之间互相看不到。会话结束用 StopRuntimeSession。

框架和模型都不限：Strands、LangGraph、CrewAI、LlamaIndex、Google ADK、OpenAI Agents SDK，Bedrock 里外的模型都行，也支持 MCP 和 A2A 协议。文档 · What is

2 · 两种计算方式

要点本节关键信息
  • 创建 runtime 时选，之后不能改。文档 · Instances
  • 官方建议：轻量、API 驱动、很快做完的 agent 用 microVM；长时间、有状态、要 GPU 或多 agent 共享环境的用 Instances。文档 · Instances
microVM（默认）Instances
跑在哪AWS 托管的 Firecracker microVM，你看不到机器你自己账号、自己 VPC 里的 EC2（AWS 托管的实例）
架构arm64x86_64 或 arm64，机型自己选（最多 30 种）
规格按需扩，最大 8 vCPU / 32 GB，镜像最大 10 GB由机型决定，包括 GPU、大内存
会话最长8 小时14 天，停了以后还能用同一个会话 ID 恢复（数据盘保留）
隔离单位一个会话一台 microVM一个会话一台 EC2；同一会话里的多个 agent 互相不隔离
root 权限没有可选特权模式（PRIVILEGED）
计费按实际 CPU、内存用量，按秒EC2 按实例时长 + 12% 管理费
启动实测2.5–6 秒63–93 秒（要开一台 EC2）

3 · microVM：新一代（V2）

要点本节关键信息
  • 每个会话一台独立的 Firecracker microVM，硬件级隔离。What’s New 11-12
  • V2 先把初始化好的 agent 做成快照，每个新会话从快照恢复：2 GB 镜像 P75 启动不到 2 秒（V1 是 29.7 秒）。What’s New 11-12
  • 内存按需分配、不用就回收，多轮对话的 agent 计费内存最多少 68%；空闲缩到 0。What’s New 11-12
  • 默认版本：2026-11-12 起，东京等 19 个区域新建 runtime 默认就是 V2；老 runtime 要自己把 platformVersion 改成 V2。What’s New 11-12
  • 适合的活：官方举的例子是编译大代码库、驱动浏览器、在会话里加载本地模型。What’s New 11-12
  • 限制：容器里没有改网络规则的权限，封不住实例元数据地址实测。所以执行角色要给最小权限：在里面跑的代码有机会拿到这个角色的临时凭证。

4 · Instances：跑在自己账号的 EC2 上

要点本节关键信息
  • 三样东西：capacity provider（EC2 的"模板"：系统、机型、子网、磁盘、角色）→ runtime（跑什么）→ 会话（一台 EC2）。文档 · Instances
  • 同一台实例上的 agent 共享文件系统，能互相读到凭证；要隔离就分开会话。文档 · Security
  • 特权模式下 agent 以 root 运行，但这个会话只跑它一个，所以隔离边界不变。文档 · Security
capacity provider系统 x86/arm、允许的机型、子网和安全组、磁盘、空闲多久关机
→
runtime容器镜像、执行角色、协议；可选特权模式
→
会话 = 一台 EC2第一次调用时开机；最长 14 天；数据盘可保留
图 1 · Instances 的三层结构（来源：文档 · Instances）

要准备的 IAM 角色

  • 基础设施角色（operator role）：AgentCore 扮演它来开机、打标签、配网卡、关机。可以直接挂托管策略 BedrockAgentCoreRuntimeInstancesOperatorRolePolicy，信任 bedrock-agentcore.amazonaws.com。文档 · Security
  • 实例配置文件：挂在 EC2 上，只用来收系统日志，不给 agent 代码任何权限。不传的话，AgentCore 会用它自己建的默认实例角色。托管策略文档
  • 执行角色：agent 代码拿到的权限，和 microVM 一样。

特权模式和嵌套虚拟化

  • 特权模式（2026-11-18）：agent 可以装系统软件、跑嵌套容器，比如自己起 Postgres 和 Redis 做集成测试。设置在 runtime 的 capacityProviderConfiguration.operatingSystemConfiguration.linux.privilegeMode。What’s New 11-18
  • 嵌套虚拟化（2026-11-19）：会话里可以用 KVM 跑虚拟机和模拟器（比如安卓模拟器），只支持 Intel 机型（C7i、C8i、M7i、M8i、R7i、R8i）。What’s New 11-19

5 · 怎么收费

要点本节关键信息
  • microVM V2：$0.1276 / vCPU·小时 + $0.0169 / GB·小时，按实际用量、按秒；等模型回复的 I/O 时间 CPU 不收费。定价页
  • Instances：EC2 按实例从开机到关机计费（最少约 1 分钟）+ 按需价 12% 的管理费（G 系列 GPU 7.8%）；Savings Plans、预留实例能抵 EC2 部分，抵不了管理费。定价页

官方例子：c7g.2xlarge（8 vCPU / 16 GB，美东）跑一个 3 小时的会话 = 3 × $0.289 = $0.867，管理费 12% = $0.104，合计约 $0.97。定价页

按我的任务估一下（量级）

  • agent 大部分时间在等模型回复，CPU 很闲。microVM 只收实际用量，每个 agent 跑 40 分钟大约几分钱。
  • Instances 整台机器从开机就计费（包括约 1.5 分钟的开机时间）：m7g.2xlarge 东京按需价 $0.4216/小时，加 12% 管理费是 $0.472/小时，一个 agent 跑 40 分钟约 $0.33。AWS Price List
  • 128 个 agent 同时跑 40 分钟：microVM 约 $4.7，Instances（m7g.2xlarge）约 $42；换成 m8g.large 约 $11.5、m7g.large 约 $10.5。对比之下，这种规模的任务模型费用是几百美元。下一节有计算器。

6 · 评估：两种方式逐项对比

要点本节关键信息
  • 速度、费用、运维：microVM 明显更好；安全控制、硬件选择、长任务：Instances 更好。实测
  • 计算费在 agent 任务里通常只是零头：这次实测 microVM 约占总费用 0.3%，Instances 约 3.5%（模型费 $3.01）。实测
  • Instances 最大的风险不是贵，而是忘了删会话：一台 m7g.2xlarge 忘记关，一天就是 $11.3。AWS Price List

7 · 实测：同一个任务，一半放 microVM，一半放 Instances

要点本节关键信息
  • 启动差一个数量级：microVM 2.5–6 秒，Instances 63–93 秒；开始干活以后两边一样快。实测
  • Instances 开特权模式后，实例元数据地址能真正封住（容器内 iptables 生效并验证）；microVM 做不到。实测
  • 停会话不会释放 EC2：我有 6 台实例在会话停掉后又跑了约 1 小时，必须删除会话才关机。实测

官方文档没写清楚、我踩到的坑

  1. 停会话不等于关机器。StopRuntimeSession 只停了 agent，EC2 还开着、还在计费，"空闲 10 分钟关机"也没触发（我的 6 台多跑了 35–80 分钟，多花约 $2.66）。要调 DeleteCapacityProviderSession（参数是 capacity provider ID 和会话 ID），实例才会释放。实测
  2. 这些实例默认是隐藏的。文档提了一句：托管实例默认不出现在 EC2 控制台和 API 的列表里。用 CLI 查要加 --include-managed-resources，否则会以为"都关了"。实例标签里有 bedrock-agentcore:runtime-session-id，可以按它对账。文档 · Instances
  3. 默认的 STANDARD 模式下，容器虽然是 uid 0，但权限被收掉了：不能 chown、不能切换到别的用户、不能改 iptables。如果你的入口程序要降权运行 agent，就得用特权模式。实测
  4. 请求内容是分块传的（Transfer-Encoding: chunked，没有 Content-Length）。只认 Content-Length 的 HTTP 服务器会读到空内容。microVM 上没这个问题。实测
  5. 允许的机型列表不是优先顺序。我写的是 m8g.2xlarge 在前、m7g.2xlarge 在后，结果开出来的都是 m7g。实测
  6. 特权模式要新版 SDK。CLI 2.36.47 还没有这个参数，boto3 1.44.11 有。实测

8 · 怎么选

要点本节关键信息
  • 默认用 microVM：启动快、按用量付费、几乎不用运维。
  • 这几种情况用 Instances：要 x86 或 GPU；会话超过 8 小时；要 root（装系统软件、跑容器、封网络）；要用 Savings Plans 或容量预留。
  • 两种可以混用：一个系统里，决定整体进度的 agent（比如规划者、组长）放 microVM 求快；需要特殊环境或更严格网络控制的 agent 放 Instances。
  • Instances 上不要为了省钱把互不信任的 agent 塞进同一个会话：它们能读到彼此的凭证。
  • 大规模之前先看配额：Instances 一个会话一台 EC2，100 个并发会话就是 100 台实例，要先确认账号的 EC2 vCPU 配额。
  • 一定要做对账：任务结束后，按会话 ID 标签查一遍还有没有在跑的实例（记得加 --include-managed-resources）。

9 · 上手：Instances 的四步

要点本节关键信息
  • 前提：一个实现了 /ping 和 /invocations 的容器镜像（推到 ECR），一个私有子网和安全组。
# 1. 基础设施角色：信任 bedrock-agentcore.amazonaws.com，挂托管策略
#    BedrockAgentCoreRuntimeInstancesOperatorRolePolicy（在 IAM 里建）

# 2. capacity provider：系统、机型、网络、空闲多久关机
aws bedrock-agentcore-control create-capacity-provider --name my_cp \
  --permissions-configuration capacityProviderOperatorRoleArn=<基础设施角色 ARN> \
  --compute-configuration '{"ec2Configuration": {
     "launchTemplateSource": {"launchParameters": {"operatingSystem": "LINUX_ARM64",
        "instanceRequirements": {"allowedInstanceTypes": ["m8g.large"]}}},
     "vpcConfiguration": {"subnets": ["<子网>"], "securityGroups": ["<安全组>"]},
     "lifecycleConfiguration": {"idleInstanceTimeout": 600, "maxLifetime": 28800}}}'

# 3. runtime：镜像、执行角色，挂到 capacity provider 上（要特权模式就用新版 boto3）
aws bedrock-agentcore-control create-agent-runtime --agent-runtime-name my_agent \
  --agent-runtime-artifact containerConfiguration={containerUri=<ECR 镜像>} \
  --role-arn <执行角色 ARN> \
  --capacity-provider-configuration capacityProviderArn=<capacity provider ARN>

# 4. 用完：先停，再删会话（只停不删，EC2 会一直开着）
aws bedrock-agentcore stop-runtime-session --agent-runtime-arn <runtime ARN> --runtime-session-id <会话 ID>
aws bedrock-agentcore delete-capacity-provider-session --capacity-provider-id <ID> --session-id <会话 ID>

注意：在 zsh 里写 ARN 时，"$ACCOUNT:role/..." 里的 :r 会被当成变量修饰符吃掉，ARN 变成 ...ole/...。要写成 ${ACCOUNT}。实测
