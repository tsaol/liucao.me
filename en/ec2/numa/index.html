NUMA: The hidden tax of large instance types

You rent a big 192-core machine, but benchmarks come in at only 60% of what you expected. The CPU graphs look normal, and memory isn't full. The problem often isn't "how much is used" but "where the data lives." This post starts from a real motherboard and works up to the kernel, databases, and Kubernetes.

1 · Physical origins 2 · Why it's called NUMA 3 · Look at the topology 4 · Where to put memory 5 · Counters 6 · Automatic migration 7 · Real MySQL incidents 8 · Common pitfalls 9 · EC2 topology 10 · K8s 11 · When to leave it alone
NUMA in three sentences
  1. A large server has several CPUs,Each CPU manages its own set of memory. A CPU plus its memory is called a NUMA node.
  2. Reading your own node's memory is fast; reading another node's memory About twice as slow.
  3. So on large machines, besides looking at "how much memory is used", you also need to look at"Which node the memory is placed on". Small instances (single node) don't need to worry about this at all.

1 · Physical origins

Let's start with an analogy. A company rents two buildings, and each building has its own file room. Employees who need a file from their own building's file room just walk a few steps. To get a file from the other building, they have to cross the skybridge between the two. The route is longer, the skybridge is only so wide, and when it gets crowded they have to queue.

This is exactly how memory is laid out in a server:

  1. Building = CPU socket(a CPU socket holds one CPU; it can also be a CCD / tile within a chip, i.e. a group of cores inside the chip). Each socket has its own Memory controller(the circuitry that reads and writes the memory DIMMs).
  2. Records room = DIMM memory module. Each DIMM connects to a specific memory controller, so it "belongs" to a particular socket.
  3. Corridor = interconnect between sockets. Intel calls it UPI (formerly QPI), AMD calls it Infinity Fabric, and Arm Neoverse platforms use a CMN mesh (on-chip mesh network) plus inter-chip coherent links. Bandwidth is limited, and there's extra latency.

A description alone isn't very intuitive, so let's look at a real dual-socket motherboard:

In the photo you can see the "buildings" and the "archive rooms," but not the "skybridges." Drawn as a diagram, it looks like this. A socket plus its own memory is called a NUMA node:

How much slower exactly? Here are typical latencies:

Where the data lives Latency
L1 cache (the fastest cache inside the CPU)~1 ns
L2 cache~4 ns
L3 cache~15 ns
Local DRAM (memory modules)~80 ns
Remote DRAM (cross-socket)~150–200 ns

Compared with local, cross-socket is roughly 2x slower. In other words, for the same memory read, if the data is on the wrong node, you wait twice as long. Multiply that by billions of memory accesses per second and you get a performance gap you can actually feel.

2 · Why it's called NUMA

NUMA is Non-Uniform Memory Access , short for Non-Uniform Memory Access. “Non-uniform” refers to the behavior described in the previous section:How long a memory read takes depends on where the memory is. Local is fast, remote is slow, and the gap isn't a fixed number.

Where there's "non-uniform", there's "uniform". Its opposite is called UMA(Uniform Memory Access):

Back to the archive room analogy: UMA is like a company with only one archive room. It's equally far for everyone, so access time is "uniform." That's fine when there are few people, but once there are many, everyone crowds into the same hallway, and the hallway becomes the bottleneck.

The fix is for each building to have its own records room, i.e.Moved the memory controller into the CPU. AMD did this first with Opteron in 2003, and Intel followed with the Nehalem architecture in 2008 (the server Xeon 5500 launched in 2009). Since then, almost every dual-socket server has been NUMA.

NUMA as a design actually goes back further: in the 1990s, large machines like Sequent's NUMA-Q and SGI's Origin already used it. Back then it was limited to expensive specialized machines. Only once the memory controller moved into the CPU did it become something any developer might run into.[10]

3 · Look at Topology

Before tuning, look at the "floor plan": how many buildings this machine has, and which CPUs and how much memory each building holds. The most common command is numactl -H. Below is a dual-socket x86 machine (m7i.48xlarge, 192 vCPU, 768 GiB) output:

$ numactl -H
available: 2 nodes (0-1)
node 0 cpus: 0-47 96-143
node 0 size: 386420 MB
node 0 free: 12034 MB
node 1 cpus: 48-95 144-191
node 1 size: 386547 MB
node distances:
node   0   1
  0:  10  21
  1:  21  10

Line by line:

  • available: 2 nodes: two buildings.
  • node 0 cpus: 0-47 96-143: Why two ranges? Because Intel has Hyper-Threading enabled (SMT, where one physical core runs two threads at once), so each physical core has two vCPUs. 0-47 are the first threads of the 48 physical cores, and 96-143 are the second threads of the same cores. Graviton has no Hyper-Threading, so on Graviton you'll see one continuous range of numbers.
  • node distances:10 means local,21 means one hop away. The ratio is about 2.1, which matches the latency table in the previous section.

Where do numbers like node 0 and node 1 come from

It's not Linux guessing on its own; it's What the firmware tells it. At boot, the BIOS / UEFI places two tables in ACPI:

  • SRAT(System Resource Affinity Table): lists which CPUs and which ranges of physical memory belong to the same proximity domain.
  • SLIT(System Locality Information Table): lists the relative distances between these domains, i.e. the 10 / 21 table above.

At boot, Linux reads these two tables, maps each proximity domain to a node number starting from 0, and then in /sys/devices/system/node/ build under it node0, node1……[11]

Arm servers (including Graviton) use ACPI too. In a VM, these two tables are generated by the hypervisor (Nitro on EC2), while on metal instances they come directly from the motherboard firmware. To see the raw records, you can use dmesg | grep -i -E "srat|numa".

A node is a logical concept and doesn't necessarily map to a socket
A single CPU can also be split into several nodes: AMD EPYC can set NPS (Nodes Per Socket) = 1 / 2 / 4 in BIOS; Intel has SNC (Sub-NUMA Clustering). Conversely, CXL-expanded memory often shows up as a CPU-less node. So always go by numactl -H output as the source of truth; don't just count CPUs.

See other details

$ lscpu | grep NUMA
NUMA node(s):        2
NUMA node0 CPU(s):   0-47,96-143
NUMA node1 CPU(s):   48-95,144-191

$ cat /sys/devices/system/node/node0/meminfo | head -3
Node 0 MemTotal:  395694568 kB
Node 0 MemFree:    12323400 kB
Node 0 MemUsed:   383371168 kB

# NICs and NVMe devices also belong to a node (-1 means a single-node machine)
$ cat /sys/class/net/eth0/device/numa_node

You can also see exactly where a process's memory lands:

$ numastat -p $(pgrep -f postgres | head -1)

One level deeper, look at which policy each virtual memory region uses:

$ cat /proc/12345/numa_maps | head -3
7f8a1c000000 default anon=524288 dirty=524288 N0=262144 N1=262144
7f8a5c000000 bind:0  anon=131072 dirty=131072 N0=131072

N0=… N1=… is the actual number of pages of this memory region on each node.default, bind:0 is the "strategy" covered in the next section.

4 · Where to put memory:mempolicy

Let's start with the most important default behavior:first-touch. The program malloc a large chunk of memory, the kernel doesn't actually allocate it right away; it waits until some thread First write a page (the smallest unit of memory allocation, usually 4 KB) is that page actually allocated, and it is placed on the node that thread was on at the time.

It's like parking: spaces aren't assigned in advance. Whoever drives in first parks in the lot closest to them. Many problems later on happen because "the first one to drive in" isn't the one who actually uses that memory most afterward.

If you don't want the default behavior, you can set a policy (mempolicy) on a process or a memory range. The most commonly used ones in the kernel docs are [1]:

  • MPOL_DEFAULT: not set separately; it inherits the policy from the level above and ultimately falls back to the system default, which is local.
  • MPOL_LOCAL: Place it on the node of the CPU doing the allocation. This is first-touch.
  • MPOL_BIND: Allocate only from the specified set of nodes. If the set has multiple nodes, pick the one closest to the allocating point that has enough free memory. If all are full, you get Fails outright, and won't borrow from elsewhere.
  • MPOL_PREFERRED: prefer allocating from the specified One node allocation; if that fails, try other nodes from nearest to farthest.
  • MPOL_INTERLEAVE: Interleave allocation page by page across the specified nodes. Good for large shared memory regions that "everyone reads", such as database caches.

Newer kernels add two more:MPOL_PREFERRED_MANY(since 5.15, can prefer a set of nodes) and MPOL_WEIGHTED_INTERLEAVE(since 6.9, interleaves pages by weight, often used with CXL memory).

On the command line, this corresponds to numactl 's key parameters [4]:

# Bind both the process and its memory to node 0
numactl --cpunodebind=0 --membind=0 ./server
# Interleave memory across all nodes
numactl --interleave=all ./mysqld
# Prefer node 1, fall back when it's full
numactl --preferred=1 ./batch-job
The sentence people trip over most
The kernel docs say it verbatim: "pages already faulted in ... remain where they were allocated based on the policy at the time." In other words, changing the policy No move memory that has already been allocated, unless you explicitly call mbind() or migrate_pages(). So changing the policy after the service has already warmed up does little; set it at startup.[1]

5 · Interpreting the results numastat counters

Type directly numastat, you'll see a column of counters for each node. Think of it like hotel booking records: you wanted to stay at Hotel A, but A was full, so you were put in Hotel B. In that case, A records a "guest who didn't get in" and B records a "guest who wasn't meant for us."

counters Meaning (man 8 numastat)[5]
numa_hit Meant to land on this node, and it did land on this node.
numa_miss The process wanted another node but ended up on this node.
numa_foreign Meant to go on this node, but ended up on another node.Every miss on one node corresponds to a foreign on another node.
interleave_hit Placed on this node as planned under the interleave policy.
local_node The process runs on this node, and its memory is also allocated on this node.
other_node The process runs on another node, but its memory is allocated on this node.

The most common rule of thumb:node A's numa_miss high, while node B's numa_foreign is also high, it means B has run out of memory, and memory that should have been on B got pushed to A. Next, check which process on B is using the most (numastat -p).

Note that these are all cumulative values since boot. To see what's happening "now", sample twice a few seconds apart and look at the difference.

6 · Automatic migration:Auto-NUMA balancing

Since first-touch often puts pages in the wrong place, can the kernel fix it on its own? Yes, and that's NUMA balancing. It works like a moving company: it watches which building you most often go to for files, then moves the files there. But the "watching" and the "moving" both take effort.

$ cat /proc/sys/kernel/numa_balancing
1

When it's on, the kernel periodically "unmaps" some pages temporarily. The next time a thread accesses one of these pages, it triggers a lightweight page fault (the CPU notifies the kernel when a page isn't in the mapping). The kernel uses this to record "who accessed it and from which node," and moves the page to the accessor's node if needed.

The kernel docs put it bluntly: these unmappings and faults add overhead, in the hope of earning it back through better locality, but Profit not guaranteed; if the workload is already manually pinned to a node, turn it off.[2]

To tell whether it's helping, look at /proc/vmstat:

numa_pte_updates          ← pages sampled
numa_hint_faults          ← hint faults triggered
numa_hint_faults_local    ← of which, accesses where the accessor was already local
numa_pages_migrated       ← pages actually migrated
pgmigrate_success/fail    ← migration succeeded / failed

Healthy signals:numa_hint_faults_local / numa_hint_faults This ratio rises over time, showing that the kernel is "aligning" threads with memory.

Unhealthy signs:This ratio stays low, while numa_pages_migrated keeps rising, pages are just being moved back and forth for nothing. In that case, use sysctl kernel.numa_balancing=0 Turn it off and pin manually instead.

7 · Real failure: MySQL "swap insanity"

Here's a classic case. In 2010, Jeremy Cole (then at Twitter) wrote a postmortem [3]:

  • Machine: dual-socket,64 GB memory, i.e. about 32 GB per node.
  • MySQL's InnoDB buffer pool set to 48 GB, actually using about 51 GB.
  • Strange: the machine clearly still has free memory, yet MySQL keeps swapping (moving memory pages to disk and back), and performance is poor.

He uses /proc/<pid>/numa_maps A quick look shows the buffer pool has, on node 0, 30.45 GB, on node 1 there's only 20.75 GB. node 0 is almost entirely taken up by a single MySQL process.

Why does this happen? It's the first-touch behavior described earlier: most of the buffer pool was first written by threads running on node 0, so it all landed on node 0. On top of that, when local node memory ran short, the kernel at the time tended to reclaim local memory first (including swapping) rather than immediately allocating on a remote node.

The fix is just one line, in mysqld_safe add:

cmd="/usr/bin/numactl --interleave all $cmd"

After that, the buffer pool on the two nodes 26.00 GB each, and swap disappeared.

MySQL 5.7 later simply added innodb_numa_interleave parameters to do this [9]; another related switch vm.zone_reclaim_mode, and for databases the common advice is to set it to 0 (the default since Linux 3.16).

8 · Common Performance pitfalls

The pitfalls below almost all share the same root cause:The thread that first writes the memory and the threads that later use it most are not on the same node.

JVM

By default the JVM is not NUMA-aware: which node each page of the heap (the memory holding Java objects) lands on depends on who writes to it first, so the distribution is often very uneven.

Open -XX:+UseNUMA, the JVM has each thread allocate new objects on its local node first. Parallel GC has long supported this; G1 has supported it since JDK 14 [8]. Another option is to run one JVM per node:numactl --cpunodebind=N --membind=N java ….

PostgreSQL / MySQL

Database cache (shared_buffers, InnoDB buffer pool) is a large chunk of memory shared by all connections, and each page lands on the node of the process that first writes to it. Query-handling processes can be scheduled on any node, so cross-node reads are very common.

Two ways to fix it: at startup, add numactl --interleave=all, so the cache is spread evenly across both nodes; or bind the entire database to one node and leave the other node for the system and other services.

Python multiprocessing

Pool(64) It forks a batch of workers, and the scheduler spreads them across nodes; but large arrays built in the parent process before the fork live only on the parent's node. As a result, half the workers keep reading remote memory.

Fix: bind both the parent process and the workers to the same node, or have each worker load its own data after fork.

Docker container

Not set --cpuset-cpus and --cpuset-mems containers, every scheduling decision is a gamble. Setting only CPU without memory only counts as Half fixed: the CPU is on node 0, but the memory may be entirely on node 1.

NIC queues (ENA)

The NIC also belongs to a node. ENA has multiple TX/RX queues, and each queue has an interrupt (an MSI-X IRQ, the signal the NIC uses to "wake up" a CPU). Packets are processed on whichever CPU the interrupt is pinned to.

If your application runs on node 1 but the receive interrupts land on node 0, every packet has to cross the socket interconnect. AWS's ENA best practices recommend placing the application and the queues it uses on the same node [7].

# See which CPU each ENA interrupt lands on, then compare with /sys/devices/system/node/nodeX/cpulist
grep ena /proc/interrupts | awk '{print $1, $NF}'
# Which node the NIC itself is on
cat /sys/class/net/eth0/device/numa_node

On large multi-node instance types, it also depends on the ENA driver's rx_queue#_lpc_wrong_numa counters (ethtool -S eth0); if it's non-zero, the receive buffers are on the wrong node [7].

9 · EC2 Topology quick reference: the M8 and M9 generations

On EC2 you don't see the motherboard directly, but it's still there. How many NUMA nodes an instance has depends on how many CPUs sit behind it and how each CPU is partitioned internally.

Many people assume the rule is simple: "it only becomes two nodes when one CPU can't fit everything." That's true for m8g and m8a. But the newer m8i and m9g are different,A single CPU can also contain several nodes. First, the big picture:

m8g (Graviton4): the simplest

Each Graviton4 has 96 cores and no hyperthreading, so one vCPU is one physical core. Each CPU has 12 DDR5 channels.

  • medium to 24xlarge(up to 96 vCPU): uses only one CPU,1 node.
  • 48xlarge / metal-48xl(192 vCPU, 768 GiB): two CPUs,2 nodes, each node has about 372 GiB, and the node distance is 10 / 20.

AWS's Graviton documentation is also clear on this: the number of NUMA nodes is 1, and only 48xlarge has 2.[12]

m8a (AMD EPYC Turin): same as m8g

Each EPYC 9R45 has 96 cores and no hyperthreading. AMD can use NPS to split one CPU into multiple nodes, but AWS uses NPS1 on m8a, meaning one node per CPU.

  • medium to 24xlarge:1 node.
  • 48xlarge / metal-48xl: two CPUs,2 nodes. m8a has no 32xlarge.

m8i (Intel Xeon 6, Granite Rapids): one CPU split into three

This is the generation where it's easiest to trip up. Each CPU has 96 physical cores (192 vCPUs with Hyper-Threading), but AWS enabled Intel's SNC(Sub-NUMA Clustering), which splits one CPU into 3 nodes, 32 cores per node.[13]

Think of it this way: it's still the same building, but the building is split into three zones, each with its own records room. Getting files from another zone is quicker than going to another building, but still slower than your own zone.

  • large to 16xlarge(up to 64 vCPU, i.e. 32 cores): fits exactly into one domain,1 node. m8i-flex tops out at 16xlarge, so flex is always single-node.
  • 24xlarge(96 vCPU, 48 cores) and 32xlarge(128 vCPU, 64 cores): still on one CPU, but already spans regions,2 nodes.
  • 48xlarge / metal-48xl(192 vCPU): one whole CPU,3 nodes.
  • 96xlarge / metal-96xl(384 vCPU, 1536 GiB): two CPUs,6 nodes.

Supporting evidence: when you customize the core count via CPU options, m8i.48xlarge only allows multiples of 3, and 96xlarge only multiples of 6, matching exactly 3 and 6 nodes.

m9g (Graviton5): one chip, two halves

Graviton5 packs 192 cores into a single package, with no hyperthreading and 2 × 96 MB of L3 cache. Judging from the measured topology, the chip looks like Two 96-core halves joined together; each half is one node.[12][14]

  • medium to 12xlarge(up to 48 vCPU):1 node.
  • 16xlarge(64 vCPU):2 nodes, each side with 32 cores and about 124 GiB. AWS's Graviton docs also state that "16xlarge and 48xlarge have 2 nodes".
  • 24xlarge(96 vCPU): back to 1 node, exactly filling one half.
  • 48xlarge / metal-48xl(192 vCPU, 768 GiB): only one chip, but 2 nodes, distance 10 / 20.

In other words, On m9g, the intuition that "larger instances have more nodes" doesn't hold. The 16xlarge is smaller than the 24xlarge, yet it spans two nodes. If your service is latency-sensitive and needs around 64 cores, m9g.24xlarge is actually less hassle than 16xlarge.

10 · Kubernetes 's NUMA trio

In Kubernetes, the kubelet handles this. Think of it like arranging seats at a banquet: the CPU, memory, NIC, or GPU a Pod uses should ideally be seated at Same hall, not split across two buildings. Inside kubelet there are three components working together [6]:

  • CPU Manager(static policy): for Pods with Guaranteed QoS (requests equal to limits) and integer CPU requests Exclusive a group of cores.
  • Memory Manager(Static policy): reserves memory for these Pods on the specified NUMA node.
  • Topology Manager: Coordinates by combining the hints from the first two and the device plugins, deciding "which hall to sit in". It has four policies:
    • none: the default; alignment is ignored.
    • best-effort: Align if possible; if not, still let the Pod start.
    • restricted: Align if possible; if not,Reject this Pod.
    • single-numa-node: CPU, memory, and devices must all be on the same node, or the request is rejected.

Key prerequisite:Exclusive CPUs and reserved memory only apply to Guaranteed QoS + integer CPUs Pods. Ordinary Burstable / BestEffort Pods don't get any of this and still get scattered across nodes.

11 · When No need to worry about it

  • Single-node instances: For example m8g / m8a 's 24xlarge and below, m8i 's 16xlarge and below, m9g 's 12xlarge and below (plus m9g.24xlarge).numactl -H shows only one node, this article doesn't apply to you.
  • Stateless, horizontally scalable services: Running several small instances or small Pods is simpler than using one huge instance.
  • The bottleneck isn't memory at all: What actually bottlenecks you is disk, network, or a downstream API.
To be honest:If your stack isn't NUMA-friendly (a JVM with default settings, single-process Python, untuned Postgres),don't buy large dual-socket instances. Two m8g.24xlarge behind an ALB, usually versus a single m8g.48xlarge Easier to use, and less hassle to operate.

NUMA isn't black magic — it's just the physical shape of the machine you're renting.First use numactl -H Check the topology once, then pick one of three approaches ("pin, interleave, or leave it alone") and you never have to think about it again.
