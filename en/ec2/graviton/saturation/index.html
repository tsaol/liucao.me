Detecting on ARM Resource saturation

99% is the same as x86, thanks to a good Linux abstraction layer. The 1% is armv8_pmuv3 PMU, alternatives to Intel-only tools, and ENA's 6 unique "throttling" counters.

1 · 99% Same as x86

The Linux kernel absorbs most of the differences between chips./proc, /sys, top, htop, iostat, vmstat, sar, dmesg, journalctl——works exactly the same way on Graviton.Your x86 muscle memory still applies.The next page covers only the 1% that needs attention.

2 · 1% different——PMU / tool replacements

perf Hardware event name

PMU is armv8_pmuv3, not Intel Skylake/Icelake.perf stat / perf top / perf record Both work, but the raw event names differ.

$ perf list | head -20
  branch-instructions OR branches         [Hardware event]
  branch-misses                           [Hardware event]
  cache-misses                            [Hardware event]
  cache-references                        [Hardware event]
  cpu-cycles OR cycles                    [Hardware event]
  instructions                            [Hardware event]
  ...
  armv8_pmuv3/cpu_cycles/                 [Kernel PMU event]
  armv8_pmuv3/inst_retired/               [Kernel PMU event]
  armv8_pmuv3/l1d_cache_refill/           [Kernel PMU event]
  armv8_pmuv3/mem_access/                 [Kernel PMU event]

Common events (cycles, instructions, cache-misses) is the same symbol on both platforms. Intel-specific ones (uops_retired, mem_load_uops_retired) simply don't exist.

PMU works on small sizes too, but with fewer counters — verified by testing(2026-09-22, AL2023 kernel 6.12, Tokyo):
  • m8g.medium(1 vCPU):3 hardware counters, exposing 43 armv8_pmuv3 Event
  • m8g.24xlarge(96 vCPU):6 hardware counters, exposing 68 events
  • Observing more events than there are counters at once → the kernel automatically event multiplexing(perf output will show (50.09%) and similar sampling shares), the values are still statistically valid but less precise
  • ARM SPE(Statistical Profiling Extension, per-instruction sampling) and arm_cmn mesh events Not exposed on either size— requires metal Specs
  • Basic cycles + instructions IPC measured on the smallest m8g.medium works right away on
So for IPC checks any size works; only deep top-down microarchitecture analysis (many events at once, SPE, mesh bandwidth) requires a large size or metal.[6]

Intel-only tools (not available on Graviton)

  • Intel VTune
  • Intel PCM (pcm.x, pcm-memory.x)
  • Intel MLC (Memory Latency Checker)

Equivalents on ARM

  • perf——use daily
  • topdown-tool——ARM's official top-down microarchitecture analysis (pip install topdown-tool)
  • ARM Streamline——commercial ARM GUI
  • hotspot(KDAB) — an open-source GUI that reads ARM perf The data is fine

numactl, taskset, chrt, ionice, nice Both ends are identical.

SPE and CMN mesh events are not visible on either size and require metal specs.

# 1. Launch an m8g.* instance, AL2023 arm64 (kernel 6.12)
# 2. Install perf
sudo dnf install -y perf

# 3. Check how many hardware counters the PMU has

ls /sys/devices/arm_spe_0/ 2>/dev/null && echo "SPE present" || echo "SPE not present"
ls /sys/devices/ | grep -i arm_cmn || echo "arm_cmn not present"

Practical rules (verified by testing):
  • Only does Interpreting IPC(two events: cycles + instructions) — the smallest m8g.medium is also enough.
  • Do Top-down analysis with 4–6 events(front-end stall, back-end stall, L1/L2 miss, branch miss) —24xlarge and above No multiplexing, optimal.
  • Do Per-instruction sampling (SPE)or DRAM/mesh bandwidth——must *.metal specs.

How to interpret these results

1️⃣ "Counters are hidden on small sizes" is wrong, but "small sizes are weaker" is right.
What I originally said was "on small sizes the PMU is hidden by the hypervisor,perf stat can't get complete data". Testing shows a more precise way to put it is:PMU always exposed(on AL2023 kernel 6.12,m8g.medium 's dmesg also shows it armv8_pmuv3_0 PMU driver, 3 counters available), just Only 3 hardware counters, while m8g.24xlarge has 6. The number of hardware counters = the number of physical registers fixed inside the ARM Neoverse V2 core, not something cut down by the virtualization layer.

2️⃣ Multiplexing is "time-sharing", not "dropping data".
When you ask the kernel to monitor 10 events at once but there are only 3 physical counters, the kernel takes those 10 events and Take turns squeezed into those 3 slots, switching every few milliseconds. The fraction of time each event is enabled is the number on the right (30.05%). perf uses this ratio to extrapolate "what the count would be if it were enabled for the whole window" — so The numbers are still credible estimates, but variance increases, and short spikes (bursts of tens of microseconds) may fall right between sampling windows.

3️⃣ IPC is the single most useful metric on Graviton.
Run on two machines dd if=/dev/urandom of=/dev/null, and IPC is 4.05— that's a high number for Neoverse V2's 6-wide front end. Conversely, if your service's IPC < 1.0, it's bottlenecked on memory latency (cache misses, TLB misses, cross-NUMA memory access), and adding CPU cores or moving to a bigger machine No Making it faster requires fixing the algorithm or changing data structures. This diagnosis applies in m8g.medium can be done on it — no need to wait for a big machine.

4️⃣ What the absence of SPE and arm_cmn means.
SPE (Statistical Profiling Extension)is a feature introduced in ARM v8.2: unlike traditional perf record only captures the IP at sample points; SPE can For every sampled instruction Records memory addresses, cache hits/misses, and latency. Essentially an ARM version of Intel PEBS.arm_cmn is the Coherent Mesh Network event, which shows DRAM bandwidth utilization across the whole die. Neither is available inside a VM, because the information they expose could leak details about neighboring workloads on the physical host. AWS only provides them on *.metal launched on. For this kind of deep analysis, rent one hour of m8g.metal-24xl(about $5.7/hr in Tokyo) is enough.

5️⃣ Direct guidance for readers of this page.
If you just want to know whether a service is "actually busy" vs "just waiting on IO / memory", any M8g size will do. Run one line perf stat -a -e cycles,instructions -- sleep 10 you get IPC.Don't give up on profiling small machines just because of the assumption that "only big machines have a PMU".You only need at least 24xlarge those 6 counters; you only need metal for instruction-level attribution or measuring memory bandwidth.

6️⃣ How current these results are.
Tested on 2026-09-22, AL2023 kernel 6.12. The number of hardware counters is a fixed property of the Neoverse V2 chip and won't change; whether SPE / CMN are exposed is up to AWS and could in theory be relaxed in future kernel/hypervisor versions — so this page may become outdated over time. Before making important decisions, reproduce the steps above yourself.

3 · Load average The truth

Linux load average No Pure CPU load. Since Matthias Urlichs's 1993 patch, it has also counted Runnable threads and those in TASK_UNINTERRUPTIBLE(D-state tasks, usually waiting on disk IO or certain kernel locks). Urlichs's original words: "the load average goes down when you replace your fast swap disk with a slow swap disk" — this counterintuitive behavior was his motivation for the change. Other Unixes still use a CPU-only version.[3]

The three numbers (1 / 5 / 15 min) are Exponentially decaying moving average— watch the trend, not the absolute value, and always compare it against the vCPU count.

A more accurate saturation signal:

  • runqlat(bcc) — run-queue wait time histogram.
  • vmstat 1 's r column: number of runnable processes.
  • offcputime Press TASK_UNINTERRUPTIBLE Filter—find the threads that are actually stuck in D state.

4 · CPU utilization ≠ busy

%CPU = "non-idle time". It Not telling you whether those cycles are executing instructions or waiting on DRAM. DRAM latency hasn't kept up with core-count growth over the years, so many hot loops, even if %CPU 100% too Waiting on memory.[4]

Use perf stat Volume IPC (Instructions Per Cycle):

sudo perf stat -a -- sleep 10
# Focus on the insns per cycle line

Empirical criterion: IPC < 1.0 → memory-bound; IPC > 1.0 → compute-bound. 0.78 IPC on a 4-wide core means instruction throughput is only ~19.5%.

5 · CPU Saturation criteria

Load Average

Use top, uptime, or cat /proc/loadavg.

load > 0.8 × vCPU = warning
load > vCPU and trending up = saturated

Per-Core distribution

mpstat -P ALL 1——%usr, %sys, %iowait, %soft,%st(steal).

Single core %usr+%sys sustained > 90 = single-thread bottleneck
%st > 5 = neighbors stealing CPU (rare on M8g, common on t-series)

The softirq trap

a core %soft = 50%+, other cores idle — all ENA interrupts are pinned to one core. Check cat /proc/interrupts, then use irqbalance + IRQBALANCE_BANNED_CPUS or manually taskset points.

Seen on small instances (2 vCPU), a single softirq core becomes the throughput bottleneck.[7]

6 · Memory Saturation criteria

free -h

See available, not free——page cache counts toward available.

available < 10% = warning

vmstat 1

si / so column: swap in/out. Cloud machines usually have no swap, so non-zero = real trouble.

si/so consistently > 0 = already swapping

OOM tracing

dmesg -T | grep -i "killed process"
journalctl -k | grep -iE "oom|out of memory"

AL2023 has no swap by default → straight to OOM kill, no slowdown first

cgroup pressure

cat /sys/fs/cgroup/system.slice/<svc>.service/memory.pressure

a service's full avg10 > 5% = that service is thrashing memory itself

/proc/meminfo What's worth looking at in it:MemAvailable(the kernel promises it can be reclaimed),Cached, Slab(broken down into SReclaimable vs SUnreclaim), Shmem, PageTables(spikes with many processes + many maps).

7 · Disk Saturation criteria

iostat -xz 1 key columns

column Meaning Threshold
%utilbusy time Close to 100% (false positives on NVMe multi-queue; see below)
await Average latency per IO (ms)gp3 > 10 · io2 > 2
r/s + w/sIOPS Compare volume limits
rareq-sz + wareq-sz Average request size (KB)Small + high IOPS = random
EBS has two ceilings:
1️⃣ Per-volume: gp3 defaults to 3000 IOPS / 125 MB/s; buy more as needed.
2️⃣ Per-instance: e.g. m8g.large All EBS volumes combined max out at ~10K IOPS / ~700 MB/s.
Requires CloudWatch VolumeThroughputPercentage, EBSIOBalance%, EBSByteBalance% together.

A more reliable signal:PSI——cat /proc/pressure/io. On multi-queue NVMe, %util can give false positives (multiple queues processing in parallel look 100% busy even though the application isn't waiting); PSI is a kernel-level ledger, so it's always accurate.[5]

8 · Network Saturation & ENA counters explained

Basic tools (sar -n DEV 1, ip -s link, nstat -a) is the same as on x86.The one key command——ENA driver throttling counters:

ethtool -S ens5 | grep -E 'exceeded|conntrack|linklocal'

Six *_allowance_exceeded(verbatim from the AWS UserGuide)[8]

counters Meaning (original AWS wording)
bw_in_allowance_exceeded Inbound bandwidth exceeds the instance limit, so packets are queued or dropped
bw_out_allowance_exceeded Egress bandwidth exceeds the instance limit
pps_allowance_exceeded Bidirectional PPS exceeds the instance limit — small instances hit this first
conntrack_allowance_exceeded Connection tracking entries exceed the limit,New connections fail to establish——silent killer
linklocal_allowance_exceeded PPS to link-local services (DNS / IMDS / Time Sync) exceeds the limit — SDK metadata retry loop
conntrack_allowance_available How many more connections can be established (Nitro-only, requires driver ≥ 2.8.1)

ENA throttling on m8g (approximate)

Specs Baseline bandwidth PPS limit conntrack limit
m8g.medium~0.4 Gbps~100K~35K
m8g.large~0.75 Gbps~200K~55K
m8g.xlarge~1.5 Gbps~400K~130K
m8g.2xlarge~3 Gbps~800K~260K
m8g.4xlarge~6 Gbps~1.6M~450K

ENA queue affinity

ENA uses one MSI-X IRQ per RX/TX queue, named <iface>-Tx-Rx-<idx>. AWS ENA best practices recommend: pin the app to Same vCPU as the IRQ; place RPS cores on Same NUMA node;Don't disable it irqbalance, using IRQBALANCE_BANNED_CPUS to make it skip your NAPI cores.[7]

On multi-NUMA Graviton, the default affinity spreads IRQs across both nodes — pages get allocated on the wrong node. See rx_queue#_lpc_wrong_numa counters; if non-zero, pin manually.

9 · PSI(Pressure Stall Information)

Linux 4.20+ and CONFIG_PSI=y. Three files:/proc/pressure/{cpu,memory,io}. Two lines per resource:

  • some——"share of time in which at least some tasks are stalled on a given resource"
  • full——"share of time in which all non-idle tasks are stalled ... simultaneously"—during full, the CPU sits idle; sustained full = thrashing.

Fields:avg10 / avg60 / avg300(percentage) + total(cumulative microseconds).total Catches short spikes that averages hide. CPU only has some— system-wide full CPU is meaningless.[5]

Threshold reference

Values Judgment
some avg10 > 10%Warning
full avg10 > 5%Urgent—the business really is waiting

Trigger (user-space poll)

Write "some 150000 1000000" to a file, then poll() / epoll(). The window must be 500 ms–10 s, and non-privileged users can only use multiples of 2 s. Facebook's oomd relies on PSI triggers for early OOM.[5]

cgroup v2 vs global PSI:Once cgroup v2 is mounted, each cgroup has its own memory.pressure(v2 by default on AL2023; on AL2 add systemd.unified_cgroup_hierarchy=1). System-wide PSI looks calm, but one container is already thrashing — only cgroup PSI shows it. K8s VPA, systemd-oomd, and Facebook oomd all rely on this to decide what to kill.

10 · eBPF Five-piece toolkit (works out of the box on Graviton)

AL2023 runs kernel 6.x,bcc-tools and bpftrace Install and use, no ARM-specific flags:

sudo dnf install -y bcc-tools bpftrace
Tools Question answered
runqlat Scheduler run-queue wait latency histogram — the real CPU saturation signal
biolatency Block device IO latency distribution (-D split by disk)
offcputime Thread stacks while off-CPU — pair with D-state in load avg
tcpretrans 5-tuple + socket state for TCP retransmits
cachestat Page cache hit / miss ratio — early memory pressure

Gregg's rule:Daemons use BCC; one-liners use bpftrace.[9]

11 · Decision tree——where to look when a service is slow

service slow?
│
├── top: load avg > vCPU?
│    ├── YES → mpstat -P ALL 1
│    │        ├── one core high %soft → ENA IRQ affinity
│    │        └── all cores high %usr → perf top → app hotspot
│    └── NO  → keep going
│
├── free -h: available < 20%?
│    ├── YES → dmesg -T | grep -i killed → OOM history
│    │        vmstat 1 → si/so non-zero → swap thrash (rare in the cloud)
│    └── NO  → continue
│
├── iostat -xz 1: await > 10ms or PSI io some avg10 > 10%?
│    ├── YES → CloudWatch EBSByteBalance% / VolumeThroughputPercentage
│    │        → hitting volume or instance EBS limit
│    └── NO  → continue
│
├── ethtool -S ens5 | grep exceeded counters increasing?
│    ├── bw_*_allowance      → upsize or reduce traffic
│    ├── pps_allowance       → batch, send fewer small packets
│    ├── conntrack_allowance → keep-alive, reuse connections
│    └── linklocal_allowance → cache IMDS token, back off
│
└── nothing busy but still slow → offcputime -K -p <pid> 10
                                → where exactly are threads stuck
