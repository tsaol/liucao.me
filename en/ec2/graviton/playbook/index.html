On-Call Playbook

1 · Netflix 60 seconds checklist

SSH in and run these 10 commands in order, ~1 second each. After 60 seconds you'll know whether it's CPU / memory / disk / network / none of these.[6]

#CommandWhat it tells you
1uptimeLoad average 1/5/15: rising / steady / spiking
2dmesg -T | tail -20Kernel messages: OOM, TCP drops, NIC resets, EBS nvme errors
3vmstat 1 5r=run queue,si/so=swap,us/sy/wa/st
4mpstat -P ALL 1 5Per-vCPU imbalance — one hot core = single-thread bottleneck
5pidstat 1 5Rolling per-process CPU delta, better than top for catching spikes
6iostat -xz 1 5Per-device %util / await / queue — this is where EBS latency lives
7free -mfree / buff / cache — look at available Don't look at free
8sar -n DEV 1 5Per-NIC packets / bytes vs. instance limits
9sar -n TCP,ETCP 1 5active/s, retrans/s— retransmits > 0.1% means network pain
10topSanity check — sort by RES to find leaks

3 · Google SRE's Key principles

The 5 most valuable pieces of advice from the SRE Book's "Effective Troubleshooting" chapter:[3]

  • Fly the airplane first——stop the bleeding first (drain, roll back, shift traffic), then find the root cause. Don't debug while users are bleeding.
  • Horses, not zebras——the latest deploy / config push is always suspect #1. Mark deploy timestamps on the dashboard.
  • Simplify, reduce, bisect——inject known inputs between layers and bisect.
  • AssumingLikelihood × costsorting and verification; every step is written to a shared doc with a timestamp.
  • A sudden latency jump usually means "the type of work changed," not "the traffic changed"— see War Story #1.

4 · 10 Failure signature

01ALB returns 502 but the target shows "healthy"

Diagnosis: the app is stuck in IO wait, but the health check still passes because it's lightweight.

iostat -xz 1 · CloudWatch VolumeQueueLength · jstack/py-spy to find blocked threads

Fix: Pull the slow endpoint out of the traffic pool, dump the thread stacks, and restart first.

02Container gets OOMKilled, but the liveness probe passes

Diagnosis:dmesg | grep "killed process" + kubectl describe pod Reason=OOMKilled. The liveness probe only checks HTTP, not RSS.

kubectl top pod --containers · add resource limits + memory alert

03linklocal_allowance_exceeded > 0

Diagnosis: the SDK is hammering IMDS (169.254.169.254) with retries — usually a misattached IAM role or IMDSv1 hammering.

ethtool -S eth0 | grep linklocal · aws sts get-caller-identity to verify the role

Fix: Have AWS SDK v2 cache the IMDSv2 token; switch to IMDSv2; set the hop limit to 2 so Pods can reach it too.

04conntrack_allowance_exceeded Climbing

Diagnosis: A flood of short-lived connections, or the client not using keep-alive. This isENA instance-levellimit, not the kernel nf_conntrack.

ethtool -S eth0 | grep conntrack

Fix: Enable HTTP keep-alive on the client; upsize (bigger instance = bigger conntrack allowance); route heavy egress traffic through a NAT Gateway rather than a NAT instance.

05EBS io2 latency spikes (during cross-AZ replication)

Diagnosis: the volume is rebuilding after an AZ event;VolumeTotalWriteTime / VolumeWriteOps > 10 ms.

Three CloudWatch EBS metrics charts aligned with the AZ event timeline

Fix: Wait for the rebuild (time uncertain), or use Multi-AZ replication to another volume and fail over to it.

06Can't connect via SSM Session Manager

Diagnosis: the user-data script is still running, and cloud-init is blocking ssm-agent from starting.

Get console-output from the EC2 console · /var/log/cloud-init-output.log

Fix: run long user-data tasks in the background or move them to a startup service.

07Instance keeps rebooting (boot loop)

Diagnosis: cloud-init failed — attach a rescue volume and check /var/log/cloud-init.log.

aws ec2 get-console-output --instance-id i-...

08CPU steal on M8g %st > 5

Diagnosis: M8g isn't burstable, so high %st usually means contention from bare-metal neighbors — rare; open an AWS support ticket. On t3/t4g, %st isNormal— the credit balance is used up.

mpstat 1 · aws cloudwatch get-metric CPUCreditBalance (t family only)

09sar -n TCP retrans/s > 1% but no packet loss on the host

Diagnosis: the Security Group / NACL conntrack table is full, or the path MTU doesn't match.

tracepath <dest> · check SG entries + jumbo frame compatibility

10Small instances pps_allowance_exceeded Starts to emerge

Diagnosis: Small-packet floods (DNS queries, cache misses, heartbeats) hit the PPS limit before bandwidth fills up.

ethtool -S eth0 | grep pps

Fix: Upsize; batch UDP; for DNS floods, add client-side caching.

5 · Coredump on Amazon Linux 2023

AL2023 uses systemd-coredump, not a traditional core file:

sudo dnf install -y systemd-coredump
sudo sysctl -w kernel.core_pattern='|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h'
sudo systemctl edit user.slice   # DefaultLimitCORE=infinity
ulimit -c unlimited              # Applies to every shell

coredumpctl list                 # Inventory
coredumpctl info <PID>            # Metadata + backtrace
coredumpctl gdb  <PID>            # Attach gdb directly
coredumpctl dump <PID> -o /tmp/core.$PID

Dump location:/var/lib/systemd/coredump/. To use traditional core files:kernel.core_pattern=/var/coredumps/core.%e.%p.%t + fs.suid_dumpable=2.

6 · Rescue before reboot——preserve the evidence

D=/tmp/oncall-$(hostname)-$(date +%s); mkdir -p $D
dmesg -T                       > $D/dmesg.txt
journalctl -b --no-pager       > $D/journal.txt
ps auxfww                      > $D/ps.txt
top -bn1                       > $D/top.txt
ss -tanp                       > $D/ss.txt
ss -s                          > $D/ss-summary.txt
iostat -xz 1 3                 > $D/iostat.txt
vmstat 1 3                     > $D/vmstat.txt
mpstat -P ALL 1 3              > $D/mpstat.txt
free -m                        > $D/free.txt
ethtool -S eth0                > $D/ena.txt
cp -a /proc/loadavg /proc/meminfo /proc/net /proc/pressure $D/ 2>/dev/null
cp -a /var/log/messages /var/log/cloud-init*.log /var/log/dmesg $D/ 2>/dev/null
tar czf /root/oncall-snapshot.tgz $D
aws s3 cp /root/oncall-snapshot.tgz s3://$FORENSICS_BUCKET/

7 · SRE war stories— there's something to learn from all of them

#1 · App Engine "suddenly 10x slower, with no changes"[3]——a security scanner wrote thousands of rows into an allowlist table; every request then did a linear scan of the in-memory cache.No new RPCs, no traffic spikes, just that "the shape of the work changed." Lesson: looking at RPC distributions alone isn't enough; you need in-process profiles.

#2 · GKE CreateCluster 6h40m major outage[4]——a corrupted image on DockerHub blocked all new cluster creation. 41 people were online in IRC, but it took ~2 hours to designate an IC (Incident Commander). Lesson:Declare an IC early; pre-build generic stopgaps like "evict bad images from the mirror".

#3 · Belgian data center struck by lightning (2015)[4]——four lightning strikes in two minutes, damaged UPS batteries, GCE disk errors.Data loss rate for running VMs: 0.000001%——because the IC was designated immediately and every role had been rehearsed.

9 · UpgradeTrigger conditions

  • Page DBA——replication lag > 30s, more deadlocks,pg_stat_activity All idle in transaction.
  • Failover— node unreachable > 2 min, disk read errors in dmesg,EBSByteBalance% Still 0 after tuning.
  • Scale out——all cores > 80% sustained for 10 min and The ALB queue is still growing.Don't scale up when you suspect a memory leak— that's just feeding the leak.
  • Roll back——the p99 regression timeline lines up with a deploy. Roll back first, then find the root cause.
