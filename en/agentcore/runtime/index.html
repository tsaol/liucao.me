AgentCore Runtime:microVM or Instances

Runtime is the core of AgentCore: it puts an agent in a container, with an isolated environment for each session. In 2026 it gained a second compute option, Instances, which runs on EC2 in your own account. This page covers how to choose between the two, how they're billed, and where the security boundaries are, plus my measured data and the pitfalls I hit.

1 · What it is 2 · Two compute types 3 · microVM V2 4 · Instances 5 · Pricing 6 · Evaluation 7 · Measured results 8 · How to choose 9 · Getting started
Accessed 2026-11-25.Prices and limits follow the official AWS documentation. The "measured" figures come from a multi-agent coding task I ran in the Tokyo Region (ap-northeast-1): in the same run, half the agents ran on microVMs and half on Instances. The sample is small (3 agents per side), so the numbers only show orders of magnitude.
Start here: in three sentences
  1. Runtime has two compute options:microVM (serverless, pay-per-use, starts in seconds) and Instances (runs on EC2 in your own account, billed per instance plus a 12% management fee).
  2. Default to microVM.Only if you need x86 / GPU, sessions longer than 8 hours, or root access(installing system software, running containers, locking down the network) should you use Instances.
  3. When using Instances, be sure to remember:Stopping a session doesn't shut down the machine. The instance is released only when you delete the session; and these instances Not shown in the EC2 instance list by default.

1 · What Runtime is

Key points Key points of this section
  • You provide a container image (or code package), and it handles running, isolation, and scaling;One session = one isolated environment, using the one you pass in: runtimeSessionId to tell them apart.Docs · Instances
  • The container only needs to do two things:GET /ping returns the health status,POST /invocations handling requests, all in Port 8080.Docs · Getting started with Instances

Invoking it is simple:InvokeAgentRuntime with the runtime ARN, a session ID, and the request payload. The first time a new session ID is used, Runtime prepares a new environment for it; after that, all requests with the same session ID go to the same environment,Sessions can't see each other. When the session ends, use StopRuntimeSession.

Any framework and any model: Strands, LangGraph, CrewAI, LlamaIndex, Google ADK, OpenAI Agents SDK, and models inside or outside Bedrock. MCP and A2A protocols are also supported.Docs · What is

3 · microVM: the new generation (V2)

Key points Key points of this section
  • A dedicated Firecracker microVM for each session,Hardware-level isolation.What’s New 11-12
  • V2 first snapshots the initialized agent,Each new session is restored from a snapshot: a 2 GB image starts in under 2 seconds at P75 (V1 takes 29.7 seconds).What’s New 11-12
  • Memory is allocated on demand and reclaimed when unused,For multi-turn conversational agents, billed memory is up to 68% lower; scales to 0 when idle.What’s New 11-12
  • Default version: starting 2026-11-12, new runtimes in 19 Regions, including Tokyo, default to V2; for existing runtimes you have to change the platformVersion Change to V2.What’s New 11-12
  • Good fit for: the official examples are compiling large codebases, driving browsers, and loading local models within a session.What’s New 11-12
  • Limits: the container has no permission to change network rules,Can't block the instance metadata address Measured. So give the execution role least privilege: code running inside has a chance to obtain this role's temporary credentials.

4 · Instances: running on EC2 in your own account

Key points Key points of this section
  • Three things:capacity provider(the EC2 "template": OS, instance type, subnet, disk, role) → runtime(what to run) → Session(one EC2 instance).Docs · Instances
  • Agents on the same instance Shared file system, so they can read each other's credentials; use separate sessions if you need isolation.Docs · Security
  • In privileged mode the agent runs as root, but Dedicated to this one session, so the isolation boundary stays the same.Docs · Security

runtime Container image, execution role, protocol; optional privileged mode

Session = one EC2 instance Boots on first invocation; up to 14 days; data disk can be retained

IAM roles to prepare

  • Infrastructure role (operator role): AgentCore assumes it to launch, tag, configure network interfaces for, and shut down instances. You can attach the managed policy directly: BedrockAgentCoreRuntimeInstancesOperatorRolePolicy, trust bedrock-agentcore.amazonaws.com.Docs · Security
  • Instance profile: attached to the EC2 instance, used only to ship system logs,Gives the agent code no permissions. If you don't pass it, AgentCore uses a default instance role it creates itself.Managed policy documentation
  • Execution role: the permissions your agent code gets, same as with microVM.

Privileged mode and nested virtualization

  • Privileged mode(2026-11-18): agents can install system software and run nested containers, for example spinning up their own Postgres and Redis for integration tests. Set it in the runtime's capacityProviderConfiguration.operatingSystemConfiguration.linux.privilegeMode.What’s New 11-18
  • Nested virtualization(2026-11-19): sessions can use KVM to run virtual machines and emulators (such as the Android emulator),Intel instance types only(C7i, C8i, M7i, M8i, R7i, R8i).What’s New 11-19

5 · Pricing

Key points Key points of this section
  • microVM V2:$0.1276 / vCPU·hour + $0.0169 / GB·hour, billed per second for actual usage; CPU isn't charged during I/O time spent waiting for model responses.Pricing page
  • Instances:EC2 billed per instance from start to stop (minimum about 1 minute) + a management fee of 12% of the On-Demand price(7.8% for G-series GPUs); Savings Plans and Reserved Instances can cover the EC2 portion, but not the management fee.Pricing page

Official example: a 3-hour session on c7g.2xlarge (8 vCPU / 16 GB, US East) = 3 × $0.289 = $0.867, plus a 12% management fee = $0.104,Total about $0.97.Pricing page

Rough estimate for my workload (order of magnitude)

  • Agents spend most of their time waiting for model responses, so the CPU sits idle. microVM charges only for actual usage,Running an agent for 40 minutes costs a few cents.
  • Instances bills for the whole machine from boot (including about 1.5 minutes of startup): m7g.2xlarge on-demand in Tokyo is $0.4216/hour, or $0.472/hour with the 12% management fee, One agent running for 40 minutes costs about $0.33.AWS Price List
  • 128 agents running concurrently for 40 minutes:microVM about $4.7, Instances (m7g.2xlarge) about $42; with m8g.large it's about $11.5, and with m7g.large about $10.5. By comparison, model costs for a task this size run to several hundred dollars. There's a calculator in the next section.

Gotchas I hit that the official docs don't make clear

  1. Stopping a session doesn't shut down the machine.StopRuntimeSession only stopped the agent; the EC2 instance stayed up and kept billing, and the "shut down after 10 minutes idle" setting didn't trigger either (my 6 instances ran an extra 35–80 minutes, costing about $2.66 more). You need to call DeleteCapacityProviderSession(the parameters are the capacity provider ID and the session ID) before the instance is released.Measured
  2. These instances are hidden by default.The docs mention in passing: managed instances don't appear in EC2 console or API listings by default. To list them with the CLI, add --include-managed-resources, otherwise you'll think "everything is shut down". The instance tags include bedrock-agentcore:runtime-session-id, which you can use to reconcile costs.Docs · Instances
  3. In the default STANDARD mode, the container runs as uid 0, but its privileges are stripped: you can't chown, switch to another user, or change iptables. If your entrypoint needs to drop privileges to run the agent, you have to use privileged mode.Measured
  4. Request content is sent in chunks(Transfer-Encoding: chunked, no Content-Length). HTTP servers that only accept Content-Length will read an empty body. microVMs don't have this problem.Measured
  5. The list of allowed instance types is not a priority order.I listed m8g.2xlarge first and m7g.2xlarge second, but every instance launched was m7g.Measured
  6. Privileged mode requires a newer SDK version.CLI 2.36.47 doesn't have this parameter yet; boto3 1.44.11 does.Measured

8 · How to choose

Key points Key points of this section
  • microVM by default: fast startup, pay per use, almost no operations work.
  • Use Instances in these cases: you need x86 or GPUs, sessions longer than 8 hours, root (to install system software, run containers, or lock down the network), or Savings Plans or Capacity Reservations.
  • The two can be mixed: within one system, put agents that set the overall pace (such as planners or team leads) on microVM for speed; put agents that need a special environment or stricter network control on Instances.
  • On Instances, don't put mutually untrusted agents in the same session to save money: they can read each other's credentials.
  • Check quotas before going big: Instances uses one EC2 instance per session, so 100 concurrent sessions means 100 instances; check your account's EC2 vCPU quota first.
  • Be sure to reconcile your bill: after the task ends, query by session ID tag for any instances still running (remember to add --include-managed-resources).

9 · Getting started: Instances in four steps

Key points Key points of this section
  • Prerequisite: something that implements /ping and /invocations container image (pushed to ECR), a private subnet and a security group.
# 1. Infrastructure role: trust bedrock-agentcore.amazonaws.com, attach the managed policy
#    BedrockAgentCoreRuntimeInstancesOperatorRolePolicy (create it in IAM)

# 2. capacity provider: OS, instance type, network, idle time before shutdown
aws bedrock-agentcore-control create-capacity-provider --name my_cp \
  --permissions-configuration capacityProviderOperatorRoleArn=<infrastructure role ARN> \
  --compute-configuration '{"ec2Configuration": {
     "launchTemplateSource": {"launchParameters": {"operatingSystem": "LINUX_ARM64",
        "instanceRequirements": {"allowedInstanceTypes": ["m8g.large"]}}},
     "vpcConfiguration": {"subnets": ["<subnet>"], "securityGroups": ["<security group>"]},
     "lifecycleConfiguration": {"idleInstanceTimeout": 600, "maxLifetime": 28800}}}'

# 3. runtime: image, execution role, attach to the capacity provider (privileged mode needs a newer boto3)
aws bedrock-agentcore-control create-agent-runtime --agent-runtime-name my_agent \
  --agent-runtime-artifact containerConfiguration={containerUri=<ECR image>} \
  --role-arn <execution role ARN> \
  --capacity-provider-configuration capacityProviderArn=<capacity provider ARN>

# 4. When done: stop first, then delete the session (if you only stop without deleting, the EC2 instance keeps running)
aws bedrock-agentcore stop-runtime-session --agent-runtime-arn <runtime ARN> --runtime-session-id <session ID>
aws bedrock-agentcore delete-capacity-provider-session --capacity-provider-id <ID> --session-id <session ID>

Note: when writing ARNs in zsh,"$ACCOUNT:role/..." in :r gets swallowed as a variable modifier, and the ARN becomes ...ole/.... It must be written as ${ACCOUNT}.Measured
