CHAPTER 01

What the case study does: an AI researcher iterates on a recommendation model

Why it's harder than autoresearch

Challenge ①
Large exploration space
Recommendation models have evolved from DCN and DLRM to HSTU and RankMixer, and the architectures are still changing. Data processing, feature engineering, and training objectives all affect results too. This is a systems engineering problem, not a matter of tuning a few hyperparameters.
Challenge ②
Training is expensive
In a real business, training a recommendation model once takes tens to hundreds of GPU hours; autoresearch trains for only 5 minutes each time.Every failed attempt costs more, and you get fewer attempts.

Experiment setup: the target model is RankMixer(using the open-source UniRank implementation), and the dataset is public KuaiRand; the main task is click-prediction AUC, plus 5 auxiliary tasks (follow, like, comment, share, long view), and improvements must not noticeably hurt the auxiliary tasks.

Start with a general-purpose agent as the baseline: it can make changes, but doesn't get far

Given a 200 GPU·h budget and no human intervention, a strong general-purpose agent improved AUC by 1.33pp — showing it's feasible; when humans provide validated ideas, it always writes the code correctly — Writing code isn't the bottleneck. But looking at its trajectory, there are three problems:

Problem ①
76% of the gains in the first 30% of the time
The remaining 70% of the time is largely wasted, making sustained improvement hard.
Problem ②
86% of the budget bet on one direction
The direction worked at first, but marginal gains soon shrank while it kept making changes — exploration converged too early.
Problem ③
Read only a little of 50 papers
Paper-reading calls make up only 2.7% of all tool calls, and all of them happen in the first 9 hours. Not drawing on external knowledge is one of the main reasons the search direction converges.
In one sentence: Writing the code is doable; the hard part is Decides where to explore next.

CHAPTER 02

Their harness: wide exploration + deep pursuit

Wide-and-Deep exploration strategy

Wide branch · cast a wide net
Propose at least 8 ideas at a time and screen them cheaply
  • Always starts from The initial baseline version Start
  • Fewer training steps to save cost
  • Goal: quickly determine which ideas are viable and provide data for later decisions
The agent decides each round on its own
Go Wide or Deep
It considers four things: conclusions from the last few retrospectives · whether a new best model has appeared · the diversity of past exploration · when Wide was last chosen
No hard rules or thresholds
Deep branch · push deeper
One proposal at a time, pushing up the current best
  • Could build on Any historical version Keep iterating
  • Could take the ideas that worked across several versions and merge them
  • Versions that didn't improve the score can still serve as "negative evidence"

How it differs from common practice: many systems automatically pick "which version to start the next round from" using rules like scores or UCT; here that decision is left to the agent.

Three agents divide the work, with a fresh set each round

1
Proposal Agent

Decides between Wide and Deep, draws ideas from papers, code, datasets, and past results, and writes proposals (Wide ≥ 8, Deep 1)

2
Developing Agent

Write code according to the proposal; first design the "attribution chain" and the variables to observe, run static checks and code review, then start training. Multiple proposals are handled in parallel

3
Evaluation Agent

Produces objective conclusions (per-task AUC, whether the attribution chain holds) and subjective conclusions (whether this direction is worth continuing)

Three types of context
Prompts · handoff docs · long-term memory
Agents within a round pass information through simple handoff docs; cross-round information goes into long-term memory, and the next round's agents don't inherit the previous round's context. Each agent gets context on a “minimum necessary” basis.
Four types of long-term memory
Papers · Knowledge base · Leaderboard · Code
A paper library; a knowledge base built from each round's experiment findings; a leaderboard of the current best models; and the codebase itself, managed with git, also serves as memory.

Evaluation: more than just AUC

Level What to look at How to judge
Black box Main-task ΔAUC; auxiliary-task ΔAUC must not drop noticeably Computed by code rules
Glass box Exploration diversity, number of papers read, number of dataset analyses Diversity is classified by an LLM; counts are computed by code
Subjective Whether the Wide / Deep choice and "should we continue this direction" match human judgment Human judgment
Why it matters: Looking only at the final score, you can't tell whether the "AI researcher" is actually doing good research. Tracking diversity and how often it reads papers can reveal early on that it's stuck in a rabbit hole.

Results

Efficiency
40% of the budget, 41% more improvement
AUC +1.88pp, about 41% higher than the baseline's +1.33pp, using only 80 GPU·h.
Diversity
The best model used 4 categories of improvement ideas
The baseline changes almost only one direction; here both the Wide and Deep branches are explored thoroughly, continually producing new best models.
Research behavior
Read papers 50 times, analyzed data 162 times
Read 25 different papers in total; exploration was noticeably broader.

Training runs on g6.2xlarge instances, and the base model comes from Amazon Bedrock (the blog doesn't name the exact model). The numbers come from the blog and reflect a single run, with no variance reported across repeated runs.

CHAPTER 05

Could this become our case study?

Where it qualifies

Real, and from AWS
Customer scenario + AWS AI Lab co-development + Bedrock / EC2
More convincing than companies' own claims in papers, and the most direct story to tell customers.
Reproducible
Both the data and the model are public
The KuaiRand dataset and the RankMixer implementation in UniRank are both open source (Apache-2.0), so you can reproduce the baseline in your own account.
A complete story
It has a baseline, problem diagnosis, design, and results
First prove it “can make changes”, then find out why it “doesn't get far”, adjust the harness accordingly, and finally get more improvement with less budget.
Gets to the heart of it
The hard part is "where to explore"
This matches the main thread of our talk: writing code isn't hard; exploration and validation are.

What's still missing (to fill in before turning this into a case study)

  • Public data, not Xiaohongshu production data: There is still a gap between results on KuaiRand and online gains in real production; we need to confirm whether there was online validation.
  • A single experiment, no variance: The gap between +1.88pp and +1.33pp needs more runs and a look at variance before it can be claimed firmly.
  • Base model not specified: The blog doesn't say which model on Bedrock was used or what the token cost was.
  • harness code not released: The Wide-and-Deep prompts, plus the three agents' tools and handoff formats, are key to reproducing it.
  • Cost breakdown: Beyond GPU·h, what is the inference cost of the agent itself?

CHAPTER 06

Hands-on reproduction: get it running with the public code first

Publicly available

Target model
UniRank · RankMixer
salmon1802/UniRank, Apache-2.0. 15 ranking models, including RankMixer; includes preprocessing, config, and evaluation code.
Dataset
KuaiRand
Short-video recommendation data, about 320 million interactions, 6 tasks; UniRank includes ready-made preprocessing scripts.
Compute and model
EC2 g6 + Amazon Bedrock
The blog trains on g6.2xlarge; the agent's base model runs on Bedrock.

Four suggested steps

1
Get the baseline running

Train RankMixer on KuaiRand, get AUC for the main and auxiliary tasks, and confirm how many GPU·h a single training run takes

2
General-purpose agent baseline

Give the general-purpose agent the same budget and let it make changes on its own; record the gain curve, direction distribution, and number of papers read

3
Add Wide-and-Deep

Split into Proposal / Developing / Evaluation, with long-term memory and Wide / Deep branches

4
Controlled evaluation

Compare ΔAUC at the same budget; run several times to check variance; add glass-box metrics

Step 3 can directly reuse what we already have: Play's evolution engine (ShinkaEvolve) can serve as a "select parents by score" control group, and Argus's planner / worker / scoring structure can handle the division of labor among the three agents.
