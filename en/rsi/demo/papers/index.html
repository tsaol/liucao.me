AlphaEvolve: a Gemini-powered coding agent for algorithm design

AlphaEvolve: A Gemini-powered coding agent for designing advanced algorithms
DeepMind team · 2024-05
The granddaddy of them all: uses an evaluation cascade + Gemini dual-model evolution to directly rewrite Google's production code
This is the founding work of the field of "real algorithm discovery with LLMs". Before it, FunSearch could only evolve a single function. AlphaEvolve was the first to scale evolutionary code search to an entire codebase, and it went straight into high-stakes production systems like Google Borg, Gemini training kernels, and TPU Verilog. It's closed-source, with Early Access available only to a small number of academic users. The Shinka and DGM you can pip install from GitHub today are essentially open-source descendants of this paper's ideas. Understanding AlphaEvolve = understanding the original design behind every code evolution framework today.
3 core insights
1 Evaluation Cascade: tiered evaluation; if a tier fails, it stops there
The core mechanism of AlphaEvolve isn't the LLM, it's the evaluator. After each candidate program is generated, evaluation runs in multiple stages: first the cheapest stage (e.g., unit tests, small inputs, sanity checks that finish in seconds); only candidates that pass this stage are allowed into the next one (longer benchmarks, held-out datasets, perturbed inputs); and only the final stage is the truly expensive full evaluation (e.g., a complete correctness proof, large-scale performance tests). This way, the vast majority of obviously wrong or obviously mediocre candidates are killed at the first stage, and precious evaluation compute is spent only on patches with real potential. This is the "evaluation cascade" — it compresses the most expensive step in evolutionary search from "fully evaluate every candidate" into a "pyramid funnel," and it's the key to scaling the whole pipeline to tens of thousands of samples.
2 Taking matrix multiplication back from Strassen: 4×4 complex matrices in 48 multiplications
In 1969, Strassen's algorithm multiplied 4×4 matrices using 49 scalar multiplications. 56 years later, AlphaEvolve found a new algorithm using 48 multiplications for 4×4 complex matrices, the first improvement on this case since Strassen. This is no toy: the same system sped up a key matmul kernel in Gemini training by 23%, cutting overall Gemini training time by 1%. It sped up the FlashAttention kernel by up to 32.5%. It also proposed a Verilog rewrite of a highly optimized TPU arithmetic circuit, which passed correctness verification and has been integrated into the next-generation TPU. A scheduling heuristic that has run on Borg for over a year recovers an average of 0.7% of Google's global compute, saving the equivalent of building a new data center each year. On about 50 open math problems, it matched SOTA on 75% and set new records on 20%, including a new lower bound of 593 outer spheres for the kissing number in 11 dimensions.
3 Gemini Flash casts a wide net + Gemini Pro digs deep: two-model ensemble
AlphaEvolve doesn't bet on a single model. Gemini Flash is cheap and fast and handles "breadth" — producing dozens to hundreds of ideas per round for large-scale exploration; Gemini Pro is expensive, slow, and deep, and handles "depth" — making more insightful rewrites along the promising directions Flash finds. In between, a prompt sampler picks parents from the programs database (archive) to assemble prompts, the LLM outputs candidate patches, the evaluator cascade scores them, and those that pass enter the archive to become parents for the next round — a very clean evolutionary loop. The biggest difference from FunSearch: FunSearch can only evolve a single Python function, while AlphaEvolve can evolve an entire codebase, with changes across files and modules. That's also why it can directly modify Verilog, CUDA, and the Borg scheduler.
The best line
AlphaEvolve continuously recovers, on average, 0.7% of Google's worldwide compute resources.
AlphaEvolve has been running continuously on Borg for over a year, recovering an average of 0.7% of Google's worldwide compute.
How it relates to this demo
In today's demo, the composite score formula in evaluate.py, `combined = 0.7·public + 0.2·heldout + 0.1·perturbed`, and the cascade gate that scores the H tier only when the E score >= 0.7 and the M score >= 0.5, are copied straight from AlphaEvolve's evaluation cascade — cheap before expensive, local before global, and nothing advances to the next tier without passing the previous one. You can think of today's demo as taking AlphaEvolve's evaluation philosophy from "a closed-source system inside Google" to an open-source setup that runs on "a single GPU + Bedrock Claude."
What AlphaEvolve teaches you isn't "use an LLM to write code" but "use an evaluation cascade to lock the LLM in a cage, so it only gets credit when it can actually prove itself" — that's the real secret to making code evolution work.

Darwin Gödel Machine: open-ended evolution of self-improving agents

Darwin Gödel Machine: Open-Ended Evolution of Self-Improving Agents
Jenny Zhang, Shengran Hu, Cong Lu, Robert Lange, Jeff Clune (UBC + Sakana AI + Vector Institute)
Let the agent modify its own code, use benchmarks instead of formal proofs, and use an evolutionary archive instead of single-line optimization
Looking back from 2026, DGM is the starting point of the self-improving agent lineage. It was the first to bring Schmidhuber's 2003 Gödel machine out of theory and into something you can actually run, replacing the impossible requirement of "proving every change is a net gain" with "run SWE-bench and check the score." More importantly, it brought the archive idea from open-endedness research into agent self-improvement: instead of greedily pushing the best solution forward, it keeps an entire evolutionary tree, failed branches included. Today, Sakana's ShinkaEvolve and the various self-evolving harnesses all trace their lineage back to it.
3 core insights
1 From formal proofs to empirical validation
Schmidhuber's Gödel machine requires an agent to prove that a change is a "net gain" before each self-modification — theoretically elegant but impossible in practice, because most meaningful changes can't be formally proven. DGM takes a pragmatic approach: replace "proof" with "run the benchmark." Each new agent version runs on SWE-bench or Polyglot, and the score decides. This step looks simple, but it's the key to making self-improvement actually work — it turns a math problem into an engineering problem. The cost is losing theoretical guarantees; the payoff is a system that actually runs. This pragmatic shift largely set the technical direction for every self-improving agent from 2025 onward.
2 Archive-based open-endedness: keep failed branches
This is DGM's most counterintuitive and most important design choice. Traditional optimization discards low-scoring branches and keeps only the best. DGM does the opposite: it maintains an archive that keeps every agent from every generation, including those that look like failures at the time. The next generation isn't picked from the best. Instead, a parent is sampled "interestingly" from the archive, and the foundation model generates a new variant from it. This forms a constantly branching tree that explores many paths in parallel. Why do it this way? In open-ended search, today's failure is often the stepping stone to tomorrow's breakthrough. An intermediate form may not be useful on its own, but one more step on top of it can open a new dimension. The idea comes directly from Jeff Clune's group and its years of open-endedness research (the Quality-Diversity and MAP-Elites line of work).
3 Compounding at the meta level: better tools → better ability to improve
DGM doesn't modify the model weights; it modifies the agent's own codebase: tool definitions, prompts, context management, and review workflows. This creates a recursive effect: the agent improves its own code editing tool, and the next-generation agent uses that better tool to modify itself, and does it better. The concrete evolution examples in the paper are telling: DGM spontaneously added patch validation, chunked handling of long contexts, and a peer-review mechanism (one agent generates a patch, another reviews it). SWE-bench went from 20.0% to 50.0%, Polyglot from 14.2% to 30.7%, significantly outperforming baselines without self-improvement or without open-ended exploration. This isn't simple scaling; it's compounding at the meta level.
The best line
"The DGM is a significant step toward self-improving AI, capable of gathering its own stepping stones along paths that unfold into endless innovation." — DGM is a key step toward self-improving AI: it picks up its own stepping stones along the way, forging a path toward endless innovation.
How it relates to this demo
The ShinkaEvolve used in this demo (arXiv:2509.19349, 2025-09) is the productized follow-up Robert Lange built at Sakana AI. A co-author of DGM became the first author of ShinkaEvolve. The technical lineage is clear: DGM proved that the "archive + LLM mutation + benchmark validation" approach works, but its sample efficiency is poor (it needs thousands of samples). ShinkaEvolve adds parent sampling, novelty rejection, and a bandit-based LLM ensemble to the same framework, cutting the sample count to 150 while still reaching SOTA. DGM is the prototype; ShinkaEvolve is the usable tool. Today's harness self-evolution demo essentially runs the paradigm DGM established.
A self-improving agent doesn't need to prove every step is correct. Keep every branch, let the benchmark be the judge, and evolution will find its own way.

Meta-Harness: End-to-End Optimization of Model Harnesses

Meta-Harness: End-to-End Optimization of Model Harnesses
Yoonho Lee, Roshen Nair, Qizheng Zhang, Omar Khattab, Chelsea Finn, et al. (Stanford / KRAFTON / MIT)
Hand the entire harness to a coding agent to search, using the file system as the feedback channel.
In 2026 everyone is talking about harness engineering: the same model can show a 6x performance gap with a different harness. Previous text optimizers all compress feedback. OPRO only sees a scalar, GEPA stuffs in a summary, and TextGrad only looks at the current artifact. This paper raises the ceiling to 10M tokens/iter, three orders of magnitude more than existing methods. It shows that letting a coding agent grep and cat historical traces on its own beats manual prompt tuning, and beats any structured search loop.
3 core insights
1 The feedback channel shifts from the prompt to the file system
Earlier text optimizers share a common flaw: they compress the history into a one-line summary and stuff it into the prompt. OPRO uses 0.002 MTok/iter, GEPA 0.008, TTT-Discover 0.026, in millions of tokens. Meta-Harness uses a full 10.0 MTok/iter, a gap of three orders of magnitude. The proposer doesn't consume it all at once; it works like a real programmer: each round it greps a median of 82 files (41% historical harness source code, 40% execution traces), spanning 20+ historical candidates. This is non-Markovian: it doesn't just look at the previous version, but freely digs into early failure cases to reason. The implicit premise of this design: only in early 2026 did coding agents become just strong enough to decide for themselves what to look at.
2 The trace is what matters; the summary actually hurts
The paper ran a very clean ablation: scores-only (34.6 median / 41.3 best), scores+summary (34.9 / 38.7), and full Meta-Harness (50.0 / 56.7). The best score of the summary version was even 2.6 points lower than scores-only. The authors' interpretation is blunt: LLM-generated summaries crush the diagnostic information. A harness bug may only blow up dozens of steps later, and you need to see the full trajectory to trace it back to the original faulty retrieval logic. It's like debugging a distributed system: error codes alone are useless, and you have to read the full log. This insight also explains why earlier approaches like GEPA and TextGrad hit a ceiling.
3 A less-is-more outer loop
Unlike carefully engineered evolutionary frameworks such as AlphaEvolve and AFlow, Meta-Harness's outer loop is extremely minimal: no parent selection rule, no archive structure, just a Pareto frontier. In the authors' words, it's deliberately minimal—all decisions about diagnosis and modification are handed to the coding agent. The entire history lives in the file system, and the agent looks up whatever it wants. The philosophy is very Bitter Lesson: once the search space is accessible, a general-purpose agent beats hand-designed heuristics. On text classification, Meta-Harness matches in 4 rounds what OpenEvolve and TTT-Discover reach in 60, a 10× speedup. The algorithm isn't clever; it just doesn't overcomplicate things.
4 A harness that transfers across models is the real asset
The IMO math experiment is especially convincing. A retrieval harness found via search with GPT-OSS-20B was then tested on GPT-5.4-nano, GPT-5.4-mini, Gemini-3.1-Flash-Lite, and Gemini-3-Flash. All five models improved, by +4.7 on average. By comparison, dense retrieval drops 0.5 points on GPT-5.4-mini and 0.9 points on Gem-3-Flash. This shows that the search didn't find black magic overfitted to one model, but a readable, transferable strategy. The authors stress this in the Discussion as well: overfitting in code space is inspectable. If-chains and hardcoded mappings are obvious at a glance, which makes it far friendlier than overfitting in weight space. On TerminalBench-2, the Haiku 4.5 version climbed to 37.6% to take first place, and the Opus 4.6 version took second with 76.4%. An open-source automatic search beat a leaderboard full of hand-tuned entries.
The best line
"The proposer reads a median of 82 files per iteration ... referencing over 20 prior candidates per step. A single evaluation can produce up to 10,000,000 tokens of diagnostic information, roughly three orders of magnitude beyond the largest feedback budgets used in prior text optimization settings." — Each iteration reads a median of 82 files across 20+ prior candidates; a single evaluation can produce 10 million tokens of diagnostic information, three orders of magnitude more than any previous text optimizer.
How it relates to this demo
Your 8-chapter talk is about harness self-evolution — letting the harness iterate on itself. Meta-Harness is the formalized academic version of this idea: it elevates the harness to a first-class optimization target, uses a coding agent as the sole proposer, and uses the file system as a lossless memory channel. The self-rewriting patterns in your demo map to the three lines of pseudocode in the paper's Algorithm 1. Especially worth noting: the proposer used in the paper is Claude Code + Opus 4.6, essentially the same stack you run live. Read this after watching your demo, and it feels like academia has simply put its stamp on your engineering intuition.
Harnesses are no longer hand-tuned. Lay the full traces out on the file system and let a coding agent grep the history itself. That's the new auto-ML.

ShinkaEvolve: Towards Open-Ended and Sample-Efficient Program Evolution

ShinkaEvolve: Towards Open-Ended And Sample-Efficient Program Evolution
Robert Tjarko Lange, Yuki Imajuku, Edoardo Cetin (Sakana AI)
The world's only open-source, ready-to-use LLM program evolution framework (Shinka = Japanese for "evolution", 進化)
This is the engine running directly behind today's harness self-evolution demo, and currently the only code-evolution framework you can actually pip install and use. Closed-source heavyweight tools like AlphaEvolve often need thousands of samples to converge. ShinkaEvolve reaches SOTA on circle packing in just 150 samples. Its author, Robert Lange, is also the first author of the Darwin Gödel Machine (DGM), so ShinkaEvolve is essentially the productized version of DGM: the same team turned a research prototype into an engineering framework. It comes from Sakana AI, the Tokyo lab founded by Transformer paper author Llion Jones.
3 core insights
1 Parent Sampling: not pure elitism, but an explore/exploit balance
Traditional evolutionary code search either mutates only from the best individual each generation (getting stuck in local optima) or samples uniformly (wasting budget). ShinkaEvolve organizes the population into multiple islands, each offering three parent selection strategies — weighted, power_law, and beam_search — plus migration between islands and dynamic island spawning. On the archive side, elite_selection_ratio 0.3 and crowding-based replacement maintain population diversity. The core idea: give each mutation some probability of exploring "suboptimal but high-potential" branches, so the whole search doesn't collapse around the current leader. This is the first pillar behind reaching SOTA with just 150 samples.
2 Code Novelty Rejection Sampling: deduplicate right after the LLM generates code
LLMs used as mutation operators have a known flaw: given the same prompt, they keep producing patches with very similar structure, and out of thousands of samples, perhaps fewer than one in ten carry real information. After the LLM generates a candidate, ShinkaEvolve first computes an embedding (text-embedding-3-small by default) for a similarity check. Anything too close to existing code in the archive is rejected outright and never enters the evaluation queue. Evaluation is the most expensive step (it runs real code on real benchmarks), so a novelty gate before evaluation pushes sample efficiency up another notch. This is the key change that turns evolutionary search from "brute-force sampling" into "informative sampling".
3 Bandit-based LLM Ensemble: letting models bid for the next mutation
By default, the framework connects to multiple models at once, including gpt-5-mini, gemini-3-flash, gemini-3.1-pro, and gpt-5.4. Each mutation isn't tied to one fixed model. Instead, a multi-armed bandit dynamically adjusts weights based on history: "whose patches are more likely to be selected into the archive." Cheap small models cast a wide net for exploration, while expensive flagship models are only called when the bandit thinks it's worth it. Combined with max_api_costs as a hard USD budget cap, the whole run spends money where it counts. This is also why it can claim to be cost-efficient and to democratize open-ended discovery.
The best line
ShinkaEvolve discovers a new state-of-the-art circle packing solution using only 150 samples.
How it relates to this demo
Today's demo runs this framework directly. We applied three monkey-patches to make it work with Claude Opus 4.7 / 4.8 on Bedrock: first, we swapped its built-in OpenAI / Gemini client for a Bedrock client; second, we changed the pricing lookup from models.dev to a local table (Opus isn't on models.dev); third, we disabled the headless CLI path. The rest of the aggregate_fn contract (combined_score + public + private + text_feedback) is untouched — and that contract happens to leave room for our "three-tier evaluation": the fast, medium, and final evals are all written into aggregate_fn.
If you want to run code evolution today, you don't need to build it yourself — pip install shinka-evolve, define aggregate_fn clearly, and it has already handled sample efficiency for you.

ShinkaEvolve source walkthrough · from API to hook points

ShinkaEvolve · Source Code Walkthrough
1,398 stars · 280 forks · Apache 2.0
All hook points are module-level functions or dataclass fields, so monkey-patching is easier than forking
After reading the paper you know what it can do, but what really makes ShinkaEvolve easy to use is its boundary design: the LLM provider is a module-level query_* function, pricing is a CSV, and the eval contract is a metrics dict. These three boundaries let the whole framework be switched to Bedrock and plugged into any custom task, without forking. This walkthrough starts from the shinka/ directory and goes all the way to the aggregate_fn contract and the exact line numbers of the three monkey-patches, so you can modify it with confidence.
3 core insights
1 1 · Directory structure at a glance · what shinka/core, llm, database, edit, launch, and pricing each do
Top-level shinka/ has only 8 submodules that actually run. `shinka/core/` is the main evolution loop (async_runner.py at 6254 lines + EvolutionConfig in config.py + run_shinka_eval in wrap_eval.py + novelty_judge.py + sampler.py). `shinka/database/` is SQLite-backed archive/island storage (DatabaseConfig + Program dataclass in dbase.py + 5 ParentSamplingStrategy types in parents.py). `shinka/llm/` is the provider-agnostic dispatch layer (LLMClient / AsyncLLMClient in llm.py + sample_model_kwargs in kwargs.py + the bandit in prioritization.py). `shinka/llm/providers/` has one file per cloud vendor (anthropic.py / openai.py / gemini.py / deepseek.py / local_openai.py / headless.py) plus a pricing.csv. `shinka/edit/` handles applying LLM-generated patches (apply_diff.py does search-and-replace, apply_full.py overwrites the whole file, marker_validation.py checks EVOLVE-BLOCK-START/END markers). `shinka/launch/` is just a subprocess wrapper (LocalJobConfig / SlurmJobConfig / JobScheduler) that runs evaluate.py as a child process. `shinka/pricing/` is the runtime pricing catalog, loaded by merging the CSV + models.dev API.
2 2 · Main evolution loop · The three concurrent tasks of ShinkaEvolveRunner.run() → _run_async()
The entry point is `shinka/core/async_runner.py:1002 def run(self)`. The synchronous wrapper directly calls `run_async()` (line 1017) → `_run_async()` (line 1024). The real main loop isn't a for loop but an asyncio.gather over three coroutines: `_job_monitor_task` (line 2037, monitors completion of evaluate.py subprocesses), `_proposal_coordinator_task` (line 2417, decides whether to pull another patch based on pipeline_target and max_evaluation_jobs), and `_meta_summarizer_task` (optional, runs a summary every meta_rec_interval generations). Each propose goes through `_generate_evolved_proposal` (line 2702). It first calls `sample_parent()` on the database (parents.py:89 abstract method), then `PromptSampler.sample()` (core/sampler.py:77) to build the prompt, then `LLMClient.query()` (llm/llm.py:288) to get the patch, then `apply_patch_async` (edit/async_apply.py:67) to write the patch to the file system, and finally `JobScheduler.submit_async` (launch/scheduler.py:288) to run evaluate.py via subprocess. All events go into SQLite (database/dbase.py:434 table-creation SQL).
3 3 · aggregate_fn contract · Where combined_score / public / private / text_feedback / extra_data are consumed
The server side of the contract is `shinka/core/wrap_eval.py:106 run_shinka_eval` (evaluate.py usually calls it directly). Your `aggregate_metrics_fn` is called at line 391 and must return a dict, whose visible keys are destructured at `async_runner.py:1631`: `combined_score` is the primary sort key, `public` holds the metrics the LLM sees in feedback, `private` is a hold-out kept for the leaderboard but not fed to the LLM, `text_feedback` is natural-language feedback (controlled by the `evo_config.use_text_feedback` switch), and `extra_data` is popped out and pickled to disk (wrap_eval.py:462) for plotting. The Program dataclass (database/dbase.py:148) holds these four fields as first-class citizens, and they are written to the SQLite `programs` table (the table DDL at dbase.py:434 already has public_metrics / private_metrics columns). A `combined_score` of NaN/Inf is judged not correct (wrap_eval.py:432). The archive's sort weights in `default_archive_criteria` (defaults.py:49) are simply `{'combined_score': 1.0}`.
4 4 · Parent sampling & novelty rejection · all dataclass fields you can edit directly
Islands / archive / parent strategies are all exposed directly as dataclass fields in `shinka/database/dbase.py:52 DatabaseConfig`: `num_islands` (55), `archive_size` (56), `elite_selection_ratio` (62), `migration_interval / migration_rate / island_elitism` (67-69), `enable_dynamic_islands / stagnation_threshold` (76-77), `parent_selection_strategy = weighted / power_law / beam_search` (84), `exploitation_alpha / exploitation_ratio` (89-90), `archive_selection_strategy = fitness / crowding` (99). No subclassing needed — just pass them when constructing DatabaseConfig. Parent strategy implementations all live in `shinka/database/parents.py`: PowerLawSamplingStrategy (102), WeightedSamplingStrategy (237), BeamSearchSamplingStrategy (436), BestOfNSamplingStrategy (534), SequentialSamplingStrategy (601), all dispatched by `CombinedParentSelector` (669). Novelty rejection is in `shinka/core/novelty_judge.py:60 assess_novelty_with_rejection_sampling`: it first checks embedding cosine similarity (line 89, `database.compute_similarity`) and rejects if it exceeds `code_embed_sim_threshold` (config.py:59, default 0.99); if a novelty LLM is also configured, it runs an additional LLM judgment (line 122), retrying up to `max_novelty_attempts` times (config.py:58, default 3). All reject decisions happen before evaluate, so no evaluation budget is wasted.
5 5 · LLM providers · Bedrock is Anthropic in disguise and shares the same query_anthropic
`shinka/llm/providers/anthropic.py` is only 212 lines: one module-level `query_anthropic` (85) and one `query_anthropic_async` (157). The two functions are nearly identical and differ only by await. Line 108 calls `client.messages.create(...)` directly. The client is passed down from the caller and can be any of `anthropic.Anthropic`, `anthropic.AnthropicBedrock`, `anthropic.AsyncAnthropic` or `anthropic.AsyncAnthropicBedrock` (provider dispatch lives in the `_sync_constructors / _async_constructors` dicts at `shinka/llm/client.py:123-146`). The Bedrock client is built in `_constructor_configuration` at client.py:196, which only accepts AWS credentials from a few fixed environment variables. The IAM instance profile (boto3 default chain) isn't on that allowlist, so on EC2 the precheck has to be bypassed. That's why our demo needs its first monkey-patch. `NO_TEMPERATURE_MODELS` is a module-level set at `shinka/llm/kwargs.py:25`. `sample_model_kwargs` at line 128 checks whether api_model_name is in it and, if it is, omits the `temperature` field. Because it's a module-level set, you can call `.update({...})` on it right after import to add custom model ids.
6 6 · Why pricing.csv is a CSV instead of hardcoded
`shinka/llm/providers/pricing.csv` is only 76 lines, and each row is `model_name,provider,input_price,output_price,input_price_tier2,output_price_tier2,tier_threshold,is_reasoning,think_temp_fixed,requires_reasoning`. It's loaded via `shinka/pricing/normalization.py:284 _load_llm_csv`, which reads it once with stdlib `csv.DictReader`, converts each row into a `ModelPrice` frozen dataclass (catalog.py:47), then merges it into the catalog (catalog.py:82 PricingCatalog index). It's a CSV rather than Python constants because it serves as a fallback and can also be appended to at runtime. At runtime, the catalog first tries to pull the latest prices from the models.dev API (catalog.py:23 MODELS_DEV_URL, 268 `_refresh_online`). If that fails, it falls back to this CSV (normalization.py:37 include_bundled=True). So if your model's price can't be found (e.g., Opus 4.7 isn't listed on models.dev yet), appending one row to this CSV brings cost tracking back to life without changing any Python code. The lookup APIs are `shinka/llm/providers/pricing.py:37 model_exists` and 27 `calculate_cost`, and the latter is called by `anthropic.py:28 get_anthropic_costs`. If the lookup fails, it logs a warning and falls back to 0 without blocking generations that have already completed, as the comments at anthropic.py:29-33 state explicitly.
The best line
Fall back to a zero cost (with a warning) on an unknown model instead of raising, mirroring openai/local so a pricing-catalog miss never aborts a completed generation.
If a model isn't found in the pricing catalog, it's better to log a warning and use 0 cost than to discard an already completed generation because the price lookup failed (shinka/llm/providers/anthropic.py:24-33).
How it relates to this demo
In the demo, three monkey-patches at the top of `evolution/run_evo.py` target exactly these points. (1) `shinka.model_availability._model_env_access_issues` lets Bedrock IAM auth through and bypasses the env var checks around client.py:196. (2) `shinka.llm.kwargs.NO_TEMPERATURE_MODELS` gets our Bedrock inference profile id added to the module-level set at kwargs.py:25 via .update. (3) `shinka.llm.providers.anthropic.query_anthropic / query_anthropic_async` rewrites the legacy `thinking={type: enabled, budget_tokens: N}` generated by kwargs.py:181-192 into Opus 4.7+'s `thinking={type: adaptive}` + `extra_body.output_config.effort` before the call. The `combined_score / public / private / text_feedback` in the dict returned by `evaluate.py` map directly to the four-line destructuring at `async_runner.py:1631`. `public` holds the visible tier E/M/H metrics, which are fed to the next generation's LLM. `private` holds the hold-out scores, which are written only to SQLite and never go into the prompt.
Nearly every extension point in the framework is a module-level function or a dataclass field. No fork needed: just import and monkey-patch, or pass parameters at construction. That's the fundamental reason it's more usable as an engineering framework than comparable research prototypes.
P6 arXiv:2407.12883 ↗ 2024-07

BRIGHT: A Realistic and Challenging Benchmark for Reasoning-Intensive Retrieval

BRIGHT: A Realistic and Challenging Benchmark for Reasoning-Intensive Retrieval
Hongjin Su, Howard Yen, et al. (15 authors; HKU + Princeton + UW + CMU + Google DeepMind)
Upgrade retrieval from "keyword matching" to "reasoning": top embedders collapse across the board
Retrieval benchmarks from the past decade (BEIR, MTEB) are almost entirely information-seeking: queries and documents overlap heavily at the literal level, and BM25 already scores above 50. BRIGHT drags MTEB leaderboard leaders like SFR-Embedding-Mistral from 59.0 nDCG@10 down to 18.3, a full 40-point drop. The model isn't too small; the task itself has changed. The query doesn't contain the answer document's keywords at all, so a reasoning step is needed to connect them. As soon as this benchmark was released, reasoning-heavy retrieval became the newest open problem in IR. Even GPT-4 plus BM25 doesn't handle it well.
3 core insights
1 Insight 1 · What is a reasoning-intensive query
An example from the paper: an economist asks, "Is there another story that rests on the same economic principle as this one?" Nothing in the query tells you which theorem the target document is about; you first have to infer "oh, this is moral hazard" and then go find another moral hazard case. Or a programmer searches with an error message for the corresponding syntax docs, where the error text and the doc body have almost zero literal overlap. BRIGHT systematizes queries like these into 1,384 questions, covering seven StackExchange sub-sites (Biology, Economics, Psychology, Robotics, Earth Science, Stack Overflow, Sustainable Living), plus LeetCode and math Olympiad problems. The common trait: connecting the query to the gold document requires a step of domain reasoning.
2 Insight 2 · Top embedders drop sharply 59.0 → 18.3
SFR-Embedding-Mistral scores nDCG@10 = 59.0 on MTEB but only 18.3 on BRIGHT. The BM25 baseline gets 14.3, and the strongest dense model without augmentation reaches only 24.3 — two-thirds lower than its MTEB score. Even more embarrassing: add GPT-4-generated chain-of-thought reasoning to the query and feed it to BM25, and BM25 overtakes every neural retriever to top the leaderboard, gaining as much as +12.2 nDCG@10. The authors' explanation: dense embedders overfit to short information-seeking queries, so on out-of-distribution, long reasoning-heavy queries they're less flexible than plain BM25. The takeaway: the "semantics" today's embedding models learn is still largely shallow, surface-level semantics.
3 Insight 3 · How these problems are built (Google-mined hard negatives + dual PhD review)
The annotation pipeline is carefully designed: first, high-quality StackExchange posts with an accepted answer or >5 votes and a URL in the answer are selected, and the web pages those URLs point to are split into passages as gold positives. The key is the hard negatives: **annotators search Google for the post title or LLM-extracted keywords and pick pages from the results that are "topically very similar but can't actually answer the question"**. Each question gets up to 5 Google-mined hard negatives, split into several negative passages. Everything is first annotated by a CS student, then independently verified by two domain PhDs, and an item is kept only if both experts agree. This "Google-mined hard negatives" idea is well worth borrowing: no matter how capable machines get, it's hard to automatically generate distractors that are "right on topic but don't solve the problem". Only humans with a search engine can produce them.

How it relates to this demo
The 4 functional-intent questions in Demo Tier H ("a quiet gift for someone taking a long flight → noise-canceling headphones", "charging a 14-inch MacBook on a plane → USB-C 65W") **were directly inspired by BRIGHT's reasoning-intensive design**. The queries contain no keywords like "headphones" or "USB-C". Users describe scenarios and functional needs, which take a layer of reasoning to map to specific products. BRIGHT has already shown that questions like these push all BM25 variants and most embedders below 20 points, and that is exactly the core challenge our demo aims to reproduce and solve for e-commerce retrieval.
The next hard battle in retrieval isn't bigger embeddings but teaching retrievers to reason — BRIGHT puts this problem squarely on the table.
