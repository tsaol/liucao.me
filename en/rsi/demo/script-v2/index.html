S0 45 seconds Opening · Ten customers, seven leave empty-handed
Picture this: a customer searches our app for "mooncakes to give my mother-in-law", and the top result is Men's razor. This isn't a joke · it's where our search agent actually is today — BM25 baseline · hit rate 30% · Out of ten customers, seven leave empty-handed. Next, I won't talk about swapping models · I'll talk about how to make it Not a single weight is touched, it rewrites its own search code by itself.
Weights untouched · what changes is the harness layer around them.
Full-screen search screenshot in the PPT · query "mooncakes to give my mother-in-law" · top result "men's razor" · big red 30% in the bottom-right corner.
S1 5 seconds Click "Start evolution" · Press the button
The fix is right on this page · one button. I'll click it now · 90 seconds then we look at the numbers.
In these 90 seconds · no human writes the code.
Switch to liucao.me/demo/harness/run/ · click "Start Evolution" · the timer starts. (If the network fails, switch to the liucao.me/demo/harness/play/ replay · same narrative.)
S2 15 seconds "Evaluation first" · Read the exam first · then start writing
While it runs · let's see what it does first — Not writing code · grading the exam papers. The Observe node picks a parent from the program library · and takes the questions it got wrong Laid out one by one. The whole method is five verbs: Run · Observe · Propose · Verify · Commit · the engine is ShinkaEvolve, open-sourced by Sakana AI.
First see clearly where you went wrong · then start writing. This order can't be reversed.
Left side of the screen: pipeline diagram · five nodes Run → Observe → Propose → Verify → Commit · Observe highlighted; right side: scrolling list of wrong answers. Corner label: ShinkaEvolve · arXiv:2509.19349.
S3 30 seconds AI reads missed questions · writes new code · It writes code for itself
Next is Propose: Claude Opus 4.8 gets this error report · and starts writing New search code. Notice what it writes — not gradients · not LoRA parameters · but Real Python · Tokenization logic, synonym table, ranking rules · it's all in this diff. "丈母娘" and "岳母" (both mean "mother-in-law") · to BM25 they're two literally unrelated words · now it adds that rule for itself.
Can't change its own brain · so it changes how it works.
Code diff view · red for deletions, green for additions · the synonym-rule section highlighted; author noted in the corner: Claude Opus 4.8.
S4 20 seconds Three eval suites running · Three checkpoints
The new code is written · but it can't just declare itself good · this is where Verify comes in. Three evaluation suites Run concurrently: 31 questions E-commerce search tasks: 8 easy · 8 medium · 15 hardest; plus 5 hold-out problems(which it has never seen); plus 31 typo-variant questions(deliberately misspelled). hold-out prevents memorization · typo prevents brittleness · without both, it doesn't count.
Evolution without evaluation · is just random mutation.
Three progress bars run in parallel · Main 31 problems / Hold-out 5 / Typo 31 · pass rates update live.
S5 5 seconds Gate verdict · Verdict
All three suites done · Commit does only one thing:Verdict. Pass the bar · the new code is promoted into the program library; fail · the code and its error logs are sent back · the next generation keeps fixing it.
The score is the only judge.
A Gate result card pops up on screen · large PASS / FAIL text · with old vs. new score comparison.
S6 20 seconds Gen 1 results · 90 seconds · 30 to 91
Then · the first generation's results come in.30% is the starting point left by BM25 · 91% is the first version of the code written by Opus 4.8 — from pressing the button until now · 90 seconds · The timer can vouch for it.
From 30 to 91 · without a human touching a single line of code.
The big number jumps from 30% to 91% · the timer freezes around 90 seconds; replay mode freezes on the same frame.Pause here for two seconds · let the numbers sink in.
S7 40 seconds Comparison after 3 generations · The gap between the two flat lines
Then all three generations finish · the curve appears · but what I want you to look at Not the Opus line · the flat one next to it. Same eval, same pipeline · swap in Sonnet 4.5 as the author · after three generations it's stuck at 9% —— It's not that the pipeline broke · it can't understand the error report · and can't write code that passes the Gate. Opus 4.8 plateaus at 90% · Sonnet 4.5 plateaus at 9% · The gap between the two plateau lines · is the ceiling of model capability · And our evaluation system can measure where it falls short.
The ceiling is real · the good news is · now we have a ruler.
Comparison chart · x-axis Generation 0–3 · y-axis hit rate; the Opus 4.8 curve goes 30% → 91% → flattens around 90%; the Sonnet 4.5 curve stays flat around 9% · labeled Tier H (hardest 15-question tier).
S8 60 seconds Wrap-up · What the real asset is
Finally, let's do the math: one evolution run like this · API bill $0.10; solving the same problem with fine-tuning · data, compute and staff add up to about $500K —— poor 5 orders of magnitude. And after fine-tuning you still don't know whether the new model breaks on typos · because you don't have those 31 questions. Models change every quarter · Opus will be outdated next year too · what truly accumulates, and what no one can take from you, · is your 31 + 5 + 31 evaluation system. If you want to run it yourself · this page is live right now.
Models go stale · harnesses evolve · but your eval system is your only scarce asset.
Closing slide · left: $0.10 / evolution · right: $500K / fine-tune · middle: 10⁵×; bottom line: "Eval is the asset." Then switch back to the demo page and stay there · show the final 91% and the liucao.me/demo/harness/run/ link.
