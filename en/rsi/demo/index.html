E-commerce Search Agent 's Harness self-evolution

What gets improved: an e-commerce product search agent (Python search(query) function · BM25 baseline · 30% hit rate).
Method: Leave the model weights completely untouched · let AI rewrite, generation by generation, search() Code · each generation runs a 31-question eval · promoted only if it passes the gate.
Engine:ShinkaEvolve (Sakana AI) · The Proposer is Claude via AWS Bedrock.

First, understand:What this demo is actually showing

An e-commerce site finds its search isn't accurate enough — users type "apple 128gb latest" You want to buy an iPhone, but the first result is Red Fuji apples. Instead of retraining the model, the dev team had the AI automatically Write 4 versions of glue code to improve it. This demo shows the full story of how these 4 code versions succeeded and failed.

Why 4 rounds

Because AI doesn't always come up with the right approach. It takes detours. This demo keeps its full 2 failures + 1 success:

R0 · Starting point
No optimizations at all, just query directly
Baseline 60%
BM25 saw the keyword apple and recommended Red Fuji apples. Serves as the baseline.
R1 · Leakage
AI hardcodes answers into the code
Blocked by audit · Discarded
Caught by the "data leakage audit": the code hard-coded the test set answers, so the whole version was discarded.
R2 · Compute
AI shifts to throwing compute at the score
Over budget · rejected
Run 20 candidates per problem and have the LLM rank them. Accuracy rises only 2%, but token usage goes up 8x. Not worth it.
R3 · Improvement
AI actually analyzes the root cause and writes a structured pipeline
✓ Promoted 90%
Intent recognition → attribute extraction → structured retrieval. The iPhone query hits, and cost rises by only 15%.

Four keywords, each explained in one sentence

Starting pointBaseline No optimizations at all: the model answers directly, serving as the baseline. Analogy: the score you get with no studying at all before the exam.
LeakageData Leak The Proposer sneaks test set answers into the code. The data leakage audit blocks it every time. Analogy: hiding a cheat sheet in your book during the exam and getting caught by the proctor.
ComputeCompute Scaling The Proposer trades compute for score with multi-candidate reranking, repeated voting, and similar tricks. Analogy: rewriting every answer ten times, hoping to guess right.
ImprovementReal Fix The Proposer carefully analyzes failure cases and writes code that actually solves the problem. Analogy: thoroughly reviewing the material before the exam.

1 What you're about to see

The base model (e.g., Sonnet 5) stays frozen throughout, with not a single training run. What's actually changing is its The glue code around it —— Each round, the AI reads the previous log, modifies this layer of code itself, and pushes accuracy step by step from 60% to 80~90%.

We take 4-round loop laid out in one table so you can see clearly what it changed each time and how it turned out: In round 1 it tried to cheat and got caught; in round 2 it tried to spend more money to boost the score and was rejected; in round 3 it figured out the real problem and was accepted.

❄️

Frozen · base model

weights = frozen

Continuous evolution · outer harness

Prompts, retrieval strategy, tool calls, retry logic — all in a single .py file. That's what the AI edits each round.

harness.py = evolves

In 2026 papers, this approach is called harness self-evolution(ACE, Meta-Harness and DGM all take this approach), the core idea in one sentence:The base model is already strong enough; the real leverage is in "how you use it."

2 What happens in one loop iteration

Press Play and these 4 steps run 4 times:

1

Read logs · write a new version

A coding agent (call it the proposer) looks at which problems failed in the last round and why, then starts editing the harness.

2

Full benchmark run

The new harness runs all 31 questions and records accuracy and token spend.

3

Judged by three gates

Did it cheat? (leakage audit) · Did it just spend its way to a higher score? (cost penalty) · Is the overall score actually higher? (blended score)

4

Accept or discard

Pass all three gates → the new version takes over; fail any one → the whole version is discarded, and the proposer tries again next round.

Key points:No human touched the code at any point. The Proposer reads and writes on its own, the gate judges on its own, and the loop keeps going on its own. Humans do only one thing — Define the eval set and thresholds up front.

3 What the task actually looks like

Scenario 1 · Financial report extraction (FiNER XBRL) —— Precisely pick the matching accounting line-item tag from a single sentence of financial report text:

Original"Total Revenues for the fiscal year ended December 31 was $12,458 million"
Correct labelus-gaap:RevenueFromContractWithCustomer
Baseline answer us-gaap:Revenues ✗ (two similar concepts confused)
Answer after evolutionus-gaap:RevenueFromContractWithCustomer ✓
XBRL is the financial reporting markup standard the US SEC requires public companies to use, with 139 fine-grained tags. Answering without any help, the model gets it wildly wrong.

Scenario 2 · E-commerce search (attribute-aware) —— from a casual remark by the user, find the product they actually want:

User input"water bottle no plastic" (plastic-free water bottle)
Correct SKU sku-glass-500ml (500ml glass cup)
Baseline answer sku-plastic-500ml ✗ (the negation "no" got swallowed)
Answer after evolutionsku-glass-500ml ✓
Traditional BM25 retrieval most easily loses negations, modifiers, and category ambiguity (is "apple" the fruit or the phone?). The evolved harness learns to clarify intent first, then retrieve.

4 Preview of the 4 rounds

Here's the spoiler up front, so the table won't leave you confused later:

Round 0
Starting point

Zero-shot bare answers, a 60~65% floor. The common starting line for all methods.

Round 1 🚨
Cheating — caught

The Proposer takes a shortcut and copies the test set answers straight into the prompt.The leakage audit caught it on the spot, and the whole version is discarded.

Round 2 💰
Paying to boost the score — rejected

It starts piling on retries; accuracy goes up a little, but token usage grows 5~8x.The cost penalty blocks this round of tokenmaxxing.

Round 3 ✓
A real fix — accepted

It carefully examined the failure modes and wrote a structured playbook.80~90% accuracy, promoted to the new frontier.

The Easter egg comes at the end: this evolved harness Without changing a single line of code, switched directly to another base model (Fable 5), still runs just as well, or even better.This shows it learned general engineering patterns, not a trick specific to one model.

5 Terms in one sentence

Harness
The "glue" code around the model: prompt assembly, retrieval, tool calls, retries on failure.This is what evolves in this demo.
Proposer
A coding agent (e.g. Claude Code). Its work loop: read logs → write the next version of the harness.
Gate: promotion gate
Three-in-one judge: leakage audit + cost penalty + blended score. Fail any one check and the new version is discarded.
Blended score
Blended score formula:accuracy + 0.5 × all_pass − 0.005 × tokens(M).Tokens have an explicit price, so you can't trade more compute for a higher score.
Frontier
The current best harness. Every new proposal has to go head-to-head with it and only takes its place if it wins.
Leakage audit
Checks whether the proposer peeked at the test-set answers (e.g., hard-coded them). If caught → the whole version is discarded.
Cost penalty
Token spend is deducted directly from the score. Hoping to boost your score by "just trying a few more times"? No way.
Base model
Sonnet 5 / Fable 5 and other LLMs.Frozen throughout: not a single training run.
