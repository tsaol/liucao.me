Argus Agent · Hundred Eyes · Prototype

Let a group of AI agents organize themselves to write software
Only tests that can't be faked count, and every step can be replayed

Argus is a prototype: a planner writes the spec and acceptance tests, 1 lead + N workers split up the work and develop in their own sandboxes, and the grader only accepts tests from the approved version. We used it on AgentCore to run team experiments ranging from 2 to 128 members. Next up is the Evolve module: letting agents improve themselves under strict gates.

The most important experimental finding:More agents is faster, but with diminishing returns;No organizational structure is always best; it depends on how tightly coupled the product is — self-organization works better when modules are independent, while tightly coupled modules need a single accountable lead; and the larger the scale,Planning and spec quality the bigger the bottleneck.
Key numbers (measured)
Maximum scale 128 workers, 640 acceptance tests, all passing in 13–38 minutes
Cost per acceptance criterion About $0.07–0.25 (Claude Opus 5.5)
Bedrock throttling 0 with 130+ agents running concurrently
Cheating attempts Modifying tests, force-pushing, hunting for repo files, disabling guards: all blocked

Chapter 1

What Argus is and why we built it

Chapter highlights
  • Let A swarm of AI coding agents organizing themselves to build real software, only acceptance tests that "can't be faked" decide, and the entire run is recorded for replay.
  • The name comes from Argus Panoptes, the hundred-eyed giant of Greek mythology: he sees everything.
  • It is Prototype: for validating ideas, not a production system. Runs incur real model costs.

In one sentence

Put a small team (1 lead + N workers) in a room with nothing but a blank whiteboard and say, "Build this software; you decide how to split the work."Argus is this room, plus a one-way mirror.

Three questions we want to answer

  • Can an AI team organize itself?, take real software from requirements all the way to passing every acceptance test?
  • Team size and organization How does it affect speed, cost and quality? (2 to 128 agents)
  • How we keep results trustworthy: the team can't change the tests or reach credentials, and every step can be replayed and verified?

Two modules

Module 1 · Implemented
Swarm: an agent swarm writes software
Requirements → spec and acceptance tests → spec gate → self-organizing team development → scoring → iteration. Chapters 2–11 of this page.
Module 2 · Proposal
Evolve: self-evolution
Make an existing agent improve itself under strict gates; then make Swarm's own way of working the target of evolution. Chapter 12 of this page.
Chapter 2

How it works: the flow of a single run

Chapter highlights
  • Process:Planning → spec gate → approval → team development → grading → next-round revision.
  • Spec gate: the planner's tests, on the empty scaffold,All must fail, proving the tests are real.
  • In each round, new tests must fail first, and old tests must not regress.

Six steps

1
Planning

The planner writes the product spec SPEC.md and acceptance tests from a short requirements description; at large scale, 1 lead planner and several module planners write them in parallel

2
Spec gates

Every acceptance criterion must have a test; the scaffold must start; tests must be collectible and All failed. If it fails, send the reason back, up to 3 times

3
Approve

Approve the spec manually, or set it to auto-approve

4
Team development

The lead and workers start at the same time, each in its own sandbox, sharing only one git repo and one empty Postgres

5
Scoring

Run periodically on main Approved version acceptance tests; ends when all pass, the budget runs out, or time is up

6
Revisions (from round 2)

First restore the tests to the approved version; the planner adds new tests per the change request: new ones fail first, old ones don't regress

Roles

Roles What it does
planner (lead / module)Writes the spec and acceptance tests; the lead planner splits modules, merges, and resolves conflicts between modules
lead Designs the division of work and the coordination tables, and coordinates the team (the “pure swarm” organization has no lead)
worker Claim tasks, write code, push to main
observer Labels the tables the team creates (this one is announcements, that one is task assignments…) so the control room can display them
referee (arbiter)When a team appeals that "this test can't pass", judge it independently and make only the minimal change (see Chapter 11)

Two kinds of sandbox

  • AgentCore: one Amazon Bedrock AgentCore Runtime session per agent = one dedicated microVM. Most experiments use this.
  • Docker: one container per agent, running on separate worker machines.

No conversation memory is kept between sessions; agents reorient using the database, git and a status command. All model calls (including sub-agents) are pinned to Claude Opus 5.5.

Chapter 3

How the team collaborates: given only an empty database

Chapter highlights
  • Argus Not prescribed table schemas or workflows. We provide only an empty Postgres database and a git repo, and watch how the team designs them on its own.
  • Teams usually create their own tables for announcements, handbooks, task assignments and status; at 30 people they use FOR UPDATE SKIP LOCKED Grab work.
  • Four organization modes to choose from: flat, team leads, emergent hierarchy, and pure swarm.

Chapter 4

Scoring and anti-cheating

Chapter highlights
  • Scoring uses Two temporary containers: one runs the team's product; the other runs the approved tests on a clean image without loading any pytest config or plugins from the repo.
  • Scoring output includes Random nonce and encoded, so nothing the product prints can pass itself off as a grading result.
  • All observed cheating attempts were blocked.

How scoring works

  • Product container: clean-clone the specified commit on main and run the team's own startup script.
  • Test container: only from Approved spec commit extract the acceptance tests and run them with an empty config and fixed parameters, with plugin auto-loading disabled.
  • An acceptance item passes = all of its tests pass; items without tests never count as passed.
  • Grade when main gets new commits (at least 90 seconds apart), or on a schedule.

Can't modify tests

  • Inside the agent's sandbox No repository files, and can only push through the git service.
  • Server-side git hook: only while the planner is working (or during recovery tests) can changes be made on main to the acceptance/; force-pushing and deleting branches are not allowed.
  • Before each round of revisions, the tests on main are restored to the approved version (including reverting test files the team added).

Cheating test results Measured

Attempts Results
Push after modifying acceptance tests Rejected by server-side hook
Force-push / roll back main Rejected
Find repo files in the sandbox Does not exist
Disable the guard hooks in the user config Guards still apply (root-owned managed settings)
Chapter 5

Security model: why the agent can't reach credentials

Chapter highlights
  • There are no AWS credentials in the sandbox: model requests go to the hub's proxy, which signs them and only allows the inference APIs of specified models.
  • Each agent has its own token and cannot impersonate others; sandbox networking is restricted to required services.
  • Guards are the "first reminder"; the real boundaries are the network policy, git server-side hooks and the two-container grading setup.
  • Credentials: there are no AWS credentials in the sandbox. The proxy signs on the sandbox's behalf. The allowlist only permits the specified models' inference, streaming inference, conversation and token-counting APIs, plus the read-only model list. The proxy also Per-agent accounting.
  • Identity: each agent's token is derived from the run token and the agent name (HMAC). It can't be used to impersonate another agent or for a run that has ended.
  • Network: the sandbox only needs access to the hub proxy, DNS, the git service and database in the same run, and the internet. On the Docker backend, a host firewall denies all other access (other internal machines, instance metadata, the host). On the AgentCore backend, VPC security groups limit which services are reachable.
  • Guards: Claude Code's PreToolUse hook, placed in root-owned managed settings and run with Python in isolated mode, so agents can't modify or disable it; it blocks force pushes, sudo / docker, metadata access, database deletion, edits to acceptance tests, and so on.
  • Control room: all pages and APIs require login, failed attempts are rate-limited by real client IP, changing the password invalidates all old sessions, no server info is exposed, and nothing is indexed by search engines.
  • AgentCore backend: the Runtime's execution role can only pull sandbox images and write its own logs, with no permission to call models; model calls still go through the hub proxy.

Known risks and deployment details are not listed on the public page.

Chapter 7

Experiment 1: from 2 to 30 people

Chapter highlights
  • More agents is faster, but with diminishing returns: 8 → 30 workers (3.75×), but only 2.2× faster.
  • Each worker must be assigned at least About 5 acceptance criteria; at 3.3 items, a third of the workers never committed.
  • More agents doesn't make it noticeably more expensive: $0.15–0.17 per acceptance item;Planning became the slowest step.

Data Measured

Everything runs in AgentCore microVMs, with the Claude Opus 5.5 model. “Team time” = from spec approval until all acceptance tests pass in round 1.

Runworker Acceptance criteria Each Team time Completed per minute Has commits Waiting/coordination Lead share of cost Cost per item

crm-8h8405.0 5.9 minutes6.88/850%18%$0.15
pm-30h301003.3 6.6 minutes15.120/3067%5%$0.17

Conclusion

  1. More agents is faster, but with diminishing returns: 8 → 30 people, but completion is only 2.2× faster.
  2. At least ~5 acceptance criteria each: below this ratio, many workers sit idle and coordination overhead goes up.
  3. A single lead has a limited span of control: the share of waiting and coordination goes 25% → 50% → 67%, and the lead's share of spend drops from 33% to 5%, so each worker gets less and less of its attention.
  4. More agents doesn't make it noticeably more expensive: waiting is mostly reading the task table, with a cache hit rate of about 95%, so it's cheap. With 31 microVMs running concurrently, Bedrock throttling was 0.
  5. Planning became the slowest step: a single planner takes 19 minutes to write 100 items, longer than the team's 6.6 minutes of development → switched to “1 lead planner + several module planners in parallel”.

Forcing hierarchy on small teams actually makes them slower Measured

Same 60-item spec, 4 workers: flat 3.4 minutes All passed, 4/4 made commits; add 2 team leads 10.9 minutes, and only 2/4 had commits. Leads had to split the work before assigning it, leaving workers waiting for tasks → so the 128-agent experiment dropped “pre-assigned leads” in favor of “emergent hierarchy”.

Chapter 8

Experiment 2: 128 people · e-commerce platform (independent modules)

Chapter highlights
  • Same 640-item spec, comparing three organizations:No structure at all (A) performed worst, about 18% slower, with 260 rebase conflicts.
  • Emergent hierarchy (B) was as fast and as cheap as a pure swarm (C); B has the fewest conflicts and the most participation.
  • The pure swarm shrank its own effective size to about a third: only 39 workers made commits.

Data Measured

Group Organization Team time Results Team cost rebase conflicts Workers with commits
A Flat (1 lead + 128)16.3 minutes 639/640 (the 640th spec contradicts itself)$16926076
B Emergent hierarchy 13.4 minutes640/640$162583
C Pure swarm (no lead)13.7 minutes640/640$1611339

All three groups had 0 rate limits; about $0.25 per acceptance item. B and C reused the spec approved for A (with only the contradictory test fixed), so the only difference between the three groups is how they were organized.

What the team did on its own

  • B's lead Designated 10 coordinators from among the workers: one for each of the 9 modules, plus a self-organized 5-agent QA team; staffed modules by size (18 for the orders module); required each module to have its own directory, with the main program auto-loading each module's routes; marked the critical path (auth, products, inventory, cart and checkout first).
  • C's swarm: within 1 minute of starting, 6 workers each created their own set of coordination tables at the same time (9 in total). After discussion, they converged on one set based on creation time.

Conclusion

  1. With 128 people,No structure at all (A) performed worst: more conflicts, about 18% slower.
  2. B ≈ C: equally fast and equally cheap. B has the fewest conflicts and the most participation, and is the easiest to manage. C converges on its own but goes through a stretch of duplicated work.
  3. 640 acceptance tests aren't enough to keep 128 people busy: C did the same work with a third of the people; adding more people mostly adds coordination overhead.
  4. Planning is still the bottleneck: 1 top-level planner + 9 module planners took 30 minutes and about $25, longer than team development (13–16 minutes).
  5. A single self-contradictory test is very costly: A spun idle for about 14 minutes at 639/640, cost rose from $196 to $408, and it could only be stopped manually → this led to "appeals + independent arbitration" and "wind-down downsizing" (Chapter 11).
Chapter 9

Experiment 3: 128 people · workflow approval engine (tightly coupled modules)

Chapter highlights
  • The conclusion flips: A (flat) was fastest and cheapest, B came second, and C (pure swarm) was slowest and most expensive, and also broke main once.
  • Inference: for tightly coupled products, build the shared core first,A single lead in charge makes it easier for the core to take shape first.
  • During development, the team found 3 spec conflicts or ambiguities, which the arbiter fixed without stopping the run.

Data Measured

Group Organization Team time Results Team cost rebase conflicts Workers with commits
A Flat 21.5 minutes640/640$1796048
B Emergent hierarchy 23.9 minutes640/640$251781
C Pure swarm 38.1 minutes640/640$3271642
  • A: midway, a worker appealed A922 (the “default value” rule contradicted the “required” rule). The arbiter changed it to send an explicit null, fixing it without stopping the run.
  • B: a worker appealed A543 / A547 (a workflow in the tests had an unreachable step, which conflicts with “every step must be reachable”), and the arbiter added a branch plus an assertion. At 23 minutes, the run automatically scaled down for wrap-up and stopped 120 workers.
  • C: stuck at 7 from minute 8 to minute 32; at 32.6 minutes main was broken (scored 0/640), and after the fix it went straight to 640.

Note when comparing: the specs for B and C include clarifications A543 / A547 that A's doesn't, and these two took extra time in B and C.

Chapter 10

Overall conclusions, and the limits of the evidence

Chapter highlights
  • No organizational structure is always best; it depends on how tightly coupled the product is: self-organization works better when modules are independent; when modules are tightly coupled, you need a single owner.
  • The larger the scale, Planning and spec quality the bigger the bottleneck: one bad test can leave 128 people idle.
  • Each condition has been run only once so far; conclusions need repeated experiments to confirm.

Five key conclusions Measured

  1. More agents is faster, but with diminishing returns; each worker needs at least about 5 acceptance tests. Adding more workers beyond that mainly adds coordination overhead.
  2. The right organization depends on coupling: on e-commerce, B ≈ C, about 18% faster than A; on workflow, A is the fastest and cheapest.
  3. Don't force hierarchy on small teams; with many workers, letting the lead decide whether to appoint coordinators (emergent hierarchy) gives the fewest conflicts.
  4. Planning is the slowest step, and a single contradiction in the spec is extremely costly in a large team → appeals and independent arbitration are needed.
  5. Cost under control: $0.07–0.25 per acceptance test. With 31 to 130+ agents running concurrently, Bedrock throttling stayed at 0.

Limits of the evidence Judgment

  • Each organizational structure was run only once per scenario.Running the same spec several times can give noticeably different times; gaps like “18% faster” need repeated runs to confirm they exceed the noise (same as Evolve's gate requirement).
  • There are only two scenarios(one loosely coupled, one tightly coupled); "depends on coupling" is inferred from this, not a measured pattern.
  • Specs are not identical: on the workflow task, B and C had two extra clarifications after arbitration.
  • All experiments use the same model (Claude Opus 5.5) and the same Argus; conclusions may differ with a different model or framework.

What could come next

  • Have the lead / chief planner assess coupling during planning and choose the organization accordingly.
  • Or, in Evolve, make "choosing the organization structure" itself something that can evolve (Chapter 12).
  • Build a scaling curve (same spec with 1 / 4 / 8 / 16 / 30 workers) and repeat each group several times.
Chapter 11

Two mechanisms that grew out of the experiments

Chapter highlights
  • Appeals + independent arbitration: when the team believes a test can't pass, it can appeal. An independent arbiter decides and makes only the minimal change, without weakening the test.
  • Scaling down at the end: when work is nearly done and progress stalls, only a few agents are automatically kept, so a large team doesn't sit idle and burn money.

Appeals + independent arbitration

  • Teams can't change the tests, but they can file an appeal stating which test and why it can't pass.
  • The arbiter is independent of the team: if the test contradicts other tests, the spec or itself, it edits the test or the spec text to match the majority of tests,The smaller the change, the better, keeping the numbering; if the test is fine and only the product is wrong, change nothing.
  • Can only change tests and specs, not product code; can't remove acceptance items or use the opportunity to weaken tests. Changes are pushed to a separate branch and merged after checks pass.

Verification Measured

  • Deliberately planted trap tests: one contradictory test was planted among 60. The lead appealed 70 seconds in, with an accurate reason. The arbiter changed only 2 lines (200 → 201), and 60/60 passed.
  • Real runs: A922 in workflow A and A543 / A547 in B were all found by the team itself. The arbiter supplied fixes that didn't weaken the tests (explicit null; an added branch + assertion).
  • An interesting observation:Different teams' implementations of the same spec expose ambiguities in it.

Scaling down at the end Measured

After workflow B stalled at 637/640, it automatically kept only the lead + 8 workers and stopped the other 120.

Chapter 12

Evolve: letting agents improve themselves under strict gates (proposal)

Chapter highlights
  • Make an existing Strands Agent improve itself: find failures → proposer edits → Prove it actually improved on a held-out set it can't see → Human approval → release, with rollback.
  • The gate must prove three things:Not luck, not more spending, not gaming the system.
  • Next, Swarm's own way of working becomes the target of evolution — a replayable RSI demo.

What to change

An agent package + manifest: only prompts, tool descriptions and skills can be changed; tool implementations and the main program are frozen. Out-of-bounds changes are caught by diffing outside the sandbox, rejected outright and logged as security incidents.

Evolution loop

Run the baseline on the search set → failed samples + trajectories
Each generation: pick a parent (by score + diversity; weaker ones are kept too)
      → proposer (Claude Code) makes changes based on the failures and submits proposal.json: rationale, what changed, what it expects to fix / break
      → diff is checked against the allowlist; anything out of bounds is rejected
      → screen on a 20% subsample first, then run the full search set → save to the archive
Stop when the budget runs out; output the Pareto frontier (pass rate, cost, latency)

Promotion gate

Not luck
Run the baseline 3+ times on the held-out set to get the noise distribution; use a paired bootstrap, and count it as an improvement only if the lower bound of the confidence interval is > 0
Not spending more
Budget-matched baseline: give the original agent the same average cost (e.g., best of several attempts); the candidate must be significantly better
Not gaming the system
The held-out set is mounted only in the grading container and doesn't exist at all in the proposer's sandbox; every regressed sample is listed; final human approval, with a reason that can't be changed

The report breaks the improvement into three parts: what comes from extra compute, what may come from evaluation shortcuts, and what remains that truly generalizes.

Integration with Swarm Judgment

  • Treat the Swarm lead / worker prompts (and even "which organization structure to use") as what gets evolved; score them by acceptance pass rate and cost across multiple projects, with a separate set of projects held out.
  • To count as true RSI, it must clear three more bars: the improver itself must also get better; the specs and tests for held-out projects Frozen before the run and approved by a human, and can't be written on the fly by the AI planner; the gains carry over across generations.
  • Main challenges:Every score requires completing a real project, evaluation is far more costly and noisy than ordinary agent evaluation.
Chapter 13

Relationship to RSI, OpenEvolve, and other frameworks

Chapter highlights
  • Swarm is "AI writing software" and is not RSI in itself; Evolve is AI for AI (L1 of AI4AI); only once the two are connected do we first touch RSI.
  • Argus doesn't build models or reinvent evolution engines; it sits Execution + gating + release + isolation + replay.
  • Complements OpenEvolve: it answers “how do we find a better version,” while Argus answers “how do we prove it's really better and use it safely.”
  • Where Swarm stands today: the target of improvement is an external product, not the system itself (L0 in AI4AI). But “what counts as done” is written by an AI planner, so the spec gate and human approval are critical. The gate proves the tests aren't empty, but it can't prove they're correct or complete.
  • Where Evolve fits: the proposer picks the change, a manifest sets what it may edit, and the evaluation is frozen where the proposer can't see it → L1. On the “five levels of autonomy” scale, it's roughly L2.
  • Its scaling experiments are themselves first-hand data for the RSI debate: “Can AI R&D headcount scale linearly?” Here we measured diminishing returns, coordination overhead and a planning bottleneck.Judgment
  • Compared with similar frameworks: the closest to Evolve is AgentCore optimization (it changes almost the same things); the closest to Swarm is Cursor's planner / worker pattern. For a framework-by-framework comparison, see The big business picture.

Chapter 14

Known limitations and roadmap

Chapter highlights
  • Prototype, deployed only in the author's own AWS account; only one run at a time.
  • Roadmap: Evolve module, pause / resume, scaling-curve experiments, walkthrough mode.

Known limitations

  • AgentCore sessions last at most 8 hours; progress carries over between sessions via the database and git, and very long runs need a new session to pick up where the last one left off.
  • After a restart, the hub automatically takes over in-progress runs, but model requests in flight at the moment of the restart are interrupted and their cost isn't recorded; runs interrupted during the planning / gating phase have to start over.
  • Only one run at a time; pause / resume isn't implemented yet.
  • Deployed only in the author's own AWS account.

Roadmap

  • Evolve module: see Chapter 12.
  • Pause / resume.
  • Scaling-curve experiment: the same spec, run with 1 / 4 / 8 / 16 / 30 workers and repeated several times.
  • Walkthrough mode: automatic replay with narration, good for demos.
