数据来源与方法

  • 来源： CloudPing.co — AWS 区域延迟矩阵，社区维护者： Matt Aimonetti。公开 JSON 端点： https://www.cloudping.co/api/latencies?percentile={p_10|p_50|p_99}&timeframe=1W
  • 测量方式： 每个 AWS 商业区域中的一台 t3.nano EC2 实例会定期向其他所有区域建立 TCP 连接并记录往返时间。数值反映的是 公网 EC2 ↔ EC2 TCP 握手，而不是 ICMP ping，也不是 AWS 骨干网。
  • 聚合窗口： 滚动 1 周窗口，数据源每天刷新数次。本页快照采集于 2026-09-12.
  • 百分位： p10 为快速路径（10% 的样本更快）。 p50 为中位数。 p99 为尾部延迟：每 100 个样本中至少有 1 个达到这个延迟。SLA 应按 p99 而非 p50 设计。
  • 覆盖范围： 34 个目标区域。GovCloud（us-gov-*）和中国（cn-*）区域是隔离环境，无法从商业账户进行探测，因此特意未包含。
  • 注意事项：
    • 经由 Transit Gateway、VPC 对等连接、PrivateLink 或 AWS 骨干网的流量，延迟通常比这些数字更低，抖动也更小。
    • 巴林（me-south-1）的 p10/p50/p99 完全相同，这是源数据采样稀疏造成的假象，并非链路异常稳定。
    • 此处的亚毫秒精度没有实际意义；数值请按 ±3 ms 误差看待。
  • 复现： curl 'https://www.cloudping.co/api/latencies?percentile=p_50&timeframe=1W' | jq '.data["eu-south-2"]'

想要一份独立的参考数据？ 运行 30 个 Lambda 到 Lambda 的 TCP 探测，持续一天，大约只需 50 行 Python 代码。这样你就有了一份私有数据集，可以与 CloudPing 的公开数据对比。

设计建议

  • The Aurora Global Database RPO < 1 s 需要稳定的个位数至较低两位数毫秒级延迟 — 只有 eu-west-3 （巴黎，~18 ms）完全可以作为备用区域。 eu-central-2, eu-south-1, eu-west-2 都可以使用，只是回放延迟会稍大一些。
  • For 异步灾备 欧洲或美国东部的任何区域 p50 都低于 100 ms，应根据服务目录和价格来选择，而不是延迟。

区域快捷选择

  • 最近的邻近区域： eu-west-3 巴黎 — 18 ms，经法国边境的陆地光纤。同步复制的最佳选择。
  • Bedrock / SageMaker 备选： eu-central-1 法兰克福 — 31 ms，欧盟内服务种类最丰富。
  • 欧盟主权： eusc-de-east-1 European Sovereign Cloud（勃兰登堡）— 105 ms，延迟较高，因为目前仅通过少量 PoP 路由。
  • 美洲入口： us-east-1 弗吉尼亚北部 — 97 ms，标准的跨大西洋枢纽。
  • 亚洲入口： ap-south-1 孟买 — 119 ms，经 SEA-ME-WE 海缆通往亚洲的最短路径。
