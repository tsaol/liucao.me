ARM 上判定资源饱和

1 · 99% 和 x86 一样

Linux kernel 把大部分芯片差异吞掉了。/proc、/sys、top、htop、iostat、vmstat、sar、dmesg、journalctl——在 Graviton 上工作方式完全一致。你的 x86 肌肉记忆继续有效。接下来这页只讲那 1% 需要留神的地方。

2 · 1% 不同——PMU / 工具替换

perf 硬件事件名

PMU 是 armv8_pmuv3，不是 Intel Skylake/Icelake。perf stat / perf top / perf record 都能用，但原始事件名不同。

$ perf list | head -20
  branch-instructions OR branches         [Hardware event]
  branch-misses                           [Hardware event]
  cache-misses                            [Hardware event]
  cache-references                        [Hardware event]
  cpu-cycles OR cycles                    [Hardware event]
  instructions                            [Hardware event]
  ...
  armv8_pmuv3/cpu_cycles/                 [Kernel PMU event]
  armv8_pmuv3/inst_retired/               [Kernel PMU event]
  armv8_pmuv3/l1d_cache_refill/           [Kernel PMU event]
  armv8_pmuv3/mem_access/                 [Kernel PMU event]

通用事件（cycles、instructions、cache-misses）在两个平台都是同一个符号。Intel 特有的（uops_retired、mem_load_uops_retired）就不存在了。

PMU 在小 size 上也能用，但计数器少——实测已验证（2026-09-22，AL2023 kernel 6.12，Tokyo）：
  • m8g.medium（1 vCPU）：3 个硬件计数器，暴露 43 个 armv8_pmuv3 事件
  • m8g.24xlarge（96 vCPU）：6 个硬件计数器，暴露 68 个事件
  • 一次同时观测超过计数器数量 → kernel 自动 event multiplexing（perf 输出会显示 (50.09%) 之类的采样占比），值仍统计有效但精度下降
  • ARM SPE（Statistical Profiling Extension，逐指令采样）和 arm_cmn mesh 事件在两个 size 上都不暴露——需要 metal 规格
  • 基础的 cycles + instructions IPC 度量在最小的 m8g.medium 上就能用
所以做 IPC 判断随便什么 size 都行；只有做深度 top-down 微架构分析（大量事件同时看、SPE、mesh 带宽）才必须上大 size 或 metal。[6]

Intel-only 工具（Graviton 上不能用）

  • Intel VTune
  • Intel PCM（pcm.x、pcm-memory.x）
  • Intel MLC (Memory Latency Checker)

ARM 上的等价物

  • perf——每天用
  • topdown-tool——ARM 官方的自顶向下微架构分析（pip install topdown-tool）
  • ARM Streamline——ARM 商业 GUI
  • hotspot（KDAB）——开源 GUI，读 ARM perf 数据没问题

numactl、taskset、chrt、ionice、nice 两端完全一样。

2.5 · 实测 —— m8g.medium vs m8g.24xlarge PMU 对照

为了验证"小 size 上 PMU 是否可用"这个说法，我起了两台 M8g 实测。结论：小 size 的 PMU 完全能用，只是硬件计数器数量少；一次观测超过计数器上限时 kernel 自动做 event multiplexing——perf 输出里那些 (50.09%) 尾巴就是"这个事件只在 ~50% 的采样窗口里跑"。SPE 和 CMN mesh 事件在两个 size 上都不可见，需要 metal 规格。

维度m8g.medium (1 vCPU)m8g.24xlarge (96 vCPU)
硬件计数器数量36
armv8_pmuv3 事件43 个68 个
基础 IPC（cycles+instructions）✅ 直接量✅ 直接量
6 个 hw 事件同时⚠️ 自动 multiplexing（~50% 采样）✅ 一次全跑
10 个事件同时⚠️ 每个降到 ~20–30%⚠️ 每个降到 ~60%
ARM SPE（/sys/devices/arm_spe_0）❌❌
CMN mesh 事件（arm_cmn）❌❌

复现步骤

# 1. 起一台 m8g.*，AL2023 arm64 (kernel 6.12)
# 2. 装 perf
sudo dnf install -y perf

# 3. 看 PMU 有几个硬件计数器
dmesg | grep -E "perfevents.*armv8_pmuv3"
# 输出示例：hw perfevents: enabled with armv8_pmuv3_0 PMU driver, 6 (0,8000001f) counters available

# 4. 数一下暴露了多少个 armv8_pmuv3 事件
perf list pmu 2>&1 | grep -c "armv8_pmuv3_0/"

# 5. 跑一次多事件观测，看有没有 multiplexing 尾巴 (xx.xx%)
sudo perf stat -a -e cycles,instructions,cache-references,cache-misses,\
branch-instructions,branch-misses,bus-cycles,stalled-cycles-frontend,\
stalled-cycles-backend -- sleep 2

# 6. 看 SPE / CMN 有没有暴露（在非 metal 上都是没有）
ls /sys/devices/arm_spe_0/ 2>/dev/null && echo "SPE present" || echo "SPE not present"
ls /sys/devices/ | grep -i arm_cmn || echo "arm_cmn not present"

实用规则（实测验证过）：
  • 只做 IPC 判断（cycles + instructions 两个事件）——最小的 m8g.medium 也够。
  • 做 4–6 个事件的 top-down 分析（front-end stall、back-end stall、L1/L2 miss、branch miss）——24xlarge 及以上无多路复用，最优。
  • 做 逐指令采样（SPE）或 DRAM/mesh 带宽——必须 *.metal 规格。

怎么解读这份结果

1️⃣ "小 size 上 counter 被隐藏"是错的——但"小 size 更弱"是对的。
我原来的说法是"小 size 上 PMU 被 hypervisor 隐藏，perf stat 拿不全数据"。实测发现更精确的说法是：PMU 一定暴露（AL2023 kernel 6.12 上，m8g.medium 的 dmesg 也能看到 armv8_pmuv3_0 PMU driver, 3 counters available），只是 硬件计数器只有 3 个，而 m8g.24xlarge 有 6 个。硬件计数器数量 = ARM Neoverse V2 核心内固定的物理寄存器数量，不是虚拟化层截掉的。

2️⃣ multiplexing 是"分时复用"，不是"丢数据"。
当你要求 kernel 同时观测 10 个事件而只有 3 个物理计数器，kernel 会把这 10 个事件轮流塞进那 3 个 slot 里，每次几毫秒切换一次。每个事件被启用的时间占比就是右边那个 (30.05%)。perf 会用这个占比反推"如果全窗口都启用，估计值是多少"——所以 数值仍然是可信的估算，但方差变大，短时突刺（几十微秒的爆发）可能采样窗口正好错过。

3️⃣ IPC 是 Graviton 上最实用的一个 metric。
两台机器上跑 dd if=/dev/urandom of=/dev/null，IPC 都是 4.05——这是 Neoverse V2 的 6-wide 前端能达到的高位数字。相反，如果你的服务 IPC < 1.0，就是被内存延迟拖住了（cache miss、TLB miss、跨 NUMA 访存），加 CPU 核数或换更大机器不会让它变快，需要修算法或改数据结构。这个判断在 m8g.medium 上就能做——不用等大机器。

4️⃣ SPE 和 arm_cmn 缺席的意义。
SPE（Statistical Profiling Extension）是 ARM v8.2 起的一个特性：不像传统 perf record 只在采样点抓 IP，SPE 能为每一条被采样的指令记录内存地址、cache 命中/miss、延迟。等于是把 Intel PEBS 那套 ARM 化。arm_cmn 是 Coherent Mesh Network 事件，能看整块 die 的 DRAM 带宽利用率。两个东西在虚拟机里都拿不到——因为它们暴露的信息可能泄漏物理主机的邻居工作负载，AWS 只在 *.metal 上开。要做这类深度分析，租一小时 m8g.metal-24xl（约 $5.7/hr in Tokyo）就够。

5️⃣ 对页面读者的直接指导。
如果你只是想知道服务是不是"真的忙"vs"只是等 IO / 等内存"，任意 M8g 规格都够，跑一行 perf stat -a -e cycles,instructions -- sleep 10 就能拿到 IPC。不要因为"PMU 只有大机器有"这种想当然的说法放弃在小机器上做性能分析。只有当你想同时看 top-down 的四类瓶颈（front-end stall、back-end stall、bad speculation、retiring）时，才需要至少 24xlarge 那 6 个计数器；想做指令级归因或量内存带宽，才需要 metal。

6️⃣ 这份结果的时效性。
实测是 2026-09-22，AL2023 kernel 6.12。硬件计数器数量是 Neoverse V2 芯片固定属性，不会变；SPE / CMN 的开放策略是 AWS 决定的，理论上可能在未来 kernel/hypervisor 版本上放宽——所以本页会随时间失效，重要决定前请自己复现上面的复现步骤。

3 · Load average 真相

Linux 的 load average 不是纯 CPU 负载。自 1993 年 Matthias Urlichs 的 patch 起，它同时计入可运行线程和处于 TASK_UNINTERRUPTIBLE（D 状态，通常是磁盘 IO 或某些 kernel lock）的任务。Urlichs 当年的原话："the load average goes down when you replace your fast swap disk with a slow swap disk"——这个反直觉的现象就是他改的动机。别的 Unix 至今还是纯 CPU 版本。[3]

三个数字（1 / 5 / 15 min）是指数衰减移动平均——看趋势别看绝对值，并且一定要对比 vCPU 数。

更准的饱和信号：

  • runqlat（bcc）——run-queue 等待时间直方图。
  • vmstat 1 的 r 列——可运行进程数。
  • offcputime 按 TASK_UNINTERRUPTIBLE 过滤——找出真正卡在 D 的线程。

4 · CPU 利用率 ≠ 忙

%CPU = "非 idle 时间"。它不告诉你那些 cycles 是在执行指令，还是在等 DRAM。DRAM 延迟这些年没跟上核数扩张，所以很多热循环即使 %CPU 100% 也在等内存。[4]

用 perf stat 量 IPC (Instructions Per Cycle)：

sudo perf stat -a -- sleep 10
# 关注 insns per cycle 那一行

经验判据： IPC < 1.0 → 内存瓶颈；IPC > 1.0 → 计算瓶颈。4-wide 核心上 0.78 IPC 意味着指令吞吐只有 ~19.5%。

5 · CPU 饱和判定

Load Average

用 top、uptime、或 cat /proc/loadavg。

load > 0.8 × vCPU = warning
load > vCPU 且趋势上升 = saturated

Per-Core 分布

mpstat -P ALL 1——%usr、%sys、%iowait、%soft、%st（steal）。

单核 %usr+%sys 长期 > 90 = 单线程瓶颈
%st > 5 = 被邻居偷 CPU（M8g 少见，t 系列常见）

Softirq 陷阱

某核 %soft = 50%+、其他核闲——ENA 中断全钉在一个核。查 cat /proc/interrupts，再用 irqbalance + IRQBALANCE_BANNED_CPUS 或手动 taskset 分。

见于小实例（2 vCPU），一个软中断核就能把吞吐拉爆。[7]

6 · 内存饱和判定

free -h

看 available，不是 free——page cache 会算进 available。

available < 10% = warning

vmstat 1

si / so 列——swap in/out。云机通常没 swap，非 0 = 真出事。

si/so 持续 > 0 = 已经在换页

OOM 追溯

dmesg -T | grep -i "killed process"
journalctl -k | grep -iE "oom|out of memory"

AL2023 默认无 swap → 直接 OOM kill，不会先降速

cgroup 压力

cat /sys/fs/cgroup/system.slice/<svc>.service/memory.pressure

某 service 的 full avg10 > 5% = 那个 service 自己在 thrash 内存

/proc/meminfo 里值得看的：MemAvailable（kernel 承诺可回收）、Cached、Slab（细分 SReclaimable vs SUnreclaim）、Shmem、PageTables（进程数大 + map 多时会飙）。

7 · 磁盘饱和判定

iostat -xz 1 关键列

列含义阈值
%utilbusy time接近 100%（NVMe multi-queue 上会误报，见下）
await平均单 IO 延迟（ms）gp3 > 10 · io2 > 2
r/s + w/sIOPS对比 volume 上限
rareq-sz + wareq-sz平均请求大小（KB）小 + 高 IOPS = 随机
EBS 有两个天花板：
1️⃣ Per-volume：gp3 默认 3000 IOPS / 125 MB/s，按量买。
2️⃣ Per-instance：如 m8g.large 全部 EBS 加起来最多 ~10K IOPS / ~700 MB/s。
要用 CloudWatch VolumeThroughputPercentage、EBSIOBalance%、EBSByteBalance% 一起看。

更可靠的信号：PSI——cat /proc/pressure/io。multi-queue NVMe 上 %util 会误报（多个队列并发处理，看着 100% busy 但应用没在等），PSI 是 kernel 层账本，一定准。[5]

8 · 网络饱和 & ENA 计数器全解

基础工具（sar -n DEV 1、ip -s link、nstat -a）和 x86 一样。核心一条命令——ENA 驱动的限流计数器：

ethtool -S ens5 | grep -E 'exceeded|conntrack|linklocal'

六个 *_allowance_exceeded（AWS UserGuide 原文）[8]

计数器意思（AWS 原文）
bw_in_allowance_exceeded入向带宽超过实例上限，包被 queued 或 dropped
bw_out_allowance_exceeded出向带宽超过实例上限
pps_allowance_exceeded双向 PPS 超过实例上限——小实例先撞这个
conntrack_allowance_exceeded连接跟踪数超上限，新连接建立失败——silent killer
linklocal_allowance_exceeded访问 link-local 服务（DNS / IMDS / Time Sync）的 PPS 超上限——SDK metadata 重试环
conntrack_allowance_available还剩多少连接可建立（Nitro 独有，需驱动 ≥ 2.8.1）

m8g 的 ENA 限流（近似）

规格基线带宽PPS 上限conntrack 上限
m8g.medium~0.4 Gbps~100K~35K
m8g.large~0.75 Gbps~200K~55K
m8g.xlarge~1.5 Gbps~400K~130K
m8g.2xlarge~3 Gbps~800K~260K
m8g.4xlarge~6 Gbps~1.6M~450K

ENA queue affinity

ENA 每个 RX/TX queue 一个 MSI-X IRQ，命名 <iface>-Tx-Rx-<idx>。AWS ENA best-practices 推荐：pin app 到和 IRQ 同一个 vCPU；RPS 核放同 NUMA node；不要禁 irqbalance，用 IRQBALANCE_BANNED_CPUS 让它跳过你的 NAPI 核。[7]

Multi-NUMA Graviton 上默认 affinity 会把 IRQ 撒到两个 node——page 分配在错的 node。看 rx_queue#_lpc_wrong_numa 计数器，非 0 就要手动 pin。

9 · PSI（Pressure Stall Information）

Linux 4.20+ 且 CONFIG_PSI=y。三个文件：/proc/pressure/{cpu,memory,io}。每个资源两行：

  • some——"share of time in which at least some tasks are stalled on a given resource"
  • full——"share of time in which all non-idle tasks are stalled ... simultaneously"——full 期间 CPU 空转，持续 full = thrashing。

字段：avg10 / avg60 / avg300（百分比）+ total（累计微秒）。total 能捕捉均值掩盖的短脉冲。CPU 只有 some——系统全局的 full CPU 没意义。[5]

阈值参考

数值判断
some avg10 > 10%Warning
full avg10 > 5%Urgent——业务真的在等

Trigger（用户态 poll）

写 "some 150000 1000000" 到文件，然后 poll() / epoll()。窗口必须 500 ms–10 s，非特权只能倍数 2 s。Facebook 的 oomd 就是靠 PSI trigger 做 early OOM。[5]

cgroup v2 vs 全局 PSI：cgroup v2 挂载后，每个 cgroup 有自己的 memory.pressure（AL2023 默认 v2；AL2 要加 systemd.unified_cgroup_hierarchy=1）。系统 PSI 看着平静，但某容器已在 thrash——只有 cgroup PSI 能看到。K8s VPA、systemd-oomd、Facebook oomd 都靠这个决定杀谁。

10 · eBPF 五件套（Graviton 上直接可用）

AL2023 是 kernel 6.x，bcc-tools 和 bpftrace 装完就用，无 ARM 特殊 flag：

sudo dnf install -y bcc-tools bpftrace
工具回答的问题
runqlat调度器 run-queue 等待延迟直方图——真正的 CPU 饱和信号
biolatency块设备 IO 延迟分布（-D 按盘拆）
offcputime线程 off-CPU 时的堆栈——配合 load avg 里的 D-state
tcpretransTCP 重传的 5-tuple + socket state
cachestatpage cache hit / miss 比——早期内存压力

Gregg 的规矩：daemon 用 BCC，one-liner 用 bpftrace。[9]

11 · 决策树——服务慢了往哪查

service slow?
│
├── top: load avg > vCPU?
│    ├── YES → mpstat -P ALL 1
│    │        ├── 一个核 %soft 高 → ENA IRQ affinity
│    │        └── 所有核 %usr 高 → perf top → app hotspot
│    └── NO  → 继续往下
│
├── free -h: available < 20%?
│    ├── YES → dmesg -T | grep -i killed → OOM 历史
│    │        vmstat 1 → si/so 非 0 → swap thrash（云上罕见）
│    └── NO  → 继续
│
├── iostat -xz 1: await > 10ms 或 PSI io some avg10 > 10%?
│    ├── YES → CloudWatch EBSByteBalance% / VolumeThroughputPercentage
│    │        → 撞 volume 或 instance EBS 上限
│    └── NO  → 继续
│
├── ethtool -S ens5 | grep exceeded 计数器上涨?
│    ├── bw_*_allowance      → 升配或降流量
│    ├── pps_allowance       → 合批、减少小包
│    ├── conntrack_allowance → keep-alive、复用连接
│    └── linklocal_allowance → 缓存 IMDS token、退避
│
└── 都不忙但还是慢 → offcputime -K -p <pid> 10
                    → 线程到底卡在哪
