1 · Netflix 60 秒 checklist

SSH 进去，按顺序敲这 10 条命令，每条 ~1 秒。60 秒后你已经知道是 CPU / 内存 / 磁盘 / 网络 / 都不是。[6]

#命令告诉你什么
1uptimeLoad average 1/5/15——上升 / 平稳 / 尖峰
2dmesg -T | tail -20Kernel 消息：OOM、TCP drop、NIC reset、EBS nvme 错误
3vmstat 1 5r=run queue、si/so=swap、us/sy/wa/st
4mpstat -P ALL 1 5Per-vCPU 不均衡——单核 hot = 单线程瓶颈
5pidstat 1 5Per-process CPU 滚动 delta，比 top 更适合抓突刺
6iostat -xz 1 5Per-device %util / await / queue——EBS 延迟住在这里
7free -mfree / buff / cache——看 available 别看 free
8sar -n DEV 1 5每 NIC 包 / 字节，对比实例上限
9sar -n TCP,ETCP 1 5active/s、retrans/s——重传 > 0.1% 就有网络痛
10topSanity check——按 RES 排序找泄漏

2 · USE 方法——落到 EC2 每种资源

Brendan Gregg 的 USE = Utilization / Saturation / Errors，逐资源套 checklist。[1][2]

资源UtilizationSaturationErrors
CPU mpstat -P ALL 1（%usr+%sys+%st） vmstat r > vCPU；perf sched latency dmesg MCE；perf PMU error
Memory free -m；sar -r vmstat si/so；sar -B pgscan；dmesg | grep oom ECC；malloc 失败（bpftrace）
Disk (EBS gp3/io2) iostat -xz 1 %util avgqu-sz > 1；高 await /sys/block/nvme*/device/ioerr_cnt；smartctl

EBS 天花板 CloudWatch VolumeReadOps + WriteOps VolumeQueueLength > 1；gp2 BurstBalance == 0 VolumeThroughputPercentage

3 · Google SRE 的 心法

SRE Book "Effective Troubleshooting" 章节里最贵的 5 条建议：[3]

  • Fly the airplane first——先止血（drain、回滚、切流量），再排根因。用户在流血的时候不要 debug。
  • Horses, not zebras——最近的 deploy / config push 永远是嫌疑人 #1。dashboard 上标记 deploy 时间戳。
  • Simplify, reduce, bisect——在层之间注入已知输入，二分排查。
  • 假设按可能性 × 成本排序验证；每一步写进共享文档带时间戳。
  • 突然的延迟跳变通常是"工作类型变了"，不是"流量变了"——见战争故事 #1。

4 · 10 个 故障签名

01ALB 返回 502 但 target 显示 "healthy"

诊断：app 卡在 IO wait，健康检查却因为轻量还能过。

iostat -xz 1 · CloudWatch VolumeQueueLength · jstack/py-spy 找阻塞线程

修：把慢 endpoint 从流量池摘掉，dump 线程栈，先重启。

02Container 被 OOMKilled，但 liveness probe 通过

诊断：dmesg | grep "killed process" + kubectl describe pod Reason=OOMKilled。Liveness 只看 HTTP，不看 RSS。

kubectl top pod --containers · 加 resource limits + memory alert

03linklocal_allowance_exceeded > 0

诊断：SDK 在打 IMDS（169.254.169.254）疯狂重试——通常是 IAM role 挂错或 IMDSv1 hammer。

ethtool -S eth0 | grep linklocal · aws sts get-caller-identity 验证角色

修：AWS SDK v2 缓存 IMDSv2 token；转 IMDSv2；hop limit 设 2 让 Pod 也能拿到。

04conntrack_allowance_exceeded 攀升

诊断：短连接洪水 或 client 不用 keep-alive。这是ENA 实例级限制，不是 kernel nf_conntrack。

ethtool -S eth0 | grep conntrack

修：客户端开 HTTP keep-alive；升配（更大实例 = 更大 conntrack allowance）；出口大流量走 NAT Gateway 而非 NAT 实例。

05EBS io2 延迟尖峰（跨 AZ 复制中）

诊断：AZ 事件后卷在重建；VolumeTotalWriteTime / VolumeWriteOps > 10 ms。

CloudWatch EBS metrics 三张图对齐 AZ event 时间线

修：等重建（时间不确定），或用 Multi-AZ 复制到另一 volume 顶上去。

06SSM Session Manager 连不上

诊断：user-data 脚本还在跑，cloud-init 阻塞 ssm-agent 启动。

从 EC2 console 拿 console-output · /var/log/cloud-init-output.log

修：user-data 长任务后台化或换 startup service。

07Instance 反复重启（boot loop）

诊断：cloud-init 失败——挂 rescue volume 看 /var/log/cloud-init.log。

aws ec2 get-console-output --instance-id i-...

08M8g 上 CPU steal %st > 5

诊断：M8g 不是 burstable，%st 高一般是 bare-metal 邻居争抢——罕见，AWS 支持工单。t3/t4g 上 %st 是正常——用完了 credit balance。

mpstat 1 · aws cloudwatch get-metric CPUCreditBalance（仅 t 系列）

09sar -n TCP retrans/s > 1% 但主机无丢包

诊断：Security Group / NACL 的 conntrack 满，或路径 MTU 不匹配。

tracepath <dest> · 检查 SG entries + jumbo frame 兼容性

10小实例 pps_allowance_exceeded 冒头

诊断：小包洪水（DNS query、cache miss、心跳）先撞 PPS 上限，比带宽先满。

ethtool -S eth0 | grep pps

修：升配；合批 UDP；如 DNS 洪水加 client-side 缓存。

5 · Coredump on Amazon Linux 2023

AL2023 用 systemd-coredump，不是传统 core 文件：

sudo dnf install -y systemd-coredump
sudo sysctl -w kernel.core_pattern='|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h'
sudo systemctl edit user.slice   # DefaultLimitCORE=infinity
ulimit -c unlimited              # 每个 shell 生效

coredumpctl list                 # 库存
coredumpctl info <PID>            # 元信息 + backtrace
coredumpctl gdb  <PID>            # 直接 attach gdb
coredumpctl dump <PID> -o /tmp/core.$PID

转储位置：/var/lib/systemd/coredump/。要用传统 core 文件：kernel.core_pattern=/var/coredumps/core.%e.%p.%t + fs.suid_dumpable=2。

6 · 重启前抢救——保留现场

D=/tmp/oncall-$(hostname)-$(date +%s); mkdir -p $D
dmesg -T                       > $D/dmesg.txt
journalctl -b --no-pager       > $D/journal.txt
ps auxfww                      > $D/ps.txt
top -bn1                       > $D/top.txt
ss -tanp                       > $D/ss.txt
ss -s                          > $D/ss-summary.txt
iostat -xz 1 3                 > $D/iostat.txt
vmstat 1 3                     > $D/vmstat.txt
mpstat -P ALL 1 3              > $D/mpstat.txt
free -m                        > $D/free.txt
ethtool -S eth0                > $D/ena.txt
cp -a /proc/loadavg /proc/meminfo /proc/net /proc/pressure $D/ 2>/dev/null
cp -a /var/log/messages /var/log/cloud-init*.log /var/log/dmesg $D/ 2>/dev/null
tar czf /root/oncall-snapshot.tgz $D
aws s3 cp /root/oncall-snapshot.tgz s3://$FORENSICS_BUCKET/

7 · SRE 战争故事——都能学到东西

#1 · App Engine "突然慢 10 倍，没任何变更"[3]——一个安全扫描器往白名单表里写了几千行；每个请求随后线性扫描内存缓存。没新 RPC、没流量尖峰，只是"工作的形状变了"。教训：只看 RPC 分布不够，得看进程内 profile。

#2 · GKE CreateCluster 6h40m 大故障[4]——DockerHub 上一份镜像损坏，阻塞了所有新 cluster 创建。IRC 上 41 人上线，但 IC（Incident Commander）拖了 ~2 小时才指定。教训：早声明 IC；预置"从 mirror 里驱逐坏镜像"这种通用止血手段。

#3 · 比利时数据中心遭雷击（2015）[4]——两分钟内四次雷击，UPS 电池损坏，GCE 磁盘错误。运行中 VM 数据丢失比例：0.000001%——因为 IC 第一时间指定、角色都演练过。

9 · 升级触发条件

  • Page DBA——复制延迟 > 30s、死锁增多、pg_stat_activity 全是 idle in transaction。
  • Failover——节点不可达 > 2 min、dmesg 里出磁盘读错、EBSByteBalance% 调参后仍为 0。
  • Scale out——所有核 > 80% 持续 10 min 且 ALB 队列还在涨。怀疑内存泄漏时不要 scale up——那是喂养泄漏。
  • Roll back——p99 退化的时间线与某次 deploy 对齐。先回滚再排根因。
