M8g vs M7i — 全景对比

Amazon Graviton4 (Neoverse V2 / Armv9.0-A) 与 Intel 4th-gen Xeon Scalable (Sapphire Rapids) 的架构、规格、性能、生态、迁移。

TL;DR 1 · 微架构 2 · 规格表 3 · 性能 4 · 生态兼容性 5 · 迁移 playbook 6 · 什么情况留在 M7i 7 · 价格 8 · Graviton 家族简史
一句话结论
如果你的软件栈支持 arm64（现在绝大多数都支持），选 M8g；每 vCPU 便宜约 11%，能效高约 60%，单核延迟更好，且没有 SMT——1 vCPU = 1 物理核。仍然需要 M7i 的场景只有五类：x86-only 商业软件、AVX-512/AMX 加速的 CPU 推理、Windows Server、按 Intel core 授权的软件、要靠 Turbo Boost 冲高主频的单线程任务。

1 · 微架构差异

M8g — AWS Graviton4 / Arm Neoverse V2 "Demeter"

  • 指令集 Armv9.0-A，强制包含 SVE2、Pointer Authentication (PAC)、Branch Target Identification (BTI)。
  • 流水线：6-wide 解码、8-wide rename/dispatch、320-entry ROB、15 个执行端口、1536-entry micro-op cache。
  • 每核缓存：L1 64 KB I + 64 KB D · L2 2 MB（是 Graviton3 的两倍）。L3 是共享的 CMN-700 mesh SLC——每 die 最多 512 MB。
  • 96 物理核 / socket，最多 2 socket 一台机器（48xlarge 和 metal-48xl 有 192 vCPU）。没有 SMT——1 vCPU 就是 1 物理核。
  • 内存：M8g 是 12-channel DDR5-5600；M8gn / M8gb 版本升到 DDR5-6400。
  • 主频固定：2.8 GHz（48xlarge 是 2.7 GHz）。没有 Turbo Boost。
  • 永远开启的内存加密；每 vCPU 独占 L1/L2；PAC + BTI 硬件反 ROP。[4]

M7i — Intel Xeon Scalable 4th gen "Sapphire Rapids" (AWS 定制 SKU)

  • 指令集 x86_64，AVX-512（512-bit VNNI + bfloat16）+ AMX 矩阵 tile 加速（INT8/BF16 GEMM，M7i 全系可用）+ DSA/IAA/QAT（仅 bare-metal）。
  • 主频：3.2 GHz all-core turbo，3.8 GHz max-core turbo（比 M8g 高约 14~35%）。
  • DDR5，TME 内存加密，48xlarge / metal-48xl 支持 EFA。
  • SMT 开启——每核 2 线程；m7i.4xlarge 的 16 vCPU 其实是 8 个物理核 + 8 个 SMT 线程。这是"Graviton 快 30%"最大的错觉来源。[3]

SVE2 到底带来什么

SVE2 是"长度无关"的向量指令：同一份二进制在 128-bit 的 V2 核心和未来 256-bit 核心上都能自动向量化，不需要重编。Graviton4 上的 SVE2 是 128-bit 位宽（Graviton3 的 SVE1 是 256-bit，V2 换成了两个更窄的 SVE 单元）。[2] 现实收益：memcpy / memcmp / strlen（glibc 2.35+）、zlib-ng、OpenSSL 3.2+ 的 ChaCha 与 AES-GCM、FFmpeg 的 h.264 / AV1 dsputil。

AVX-512 依然领先的是稠密线性代数与 CPU 端 LLM 推理——大概是 4× 向量宽度差；AMX 又在 INT8 矩阵乘上进一步拉开差距。

易踩的两个"没有"：Graviton4 没有 Turbo Boost，也不再支持 32-bit userspace。任何靠冲主频的单线程 x86 代码、或者跑 32-bit ELF 的老程序，迁到 M8g 都会退化。[1]

3 · 性能——AWS 和客户自证

  • AWS 声称 M8g 比 M7g（Graviton3）compute 快 30%；vCPU / 内存上限比 M7g 高 3×。[4]
  • Graviton 家族比同代 x86 便宜约 20%，能耗低约 60%。[4]
  • M7i vs M6i：15% 更好性价比；M7i-flex 19%。[3]
  • Salesforce（M7i）：吞吐 +25%、响应 快 11%。[3]
  • Tufts Medicine（M7i）：性能 +68%、成本 -64%（$1.2M/年）。[3]
  • Bright Data（M6g → M8g）：+66% 性能。[4]
  • IBM Instana（M8g）：CPU 利用率再降 30%。[4]
第三方 benchmark 可信度提醒
Phoronix / AnandTech / ChipsAndCheese 的 Graviton4 深度评测目前是 403 / 404（原文链接失效或站点归档）。上面数字是 AWS 官方与其客户案例，做参考请留 20% 安全余量。真实场景一定要做 A/B。

Graviton4 推荐编译器 flag [1]

# Graviton4 独占 fleet — GCC 13+ 或 Clang 16+（AL2023 的 GCC 11 已 backport）
CFLAGS="-O3 -mcpu=neoverse-v2"

# 一份二进制跑 Graviton3/4/5 —— 官方推荐的均衡值
CFLAGS="-O3 -mcpu=neoverse-512tvb"

# 最保守，兼容 Graviton2/3/4/5，不内联 LSE
CFLAGS="-O2 -march=armv8.2-a -moutline-atomics"

5 · 迁移 playbook：M7i → M8g

  1. 清点二进制依赖——用下面的扫描脚本扫典型 M7i host。
  2. 把镜像重编成 multi-arch——docker buildx build --platform linux/amd64,linux/arm64 --push ...，ECR 存 multi-arch manifest。
  3. 混合 ASG 试跑——把 M8g launch template 加进来，先给权重 0，观察健康检查通过率与错误率。
  4. 压测头对头——比 p50/p95/p99 和 CPU 利用率，不能只看吞吐（Graviton4 单核更强，同吞吐下 CPU 利用率往往更低）。
  5. 切换——渐进调权重，M7i template 保留 30 天做回滚 AMI。
  6. Right-sizing——Graviton4 没 SMT 但单核更快，通常你需要的 vCPU 数比 M7i 少。经验：32 vCPU M7i → 24 vCPU M8g。

一份 x86 兼容性扫描脚本

#!/bin/bash
# arm64-readiness.sh — 在 M7i 上运行，找所有还是 x86-only 的东西
set -euo pipefail

echo "== 找 /opt /usr/local /srv 下的非可移植二进制 =="
find /opt /usr/local /srv -type f \( -perm -u+x -o -name '*.so*' \) 2>/dev/null | \
  while read -r f; do
    file "$f" | grep -q 'ELF.*x86-64' && echo "x86-only: $f"
  done

echo "== Docker 镜像检查 =="
if command -v docker >/dev/null; then
  docker image ls --format '{{.Repository}}:{{.Tag}}' | while read img; do
    arches=$(docker manifest inspect "$img" 2>/dev/null | \
      grep -oP '"architecture":\s*"\K[^"]+' | sort -u | paste -sd,)
    [[ "$arches" == *arm64* ]] || echo "no-arm64: $img ($arches)"
  done
fi

echo "== Java native lib（JNI）=="
find / -name '*.so' 2>/dev/null | xargs -I{} file {} 2>/dev/null | \
  grep -i 'x86-64' | grep -Ei 'jni|netty|snappy|rocksdb|leveldb'

echo "== Python wheel =="
find / -name '*.whl' 2>/dev/null | grep -E 'x86_64|manylinux.*x86'

输出里的三类东西就是迁移工单：x86-only:、no-arm64:、以及 x86 版 JNI 库。

6 · 什么情况不要迁

  1. x86-only 商业软件——Oracle DB、部分 SAS/SPSS/MATLAB、老 Splunk agent、IBM MQ 的 JNI 库。[1]
  2. CPU 端 LLM / 传统 ML 推理——AVX-512 + AMX 对 INT8/BF16 GEMM 领先 Graviton4 128-bit SVE2 一大截。除非上 GPU / Inferentia，否则留在 M7i / C7i / R7iz。
  3. Windows Server——Graviton 上 Windows 只是 preview。
  4. 按 Intel core 授权的软件——某些商用数据库、老一代 ISV。
  5. 依赖 32-bit userspace——Graviton4/5 完全放弃 32-bit。[1]
  6. 依赖 Turbo Boost 冲主频的单线程任务——M7i 3.8 GHz vs M8g 2.8 GHz 是 35% 差距。
  7. Kernel < 4.15（没有 SVE 支持）或 AL2 4.14——先迁到 AL2023 再考虑换芯片。[5]
  8. 监控 / 安全 agent 只有 x86 版——CrowdStrike、Splunk 老版本、部分 EDR。生态债务往往吃掉那 ~11% 的实例节省。

8 · Graviton 家族简史

Graviton1（2018，EC2 A1）是 16 核 Cortex-A72 的试水，性能一般。Graviton2（2019，M6g/C6g/R6g）跳到 64 核 Neoverse N1、7nm DDR4，让 Arm on AWS 走向主流。Graviton3（2022，M7g/C7g）换 Neoverse V1、Armv8.4、SVE1、DDR5。

Graviton4（2024，R8g / M8g / C8g）——Neoverse V2、Armv9.0、SVE2、96 核、12-channel DDR5。Graviton5（Neoverse V3，192 核，PCIe Gen 6，3 nm）在 2026 年 6 月 GA，出在 M9g / M9gd 上，AWS 声称比 M8g 再快 ~25%。这意味着 M8g 现在是"中生代"——不是前沿，但生态最成熟。
