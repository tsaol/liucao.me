GPU 开不出来？先把容量订下来

GPU 紧张时，开机器总是报"没有容量"。这篇用订酒店来打个比方，讲清楚按需容量预留（ODCR）是什么、什么时候用官方的 Fleet、什么时候用演示脚本 gpu-hunter，以及怎么判断效果。

1 · 先选方案 2 · ODCR 是什么 3 · gpu-hunter 怎么抢 4 · 怎么用 5 · 抢之前检查 6 · 怎么看效果 7 · 欧洲 GPU 分布 8 · 费用和释放 术语表
声明：本文的脚本只用于演示和学习，不是 AWS 官方工具，不要直接用在生产环境。
容量预留从创建起就按按需价收费，用不用都收。限制、价格、配额以 AWS 官方文档为准。
先看这里：三句话
  1. 开不出 GPU，是那个机房暂时没有空机器。能做的只有：过一会儿再试、换机房（AZ）、换机型、少要几台。
  2. ODCR 就像提前订酒店房间：订到了就一直给你留着，机器关了也不丢；但从订到那一刻起就收钱，住不住都收。
  3. 只在一个 AZ 里抢的话，先用 AWS 自带的 Capacity Reservation Fleet；要同时在好几个 AZ 里找，再用 gpu-hunter。

2 · ODCR 是什么：像订酒店房间

ODCR（按需容量预留）就是在某一个 AZ 里，把某种机器先订下来，不用马上开机。

① 订房创建 ODCR，比如订 4 台 g6e.12xlarge
→
② 房间留着💰 开始按按需价收钱，不住也收
→
③ 入住在预留里开机器，💰 只收机器的钱
→
④ 退房机器关掉，🔑 房间还是你的，想用再开
→
⑤ 退订取消预留，✅ 停止收钱
图 2 · ODCR 的一生

和直接开机器（run-instances）比，最大的区别是第 ④ 步：机器关了，容量还在。

直接开机器（run-instances）先订容量（ODCR）
拿到的是什么一台运行中的机器某个 AZ 里某种机器的"房间"，给你留着
每次重试要准备镜像、子网、安全组、密钥、磁盘只要机型、AZ、数量
机器关掉以后容量还回去，下次可能开不出来容量还是你的
只有一部分空房可以少拿几台一次请求要么全给、要么不给，所以要自己拆小
价格按需价，机器开着才收按需价，订到就收，用不用都收
要注意的一点：订到以后，系统可能要最多约 5 分钟才把状态从 pending 显示成 active。这段时间不是没订到，不要去退掉它。

4 · 怎么用

# 1. 一定先 dry-run：只检查权限和参数，不创建任何东西
./gpu-hunter.sh -r eu-central-1 -t g6e.12xlarge -n 2 --dry-run

# 2. 抢 4 台：先试 g6e.12xlarge，再试 g6e.24xlarge；6 小时还没抢满就停
./gpu-hunter.sh -r eu-central-1 -t g6e.12xlarge,g6e.24xlarge -n 4 --max-hours 6

# 3. 看抢到了什么；不用了就释放（停止收费）
./gpu-hunter.sh -r eu-central-1 --status
./gpu-hunter.sh -r eu-central-1 --release

# 4. 看这次运行的效果（默认读最新的记录文件）
tools/report.sh

脚本结束时的退出码

退出码意思
0全部抢到了
1参数写错了
2选的机型在这些 AZ 都没有
3致命错误：配额不够、没权限、参数不被接受
4到了 --max-hours 还没抢满
130被你手动停掉了（Ctrl+C）

不管怎么结束，已经抢到的预留都会保留，要用 --release 释放。

抢到以后怎么开机器

  • open 模式（默认）：同一个账号里，机型、平台、AZ 对得上的机器会自动用上预留，正常开机就行。
  • targeted 模式（加 --targeted）：只有开机时写明了预留 ID 的机器才能用：
aws ec2 run-instances ... \
  --capacity-reservation-specification 'CapacityReservationTarget={CapacityReservationId=cr-xxxx}'

5 · 抢之前检查

  • 配额够不够：看按需 vCPU 配额（Running On-Demand G and VT / P instances）。预留也算在配额里。比如一台 p4d.24xlarge 就是 96 vCPU。
  • 权限：创建、查询、取消预留，打 tag；用通知的话还要 SNS。先跑 --dry-run 确认。
  • 机型和 AZ 多给几个：业务能接受的话，把同级别的机型都写上，选择越多越容易抢到。
  • open 模式会"吸走"正在跑的机器：账号里已经有同型号、同 AZ 的机器在跑的话，预留一生效它们就会占进来，你抢到的容量就被用掉了。不想这样就用 --targeted。
  • 别问得太勤：创建预留和账号里所有"修改资源"的操作共用一个限流额度（见图 6）。太快会连累客户自己的 Auto Scaling、Terraform。
  • 在同一个区域里运行：实测查询请求本区域约 0.4 秒，跨区域约 1.3 秒（本区域的创建请求没有单独测过）。
  • 量大或要长期用：同时找 AWS account team。脚本只能抢偶尔空出来的容量。

6 · 怎么看效果

每次运行都会把每次申请记进一个 CSV 文件，结束时打印一行统计；tools/report.sh 可以汇总成表。主要看这几个数：

看什么说明什么
⭐ 多久抢满最重要，代表整体效果
多久抢到第一台最快多久能开始干活
各机型 × AZ 的成功率哪里更好抢，下次把它排在前面
被限流的次数应该是 0；不是 0 就把间隔调大
闲置成本订到了却没用上，浪费了多少钱（看 CloudWatch 的使用率指标）
对比要公平：容量一直在变，所以要和一个"基线"做法比，两种做法轮流跑，不要在同一个账号里同时跑，每种多跑几次再看结果。详细方法见 机制详解。

8 · 费用和释放

  • 预留订到就按按需价收钱，没开机器也收；开了机器只收机器的钱，不会重复收。按秒计费，最少 60 秒。
  • Savings Plans 的折扣对预留也有效。
  • 脚本订的预留没有结束时间，随时可以退订，退订免费：./gpu-hunter.sh --release。还在 pending 的暂时退不了，过几分钟再运行一次。
  • 每次没抢到，账号里会留下一条 failed 记录：不收钱、不占配额，60 分钟后就看不到了。
  • 几个任务一起跑时，用 --tag 分开，释放时不会互相影响。

? · 术语表

术语大白话
AZ（可用区）一个区域里的一个机房。法兰克福有 3 个
ICEInsufficientInstanceCapacity："这个机房现在没有空的这种机器了"
ODCROn-Demand Capacity Reservation，按需容量预留：先把机器"订下来"
open 模式订下的容量"谁来都能用"：机型、AZ 对得上的机器自动用上
targeted 模式订下的容量"只给报了订单号的用"：开机时要写明预留 ID
配额账号最多能同时用多少 vCPU。超了就开不了，和有没有货无关
限流一秒钟内调用 API 太多次，AWS 让你等一会儿再来
pending / active预留的状态："订到了，还在准备" / "准备好了"
请求编号（ClientToken）给每个请求编个号，同一个号重复发，AWS 只处理一次
Capacity Reservation FleetAWS 官方的"自动帮你一直订"的功能，只能在一个 AZ 里用
