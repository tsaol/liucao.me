01
CHAPTER 01

Argus 是什么,为什么做

本章要点
  • 让一群 AI 编程 agent 自己组织起来写出真实的软件,只有「做不了假」的验收测试说了算,全程录像可回放。
  • 名字来自希腊神话里的百眼巨人 Argus Panoptes:什么都看得见。
  • 它是原型:用来验证想法,不是生产系统;运行会产生真实的模型费用。

一句话

把一个小团队(1 个 lead + N 个 worker)关进一间只有一块空白板的屋子,说「把这个软件做出来,怎么分工你们自己定」。Argus 就是这间屋子,加上一面单向玻璃。

想回答的三个问题

  • AI 团队能不能自己组织起来,把一个真实的软件从需求做到全部验收通过?
  • 团队规模和组织方式怎么影响速度、成本和质量?(2 人到 128 人)
  • 怎么保证结果可信:团队改不了测试、碰不到凭证,每一步都能回放查证?

两个模块

模块一 · 已实现
Swarm 蜂群写软件
需求 → 规格和验收测试 → 规格门禁 → 团队自组织开发 → 判分 → 迭代。本页第 2–11 章。
模块二 · 方案
Evolve 自进化
让一个已有的 agent 在严格门禁下自己变好;之后把 Swarm 自己的工作方式当作进化对象。本页第 12 章。
02
CHAPTER 02

它怎么工作:一次运行的流程

本章要点
  • 流程:规划 → 规格门禁 → 批准 → 团队开发 → 判分 → 下一轮修订。
  • 规格门禁:planner 写的测试在空脚手架上必须全部失败,证明测试是真的。
  • 每一轮的新测试先失败、旧测试不许退步。

六步

1
规划

planner 根据一段需求写产品规格 SPEC.md 和验收测试;规模大时由 1 个总 planner + 若干模块 planner 并行写

2
规格门禁

每个验收项都要有测试;脚手架能启动;测试能被收集且全部失败。不过就把原因发回,最多 3 次

3
批准

人工批准规格,或设为自动批准

4
团队开发

lead 和 worker 各在独立沙箱里同时开工,只共享一个 git 仓库和一个空的 Postgres

5
判分

定期在 main 上跑批准版本的验收测试;全部通过、预算用完或到时间就结束

6
修订(第 2 轮起)

先把测试恢复成批准版;planner 按修改要求加新测试:新的先失败,旧的不退步

角色

角色做什么
planner(总 / 模块)写规格和验收测试;总 planner 拆模块、合并、处理模块间矛盾
lead设计分工方式和协作表,协调团队(「纯蜂群」组织里没有 lead)
worker领活、写代码、推到 main
observer给团队自建的表打标签(这是公告、那是分工……),方便控制室显示
referee(仲裁者)团队申诉「这条测试不可能通过」时,独立判断并只做最小修改(见第 11 章)

两种沙箱

  • AgentCore:每个 agent 一个 Amazon Bedrock AgentCore Runtime 会话 = 一台独立 microVM。实验大多用这个。
  • Docker:每个 agent 一个容器,跑在单独的 worker 机器上。

会话之间不保留对话记忆,agent 靠数据库、git 和一个状态命令重新定位;所有模型调用(包括子 agent)都固定为 Claude Opus 5.5。

CHAPTER 03

团队怎么协作:只给一个空数据库

本章要点
  • Argus 不规定表结构和流程,只给一个空的 Postgres 和一个 git 仓库,看团队自己怎么设计。
  • 团队通常会自建「公告、手册、分工、状态」几类表;30 人时会用 FOR UPDATE SKIP LOCKED 抢活。
  • 可以选四种组织方式:扁平、小组长、涌现分层、纯蜂群。

CHAPTER 04

判分与防作弊

本章要点
  • 判分用两个临时容器:一个跑团队的产品,另一个用干净镜像跑批准版测试,不加载仓库里的任何 pytest 配置或插件。
  • 判分输出带随机 nonce 并编码,产品打印的内容冒充不了判分结果。
  • 实测的作弊尝试全部被挡住。

判分怎么做

  • 产品容器:干净克隆 main 的指定提交,跑团队自己的启动脚本。
  • 测试容器:只从批准的规格提交里取出验收测试,用空的配置和固定参数跑,禁止自动加载插件。
  • 一个验收项通过 = 它的所有测试都通过;没有测试的项永远不算通过。
  • main 有新提交时判分(至少间隔 90 秒),或定时判分。

改不了测试

  • agent 的沙箱里没有仓库文件,只能通过 git 服务推送。
  • 服务端 git 钩子:只有 planner 工作期间(或恢复测试期间)才允许改 main 上的 acceptance/;禁止强制推送和删除分支。
  • 每一轮修订前,先把 main 上的测试恢复成批准版本(包括撤销团队新增的测试文件)。

作弊测试结果 实测

尝试结果

CHAPTER 05

安全模型:为什么 agent 碰不到凭证

本章要点
  • 沙箱里没有任何 AWS 凭证:模型请求发给 hub 的代理,由代理签名,而且只放行指定模型的推理接口。
  • 每个 agent 一个独立 token,不能冒充别人;沙箱的网络被限制在必要的服务上。
  • 守卫是「第一道提醒」,真正的边界是网络策略、git 服务端钩子和判分双容器。
  • 凭证:沙箱里没有 AWS 凭证。代理替沙箱签名;白名单只允许指定模型的推理、流式推理、对话和计 token 接口,以及只读的模型列表。代理同时按 agent 记账。
  • 身份:每个 agent 的 token 由运行 token 和 agent 名派生(HMAC);不能冒名,也不能用于已结束的运行。
  • 网络:沙箱只需要访问 hub 代理、DNS、同一运行里的 git 服务和数据库,以及外网。Docker 后端由宿主机防火墙把其余访问(内网其他机器、实例元数据、宿主机)全部拒绝;AgentCore 后端由 VPC 安全组限制可达的服务。
  • 守卫:Claude Code 的 PreToolUse 钩子,放在 root 所有的 managed settings 里,用隔离模式的 Python 运行,agent 改不了、关不掉;拦截强制推送、sudo / docker、访问元数据、删库、改验收测试等。
  • 控制室:所有页面和 API 都要登录;按真实客户端 IP 限制错误次数;改密码后旧会话全部失效;不暴露服务器信息,不被搜索引擎收录。
  • AgentCore 后端:Runtime 的执行角色只有拉取沙箱镜像和写自己日志的权限,不给任何模型调用权限,模型调用仍然走 hub 代理。

已知风险和部署细节没有在公开页面列出。

CHAPTER 07

实验一:从 2 人到 30 人

本章要点
  • 人多更快,但收益递减:8 → 30 个 worker(3.75 倍),速度只提高 2.2 倍。
  • 每个 worker 至少要分到约 5 条验收;3.3 条时三分之一的人一直没有提交。
  • 人多不明显变贵:每条验收 0.15–0.17 美元;规划成了最慢的一环。

数据 实测

全部在 AgentCore microVM 里,模型 Claude Opus 5.5。「团队用时」= 从批准规格到第 1 轮全部验收通过。

运行worker验收项每人团队用时每分钟完成有提交等待/协调lead 花费占比每条花费
tiny-recipes2105.01.7 分钟5.92/225%33%$0.07
ac-tasks2105.02.3 分钟4.32/227%28%$0.08
crm-8h8405.05.9 分钟6.88/850%18%$0.15
pm-30h301003.36.6 分钟15.120/3067%5%$0.17

结论

  1. 人多更快,但收益递减:8 → 30 人,完成速度只提高 2.2 倍。
  2. 每人至少约 5 条验收:少于这个比例,很多 worker 空等,还拉高协调开销。
  3. 单个 lead 的管理范围有限:等待和协调占比 25% → 50% → 67%;lead 花费占比从 33% 降到 5%,分到每个人身上的精力越来越少。
  4. 人多不明显变贵:等待主要是读任务表,缓存命中率约 95%,很便宜。31 台 microVM 并发时 Bedrock 限流为 0。
  5. 规划成了最慢的一环:单个 planner 写 100 条要 19 分钟,比团队开发的 6.6 分钟还长 → 改成「1 个总 planner + 若干模块 planner 并行」。

人少时硬加层级反而更慢 实测

同一份 60 条规格、4 个 worker:扁平 3.4 分钟全部通过、4/4 有提交;加 2 个小组长 10.9 分钟、只有 2/4 有提交。小组长要先拆分再分配,worker 等着领活 → 128 人实验里不再「事先规定小组长」,改成「涌现分层」。

CHAPTER 08

实验二:128 人 · 电商平台(模块独立)

本章要点
  • 同一份 640 条规格,比较三种组织:完全没有结构(A)最差,慢约 18%,rebase 冲突 260 次。
  • 涌现分层(B)和纯蜂群(C)一样快、一样便宜;B 冲突最少、参与最多。
  • 纯蜂群自己把有效规模缩小到约三分之一:只有 39 个 worker 有提交。

数据 实测

组组织方式团队用时结果团队花费rebase 冲突有提交的 worker
A扁平(1 lead + 128)16.3 分钟639/640(第 640 条规格自相矛盾)$16926076
B涌现分层13.4 分钟640/640$162583
C纯蜂群(无 lead)13.7 分钟640/640$1611339
A 扁平B 涌现分层C 纯蜂群

三组限流都是 0;每条验收约 $0.25。B、C 复用 A 批准的规格(只修了那条矛盾测试),所以三组唯一的区别是组织方式。

团队自己做了什么

  • B 的 lead 从 worker 里指定了 10 个协调者:9 个模块各一个,外加一个自建的 5 人 QA 组;按模块大小分人(订单模块 18 人);规定每个模块独立目录、主程序自动加载各模块路由;标出关键路径(认证、商品、库存、购物车、结算优先)。
  • C 的蜂群:开工 1 分钟内 6 个 worker 同时各建一套协作表(共 9 张),随后讨论,按创建时间收敛到一套。

结论

  1. 128 人时,没有任何结构(A)最差:冲突多、慢约 18%。
  2. B ≈ C:一样快、一样便宜;B 冲突最少、参与最多、最好管理;C 会自己收敛,但有一段重复建设。
  3. 640 条验收用不满 128 个人:C 用三分之一的人完成同样的工作,继续加人主要增加协调开销。
  4. 规划仍是瓶颈:1 个总 planner + 9 个模块 planner 用了 30 分钟、约 $25,比团队开发(13–16 分钟)还长。
  5. 一条自相矛盾的测试代价很高:A 在 639/640 时空转约 14 分钟,花费从 $196 涨到 $408,只能手动停止 → 催生了「申诉 + 独立仲裁」和「收尾缩编」(第 11 章)。

实验三:128 人 · 工作流审批引擎(模块高度耦合)

本章要点
  • 结论反过来了:A 扁平最快最便宜,B 次之,C 纯蜂群最慢最贵,还把 main 改坏过一次。
  • 推断:耦合度高的产品要先把共用核心做好,一个统一负责的 lead 更容易让核心先成型。
  • 团队在开发中发现了 3 条规格矛盾或歧义,由仲裁者不停机修好。

CHAPTER 10

总结论,以及证据的局限

本章要点
  • 没有一种组织方式永远最好,取决于产品的耦合度:模块独立时自组织更好,模块高度耦合时需要统一负责的人。
  • 规模越大,规划和规格质量越是瓶颈:一条坏测试能让 128 人空转。
  • 每种条件目前只跑了一次,结论需要重复实验来确认。

五条总结论 实测

  1. 人多更快,但收益递减;每人至少约 5 条验收,继续加人主要增加协调开销。
  2. 组织方式取决于耦合度:电商上 B ≈ C 比 A 快约 18%;工作流上 A 最快最便宜。
  3. 人少时不要硬加层级;人多时,让 lead 自己决定要不要指定协调者(涌现分层),冲突最少。
  4. 规划是最慢的一环,而且规格里的一条矛盾在大团队里代价极高 → 需要申诉和独立仲裁。
  5. 成本可控:每条验收 0.07–0.25 美元;31 到 130 多个 agent 并发时,Bedrock 限流都为 0。

证据的局限 判断

  • 每种组织方式在每个场景下只跑了一次。同一份规格多跑几次,用时可能有明显波动;「快 18%」这类差距需要重复跑来确认是否超出噪声(和 Evolve 的门禁要求一样)。
  • 场景只有两个(一个松耦合、一个紧耦合),「取决于耦合度」是由此推断,不是测量出的规律。
  • 规格不完全相同:工作流的 B、C 多了两条仲裁后的澄清。
  • 所有实验都用同一个模型(Claude Opus 5.5)和同一套 Argus;换模型或换框架结论可能不同。

下一步可以怎么做

  • 让 lead / 总 planner 在规划时就判断耦合度,并选择组织方式。
  • 或者在 Evolve 里把「选组织方式」也变成可进化的对象(第 12 章)。
  • 做扩展曲线(同一规格 1 / 4 / 8 / 16 / 30 人)并每组重复多次。

CHAPTER 11

从实验里长出来的两个机制

本章要点
  • 申诉 + 独立仲裁:团队认为某条测试不可能通过时可以申诉,由独立的仲裁者判断,只做最小修改,不削弱测试。
  • 收尾缩编:接近完成、进度停滞时自动只保留少数人,避免大团队空转烧钱。

申诉 + 独立仲裁

  • 团队改不了测试,但可以提交申诉:哪一条、为什么不可能通过。
  • 仲裁者独立于团队:如果这条测试和别的测试、规格或它自己矛盾,就修改测试或规格文字,让它和多数测试一致,改动越小越好,保留编号;如果测试没问题、只是产品没做好,就什么都不改。
  • 只能改测试和规格,不能改产品代码,不能删验收项,不能借机削弱测试;改动推到单独的分支,检查通过后再合并。

验证 实测

  • 故意埋雷测试:在 60 条里埋一条矛盾测试,lead 开工 70 秒就申诉,理由准确;仲裁者只改了 2 行(200 → 201),60/60 通过。
  • 真实运行:工作流 A 的 A922、B 的 A543 / A547 都是团队自己发现的,仲裁者给出了不削弱测试的修正(显式 null;补分支 + 断言)。
  • 一个有意思的现象:不同团队对同一份规格的不同实现,会暴露规格里的歧义。

收尾缩编 实测

工作流 B 在 637/640 停滞后,自动只保留 lead + 8 个 worker,停掉 120 个。

CHAPTER 12

Evolve:让 agent 在严格门禁下自己变好(方案)

本章要点
  • 让一个已有的 Strands Agent 自己变好:找失败 → proposer 修改 → 在它看不到的 held-out 集上证明真的变好了 → 人工审批 → 发布,可回滚。
  • 门禁要证明三件事:不是运气、不是多花钱、不是钻空子。
  • 之后把 Swarm 自己的工作方式当作进化对象 —— 一个可回放的 RSI 演示。

改什么

一个 agent 包 + 清单:只能改提示词、工具描述、skills;工具实现和主程序冻结。越界修改在沙箱外比对 diff,直接拒绝并记为安全事件。

进化循环

基线在搜索集上跑 → 失败样本 + 轨迹
每一代:选父代(按分数 + 多样性,差的也保留)
      → proposer(Claude Code)依据失败修改,交 proposal.json:依据、改了什么、预计修好 / 弄坏什么
      → 清单比对 diff,越界即拒
      → 先在 20% 小样本上初筛,再跑全量搜索集 → 存入档案
预算用完即停,输出帕累托前沿(通过率、成本、延迟)

晋升门禁

不是运气
基线在 held-out 上重复跑 3 次以上得到噪声分布;用配对 bootstrap,置信区间下界 > 0 才算提升
不是多花钱
预算匹配基线:给原 agent 同样的平均成本(比如多试几次取最好),候选必须显著更好
不是钻空子
held-out 只挂进判分容器,proposer 沙箱里根本没有;逐条列出退化的样本;最后人工审批,理由不可改

报告会把提升拆成三部分:额外算力带来的、可能来自评测捷径的、剩下真正可泛化的。

和 Swarm 打通 判断

  • 把 Swarm 的 lead / worker 提示词(甚至「选哪种组织方式」)当作进化对象;用多个项目的验收通过率和成本打分,另一组项目做 held-out。
  • 要算真正的 RSI,还要过三道门槛:改进者本身也要变好;held-out 项目的规格和测试在运行前冻结、人工批准,不能由 AI planner 现写;收益跨多代持续。
  • 主要难点:每打一次分都要做完一个真项目,评测成本和噪声远高于普通 agent 评测。

CHAPTER 13

和 RSI、OpenEvolve 以及其他框架的关系

本章要点
  • Swarm 是「AI 写软件」,本身不是 RSI;Evolve 是 AI for AI(AI4AI 的 L1);打通后才第一次碰到 RSI。
  • Argus 不做模型、不重造进化引擎;位置在执行 + 门禁 + 上线 + 隔离 + 回放。
  • 和 OpenEvolve 互补:它回答「怎么找到更好的版本」,Argus 回答「怎么证明真的更好并安全用起来」。
  • Swarm 今天的位置:改进的对象是外部产品,不改进自己(AI4AI 的 L0)。但「什么算做完」是 AI planner 写的,所以规格门禁和人工批准很关键 —— 门禁证明测试不是空的,证明不了测试是对的、完整的。
  • Evolve 的位置:proposer 选改法,可改范围由清单定、评测冻结在 proposer 看不到的地方 → L1;在「五级自主」里大约是 L2。
  • 它的扩展实验本身就是 RSI 争论的一手数据:「AI 研发人力能不能线性扩展」——这里测到了收益递减、协调开销和规划瓶颈。判断
  • 和同类框架比:最接近 Evolve 的是 AgentCore optimization(改的对象几乎一样);最接近 Swarm 的是 Cursor 的 planner / worker 模式。逐个框架的对照见 业务大图。
