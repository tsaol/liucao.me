一句话结论

结论

可以做成案例:它是「从 autoresearch 走到真实业务」的现成证据

在一个训练很贵、探索空间很大的推荐模型上,通用 agent 很快就钻进一个方向出不来;加上「宽探索 + 深推进」的 harness 之后,用 40% 的预算拿到了多 41% 的提升。

  • 真实客户场景(小红书推荐),AWS AI Lab 共创
  • 跑在 Amazon Bedrock + EC2 上
  • 数据集和目标模型都是公开的,可以复现

CHAPTER 01

案例在做什么:让 AI 研究员迭代推荐模型

为什么比 autoresearch 难

难点 ①
探索空间大
推荐模型从 DCN、DLRM 演进到 HSTU、RankMixer,结构还在变;数据处理、特征工程、训练目标也都影响效果。这是一个系统工程,不是调几个超参。
难点 ②
训练很贵
真实业务里训一次推荐模型要几十到几百 GPU 小时;autoresearch 每次只训 5 分钟。每一次无效尝试都更贵,能试的次数也更少。

实验设置:目标模型是 RankMixer(用开源的 UniRank 实现),数据集是公开的 KuaiRand;主任务是点击预测的 AUC,另有关注、点赞、评论、转发、长观看 5 个辅助任务,改进不能让辅助任务明显变差。

先拿通用 agent 当基线:能改,但改不远

给一个通用的强 agent 200 GPU·h 预算,不让人插手,AUC 提升了 1.33pp —— 说明可行;人给出已验证的思路时,它总能正确写出代码 —— 写代码不是瓶颈。但看它的轨迹,有三个问题:

问题 ①
76% 的收益在前 30% 的时间
后面 70% 的时间几乎白花,很难持续改进。
问题 ②
86% 的预算押在一个方向
一开始这个方向有效,之后边际收益很快变小,它还在反复改 —— 探索太早收敛。
问题 ③
50 篇论文只读了一点
读论文的调用只占全部工具调用的 2.7%,而且都在前 9 小时。不读外部知识,是方向收敛的主要原因之一。
一句话:代码写得出来,难的是决定下一步往哪儿探索。

CHAPTER 02

他们的 harness:宽探索 + 深推进

Wide-and-Deep 探索策略

Wide 分支 · 广撒网
一次提至少 8 个想法,便宜地初筛
  • 固定从最初的基线版本出发
  • 减少训练步数,省钱
  • 目的:快速判断哪些思路可行,给后面的决策提供数据
每一轮由 agent 自己决定
走 Wide 还是 Deep
参考四样东西:最近几轮的复盘结论 · 有没有出现新的最佳模型 · 历史探索的多样性 · 上次走 Wide 是什么时候
不设硬规则和阈值
Deep 分支 · 往深里推
一次 1 个提案,推高当前最佳
  • 可以基于任何历史版本继续改
  • 可以把几个版本的有效思路合并
  • 没涨分的版本也能当「反面证据」参考

和常见做法的区别:很多系统按分数或 UCT 这类规则自动选「下一轮从哪个版本出发」;这里把这个决定交给 agent 自己判断。

三个 agent 分工,每一轮换一组新的

1
Proposal Agent

决定走 Wide 还是 Deep,从论文、代码、数据集、历史结果四个方面找思路,写出提案(Wide ≥ 8 个,Deep 1 个)

2
Developing Agent

按提案写代码;先设计「归因链」和要观测的变量,做静态检查和代码评审,再开始训练。多个提案并发处理

3
Evaluation Agent

出客观结论(各任务 AUC、归因链是否成立)和主观结论(这个方向值不值得继续)

上下文分三类
提示词 · 交接文档 · 长期记忆
一轮里的 agent 之间用简单的交接文档传信息;跨轮的信息写进长期记忆,下一轮的 agent 不继承上一轮的上下文。按「最小必要」给每个 agent 配上下文。
长期记忆四类
论文 · 知识库 · 排行榜 · 代码
论文库;每轮实验结论组成的知识库;当前最佳模型的排行榜;代码库本身也当记忆,用 git 管理。

评估:不只看 AUC

层次看什么怎么判
黑盒主任务 ΔAUC;辅助任务 ΔAUC 不能明显下降代码规则计算
玻璃盒探索多样性、读论文次数、分析数据集次数多样性用 LLM 归类;次数用代码统计
主观Wide / Deep 选择、「要不要继续这个方向」和人的判断是否一致人工评判
为什么重要:只看最终分数,看不出「AI 研究员」是不是在好好做研究。看多样性和读论文次数,能提前发现它钻牛角尖。

结果

效率
40% 的预算,多 41% 的提升
AUC +1.88pp,比基线的 +1.33pp 高约 41%;只用了 80 GPU·h。
多样性
最佳模型用了 4 类改进思路
基线几乎只在一个方向上改;这里在 Wide 和 Deep 两个分支都充分探索,持续刷新最佳模型。
研究行为
读论文 50 次、分析数据 162 次
共读了 25 篇不同的论文;探索行为明显更广。

训练用 g6.2xlarge 实例,基座模型来自 Amazon Bedrock(博客未写具体型号)。数字来自博客,是一次实验的结果,没有给出多次重复的方差。

和我们的关系

它补上了我们分享里的哪一环

我们讲的这个案例里的对应
autoresearch 的局限:只留一条线、没有档案基线 agent 的 76% / 86% / 2.7% —— 同样的问题在真实业务里出现了
DGM 的「达尔文」那一半:留档案、保持多样性、不只留第一名Wide 分支保证多样性;Deep 分支可以从任何历史版本出发、合并多个版本;长期记忆就是档案
Play demo:ShinkaEvolve 按分数加权选亲本不按分数选,让 agent 自己判断下一轮走哪条路 —— 一个值得我们对比的设计点
Argus:planner 写规格、worker 开发、独立判分Proposal / Developing / Evaluation 三个 agent 分工,每轮换新的一组,靠交接文档和长期记忆传信息
「评测放在改不到的地方」主任务和辅助任务 AUC 由代码规则算;另加玻璃盒指标监督「研究行为」
「先建评估,再谈进化」他们按 ADLC 框架,先设计评估体系(黑盒 / 玻璃盒 / 主观),再改 harness

能不能做成我们的案例

够格的地方

真实、而且是 AWS 的
客户场景 + AWS AI Lab 共创 + Bedrock / EC2
比论文里的公司自述更有说服力,讲给客户听也最直接。
能复现
数据和模型都是公开的
KuaiRand 数据集、UniRank 里的 RankMixer 实现都是开源的(Apache-2.0),可以在自己的账号里复现基线。
故事完整
有基线、有问题诊断、有设计、有结果
先证明「能改」,再找出「改不远」的原因,针对性地改 harness,最后用更少预算拿到更多提升。
切中要害
难点在「往哪儿探索」
和我们分享的主线一致:写代码不难,难的是探索和验证。

还缺什么(做成案例前要补)

  • 是公开数据,不是小红书线上数据:KuaiRand 上的结果,和真实业务的线上收益之间还有距离;需要确认有没有线上验证。
  • 一次实验,没有方差:+1.88pp 和 +1.33pp 的差,需要多跑几次、看波动,才能说得硬。
  • 基座模型没写:用的是 Bedrock 上哪个模型、多少 token 成本,博客没写。
  • harness 代码没公开:Wide-and-Deep 的提示词、三个 agent 的工具和交接格式,是复现的关键。
  • 成本账:GPU·h 之外,agent 本身的推理成本是多少。

CHAPTER 06

动手复现:用公开代码先跑起来

公开能拿到的

目标模型
UniRank · RankMixer
salmon1802/UniRank,Apache-2.0。15 种排序模型,含 RankMixer;自带预处理、配置和评测代码。
数据集
KuaiRand
短视频推荐数据,约 3.2 亿条交互,6 个任务;UniRank 里有现成的预处理脚本。
算力和模型
EC2 g6 + Amazon Bedrock
博客用 g6.2xlarge 训练;agent 的基座模型走 Bedrock。

建议的四步

1
跑通基线

在 KuaiRand 上训练 RankMixer,拿到主任务和辅助任务的 AUC,确认单次训练要多少 GPU·h

2
通用 agent 基线

给同样的预算,让通用 agent 自己改;记录收益曲线、方向分布、读论文次数

3
加 Wide-and-Deep

拆成 Proposal / Developing / Evaluation,加长期记忆和 Wide / Deep 分支

4
对照评估

同预算比 ΔAUC;多跑几次看波动;加上玻璃盒指标

第 3 步可以直接复用我们已有的东西:Play 的进化引擎(ShinkaEvolve)可以作为「按分数选亲本」的对照组,Argus 的 planner / worker / 判分结构可以承载三个 agent 的分工。
